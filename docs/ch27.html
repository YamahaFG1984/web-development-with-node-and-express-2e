第 27 章

实时通信

到现在为止，所有数据流动都由浏览器发起：它问，服务器答。 这一章反转这个方向 —— 让服务器主动推。通知、进度条、协作编辑、AI 流式输出， 都建立在这个能力上。

本章目标

  • 分清轮询、SSE、WebSocket 三者的适用场景，别一上来就选 WebSocket
  • 用 hono/streaming 实现服务器推送，包括 AI 流式输出
  • 处理断线重连和消息补发
  • 理解多实例部署下「广播」为什么会失效，以及怎么解决
  • 知道边缘环境下的特殊做法（Durable Objects）

三种方案

★ 大多数「实时」需求用 SSE 就够了

人们习惯性地一想到实时就用 WebSocket，但盘一下真实需求： 通知推送、订单状态更新、任务进度条、日志流、AI 流式回复 —— 这些全都是单向的（服务器 → 浏览器）。
浏览器要发消息？用普通的 fetch POST 就行，不需要走同一条长连接。
真正需要 WebSocket 的是：多人协作光标、实时对战游戏、语音视频信令 —— 浏览器需要每秒发几十条消息的场景。

被低估的方案：轮询

// 别嘲笑它 —— 对于「查任务做完没」这类需求，这是最合理的方案
async function pollJobStatus(jobId: string, onUpdate: (s: JobStatus) => void) {
  let delay = 1000
  while (true) {
    const res = await fetch(`/api/v1/jobs/${jobId}`)
    const job = await res.json()
    onUpdate(job)

    if (job.status === 'done' || job.status === 'failed') return job

    await new Promise((r) => setTimeout(r, delay))
    delay = Math.min(delay * 1.5, 10_000)   // 退避：越等越久，减少无效请求
  }
}
💡 轮询的优点是「没有连接状态」

长连接会带来一整类新问题：连接数上限、心跳、超时、代理断连、多实例广播、 优雅重启时如何迁移连接。轮询完全没有这些 —— 每次都是一个独立的普通请求， 可以缓存、可以负载均衡、可以随便重启。
第 25 章那个「202 + 查状态」的接口设计，配上退避轮询，能覆盖非常多的场景。

SSE

Server-Sent Events 本质上是一个永远不结束的 HTTP 响应： Content-Type 是 text/event-stream，服务器不断往里写数据，浏览器边收边处理。 

GET /api/v1/notifications HTTP/1.1
Accept: text/event-stream

HTTP/1.1 200 OK
Content-Type: text/event-stream

id: 1
event: notification
data: {"title":"订单已确认","orderId":"o_123"}

id: 2
event: notification
data: {"title":"已发货","orderId":"o_123"}

: 这是注释，用来做心跳保活

服务端

import { streamSSE } from 'hono/streaming'

app.get('/api/v1/notifications', async (c) => {
  const userId = c.get('user').id
  // 浏览器重连时会带上这个头，告诉你它收到哪儿了
  const lastEventId = c.req.header('Last-Event-ID')

  return streamSSE(c, async (stream) => {
    // ① 先补发断线期间错过的消息
    if (lastEventId) {
      const missed = await getNotificationsAfter(userId, lastEventId)
      for (const n of missed) {
        await stream.writeSSE({ id: n.id, event: 'notification', data: JSON.stringify(n) })
      }
    }

    // ② 然后持续推送新消息
    let alive = true
    stream.onAbort(() => { alive = true && (alive = false) })

    while (alive) {
      const batch = await waitForNotifications(userId, { timeoutMs: 25_000 })

      if (batch.length === 0) {
        // 没消息也要定期发点东西，否则代理会认为连接死了直接掐断
        await stream.writeSSE({ data: '', event: 'ping' })
        continue
      }

      for (const n of batch) {
        await stream.writeSSE({ id: n.id, event: 'notification', data: JSON.stringify(n) })
      }
    }
  })
})

⚠ SSE 的两个坑
  • HTTP/1.1 下同域最多 6 个连接。用户开了 7 个标签页，第 7 个就连不上， 而且会莫名其妙地卡住其他请求。HTTP/2 没这个问题（多路复用）， 所以用 SSE 前先确认你的服务走的是 HTTP/2。
  • 中间的代理会掐连接。Nginx 默认 60 秒无数据就断开。 所以必须发心跳（哪怕是一行注释 :ping），周期要小于代理的超时。

用 SSE 做 AI 流式输出

这是今天 SSE 最常见的用途。LLM 生成一段话要几秒，如果等全部生成完再返回， 用户面对的是几秒空白；流式输出则是一个字一个字往外蹦，感知延迟接近于零。 

import { streamSSE } from 'hono/streaming'
import Anthropic from '@anthropic-ai/sdk'

app.post('/api/v1/assistant', zValidator('json', z.object({ prompt: z.string().max(2000) })), async (c) => {
  const { prompt } = c.req.valid('json')
  const client = new Anthropic({ apiKey: c.env.ANTHROPIC_API_KEY })

  return streamSSE(c, async (stream) => {
    let aborted = false
    // 用户关掉页面时，要停止计费！
    stream.onAbort(() => { aborted = true })

    try {
      const result = client.messages.stream({
        model: 'claude-sonnet-5',
        max_tokens: 1024,
        messages: [{ role: 'user', content: prompt }],
      })

      for await (const event of result) {
        if (aborted) break
        if (event.type === 'content_block_delta' && event.delta.type === 'text_delta') {
          await stream.writeSSE({ event: 'delta', data: event.delta.text })
        }
      }

      if (!aborted) await stream.writeSSE({ event: 'done', data: '' })
    } catch (err) {
      console.error('AI 调用失败', err)
      await stream.writeSSE({ event: 'error', data: '生成失败，请重试' })
    }
  })
})
★ onAbort 在这里直接等于钱

用户看了两句就关掉页面，但如果你不监听中断，服务端会继续把整段生成完 —— token 照常计费，连接照常占着。
任何按量计费的流式接口都要处理中断。这是第 22 章「超时预算」思路的延伸： 不要为已经没人要的结果付钱。 

// 浏览器端：注意 EventSource 只支持 GET，POST 要用 fetch + 手动解析
const res = await fetch('/api/v1/assistant', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ prompt }),
  signal: controller.signal,          // 用户点「停止」时 controller.abort()
})

const reader = res.body.getReader()
const decoder = new TextDecoder()
let buffer = ''

while (true) {
  const { done, value } = await reader.read()
  if (done) break

  buffer += decoder.decode(value, { stream: true })
  const chunks = buffer.split('\n\n')
  buffer = chunks.pop() ?? ''          // 最后一段可能不完整，留到下一轮

  for (const chunk of chunks) {
    const data = chunk.split('\n').find((l) => l.startsWith('data: '))?.slice(6)
    if (data) appendToOutput(data)
  }
}
ⓘ 为什么要留 buffer

网络传输不保证按消息边界切分 —— 一次 read() 可能拿到一条半消息。 直接按 \n\n 切会把最后那半条丢掉或解析错。
把不完整的尾巴留到下一轮，是所有流式协议解析的通用模式。

WebSocket

当浏览器也需要高频发消息时，才轮到 WebSocket。各运行时的支持方式不同：

// Bun / Deno / Cloudflare Workers 通用写法
import { upgradeWebSocket } from 'hono/bun'      // 或 hono/deno、hono/cloudflare-workers

app.get('/ws', upgradeWebSocket((c) => {
  const userId = c.get('user').id

  return {
    onOpen(_evt, ws) {
      console.log('连接建立', userId)
      hub.join(userId, ws)
    },
    onMessage(evt, ws) {
      const msg = JSON.parse(String(evt.data))
      if (msg.type === 'cursor') {
        hub.broadcast(msg.docId, { type: 'cursor', userId, pos: msg.pos }, { except: userId })
      }
    },
    onClose() {
      hub.leave(userId)
    },
    onError(err) {
      console.error('WebSocket 错误', err)
    },
  }
}))
⚠ Node.js 上不能直接用

@hono/node-server 需要额外的 @hono/node-ws 包来支持 WebSocket 升级， 因为 Node 的 http 模块处理 upgrade 的方式和 Web 标准不一样。
这也是本章推荐优先用 SSE 的一个现实原因：SSE 就是普通 HTTP，哪儿都能跑。

浏览器端要自己写重连

function connect(url, onMessage) {
  let ws
  let retry = 0
  let heartbeat

  const open = () => {
    ws = new WebSocket(url)

    ws.onopen = () => {
      retry = 0                                    // 成功了就重置退避
      heartbeat = setInterval(() => {
        if (ws.readyState === WebSocket.OPEN) ws.send('{"type":"ping"}')
      }, 25_000)
    }

    ws.onmessage = (e) => onMessage(JSON.parse(e.data))

    ws.onclose = () => {
      clearInterval(heartbeat)
      // 指数退避 + 抖动（和第 22 章重试同一个道理）
      const delay = Math.min(1000 * 2 ** retry++, 30_000) + Math.random() * 1000
      setTimeout(open, delay)
    }
  }

  open()
  return { close: () => { clearInterval(heartbeat); ws?.close() } }
}
★ 重连必须带退避

没有退避的重连是自杀式的：服务器重启的那 30 秒， 一万个客户端每秒重连一次 = 每秒 10000 个连接请求，服务器刚起来就被打死， 然后又重启……形成死循环。
加上随机抖动同样重要，否则所有客户端会在同一时刻整齐划一地重连。

多实例的广播问题

这是长连接最大的架构陷阱，也是第 12 章「无状态」原则的直接后果。 

import { Redis } from 'ioredis'

const pub = new Redis(process.env.REDIS_URL!)
const sub = new Redis(process.env.REDIS_URL!)   // 订阅要用独立连接

// 本实例持有的连接
const local = new Map<string, Set<WSContext>>()

// 启动时订阅
sub.subscribe('broadcast')
sub.on('message', (_channel, payload) => {
  const { room, data } = JSON.parse(payload)
  for (const ws of local.get(room) ?? []) {
    ws.send(JSON.stringify(data))
  }
})

// 广播 = 发到 Redis，让所有实例（包括自己）都收到
export async function broadcast(room: string, data: unknown) {
  await pub.publish('broadcast', JSON.stringify({ room, data }))
}

Cloudflare 上的另一种思路

ⓘ Durable Objects：把「有状态」正当化

Workers 是无状态的，跑不了长连接的房间管理。Cloudflare 给的答案是 Durable Object：一个全球唯一的对象实例，有自己的内存和存储， 所有针对它的请求都路由到同一个地方。

于是「一个聊天室 = 一个 Durable Object」，所有成员的 WebSocket 都连到同一个实例上， 广播就是简单的内存遍历，不需要 Redis。第 23 章讲的并发问题在这里也自动消失了 —— 因为它天然串行。 

export class ChatRoom implements DurableObject {
  private sessions = new Set<WebSocket>()

  constructor(private state: DurableObjectState, private env: Env) {}

  async fetch(request: Request) {
    const pair = new WebSocketPair()
    const [client, server] = Object.values(pair)

    server.accept()
    this.sessions.add(server)

    server.addEventListener('message', (evt) => {
      // 房间里所有人都连在这一个对象上，广播就是遍历
      for (const ws of this.sessions) {
        if (ws !== server) ws.send(evt.data)
      }
    })

    server.addEventListener('close', () => this.sessions.delete(server))

    return new Response(null, { status: 101, webSocket: client })
  }
}

运维上要注意的

问题说明与对策
连接数就是内存 每条连接几十 KB。一万条连接就是几百 MB，还占一个文件描述符。要监控连接数并设上限
部署会断开所有连接 滚动更新时全体客户端重连 —— 这正是退避抖动存在的意义。发版尽量选低峰
慢客户端造成反压 对方网络差，你写得比他收得快，缓冲区无限增长直到 OOM。要监控发送缓冲，超阈值就丢消息或断开
鉴权时机不同 WebSocket 握手后就没有请求头了。要在升级前验证身份，并定期检查会话是否已失效
浏览器 EventSource 不能带自定义头 没法传 Authorization。用 Cookie 认证，或者把短期令牌放在查询串里
无法水平缓存 长连接不能走 CDN 缓存，每条都实打实占着一个后端资源
⚠ 别把长连接当数据库用

常见错误：把「当前在线用户」「房间成员列表」只存在实例内存里。 实例一重启，这些状态全没了，而且别的实例根本看不到。
连接是易失的，状态要落库。内存里只保留「连接对象本身」， 其余一切（谁在哪个房间、消息历史）都存数据库或 Redis。

优雅降级

企业内网代理、老旧浏览器、某些移动网络都可能让长连接建立不起来。 好的实现要能退回到轮询： 

function subscribe(onMessage) {
  if (typeof EventSource === 'undefined') return startPolling(onMessage)

  const source = new EventSource('/api/v1/notifications')
  let gotAnything = false

  source.addEventListener('notification', (e) => {
    gotAnything = true
    onMessage(JSON.parse(e.data))
  })

  // 8 秒内一条都没收到（连心跳都没有）→ 认为环境不支持，退回轮询
  setTimeout(() => {
    if (!gotAnything) {
      console.warn('SSE 似乎不可用，退回轮询')
      source.close()
      startPolling(onMessage)
    }
  }, 8000)

  return source
}

小结

  • 选型顺序：轮询 → SSE → WebSocket，从简单往复杂选，不要反过来。
  • 绝大多数「实时」需求是单向的，SSE 就够，而且它就是普通 HTTP，哪儿都能跑。
  • SSE 自带重连和 Last-Event-ID 补发，这是它相对 WebSocket 的最大优势。
  • 心跳必须有，周期要小于中间代理的超时。
  • 流式接口一定要处理 onAbort，尤其是按量计费的 AI 调用。
  • 解析流式数据时要保留不完整的尾巴到下一轮。
  • 多实例下广播必须走 pub/sub；Cloudflare 上可以用 Durable Objects 绕开这个问题。
  • 重连必须指数退避加抖动，否则会在服务恢复时把它再打死一次。
  • 连接是易失的，状态要落库。

动手练习

  1. 做一个 /api/v1/clock 的 SSE 端点，每秒推一次当前时间。用 curl -N 直接观察原始的事件流格式。
  2. 在浏览器里用 EventSource 连上它。然后把服务器停掉，在 Network 面板观察浏览器自动重连的行为和间隔。
  3. 给第 25 章的报表任务加一个 SSE 进度推送，替换掉轮询。对比两种实现的代码量和体验。
  4. 实现 AI 流式输出（可以先用一个假的、逐字吐出的生成器代替真实 API）。加上「停止生成」按钮，确认服务端的 onAbort 真的被触发了。
  5. 把心跳去掉，让连接空闲 5 分钟，看看它会不会被断开。然后加回心跳再试。
  6. 想一想：如果你的服务跑了 3 个实例，用户 A 连在实例 1 上，怎么让实例 3 处理的一个请求把消息推给 A？
