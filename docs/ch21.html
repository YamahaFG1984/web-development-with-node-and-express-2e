第 21 章

并发与数据一致性

第 13 章教了怎么读写数据库。这一章要问一个它没问的问题： 如果两个请求在同一毫秒到达，会发生什么？ 超卖、重复扣款、丢失更新 —— 线上事故的大头都藏在这里，而它们在本地几乎不可能复现。

本章目标

  • 看懂竞态条件是怎么产生的，以及为什么本地测不出来
  • 掌握事务和隔离级别，知道「读到了脏数据」到底是怎么回事
  • 会用乐观锁和悲观锁，知道各自的适用场景
  • 用原子更新和数据库约束兜底
  • 实现幂等，让重复请求不造成重复后果
  • 写出能真的复现竞态的测试

为什么本地测不出来

你一个人点页面，请求是一个接一个的。线上有一千个人同时点，请求是交错的。 这是两种完全不同的世界。 

// 看起来完全正常的「秒杀」代码
app.post('/vacations/:sku/book', async (c) => {
  const sku = c.req.param('sku')

  const v = await repo.findBySku(sku)            // ① 读
  if (v.remaining <= 0) {                        // ② 判断
    return c.json({ error: '已售罄' }, 409)
  }

  await repo.update(sku, { remaining: v.remaining - 1 })   // ③ 写
  await repo.createOrder({ sku, userId })

  return c.json({ ok: true })
})

这段代码有个致命问题。把两个请求的执行时刻画在一条时间轴上就看清楚了：

★ 记住这个模式的名字

check-then-act（先检查再行动）—— 先读一个值，根据它做判断，然后基于判断去写。 只要「读」和「写」之间有任何间隙，另一个请求就可能挤进来，让你的判断在写入时已经过期了。

这个模式在代码里到处都是：检查库存再扣减、检查邮箱是否已注册再插入、 检查余额是否够再扣款、检查文件是否存在再创建。它们全都有同一个 bug。

为什么开发时发现不了

本地开发生产环境
你一个人手动点击成百上千用户同时操作
请求间隔以秒计请求间隔以毫秒计，甚至完全重叠
一个进程多个实例 / 多个边缘节点
数据库在本机，延迟 0.1 ms网络延迟 5–50 ms，「间隙」被放大几百倍
测试是串行跑的—

最后一行尤其关键：你写的单元测试和集成测试默认都是串行的， 它们永远不会触发竞态。除非你专门去写并发测试（本章最后会讲）。

同一邮箱同时提交两次，两条 SELECT 都说「没注册过」，于是插入了两个账号。

事务

事务把多个操作打包成一个「全成功或全失败」的单元。这是数据库给你的第一件武器。 

import { drizzle } from 'drizzle-orm/d1'
import { eq, sql } from 'drizzle-orm'

await db.transaction(async (tx) => {
  // 从 A 账户扣钱
  await tx.update(accounts)
    .set({ balance: sql`${accounts.balance} - ${amount}` })
    .where(eq(accounts.id, fromId))

  // 给 B 账户加钱
  await tx.update(accounts)
    .set({ balance: sql`${accounts.balance} + ${amount}` })
    .where(eq(accounts.id, toId))

  // 记一笔流水
  await tx.insert(transfers).values({ fromId, toId, amount })

  // 任何一步抛异常 → 整个事务回滚，前面的操作全部撤销
})

ACID 是什么

字母含义白话
Atomicity 原子性要么全做，要么全不做不会出现「钱扣了但没到账」
Consistency 一致性事务前后数据都满足约束余额不会变成负数（如果你定义了 CHECK 约束）
Isolation 隔离性并发事务互不干扰本章的重点，也是最容易误解的一个
Durability 持久性提交后即使断电也不丢数据库替你保证
⚠ 事务 ≠ 解决了并发问题

这是最常见的误解。把上面那段超卖代码包进事务里，它照样超卖。
因为默认的隔离级别下，两个事务可以同时读到 remaining = 1， 各自判断「够」，然后各自写入 0。事务保证的是「你这几步要么全成要么全败」， 不保证「别人不会在中间插队」。

隔离级别

ⓘ 各数据库的默认级别
  • PostgreSQL：Read Committed
  • MySQL (InnoDB)：Repeatable Read
  • SQLite / Cloudflare D1：Serializable（因为它本质上串行执行写操作）

注意 D1 那一行 —— 如果你的应用只跑在 D1 上，很多并发问题会自动消失。 但这不是可以不理解它们的理由：一旦换成 Postgres，或者你的逻辑跨了数据库和 KV，问题立刻回来。

最好的办法：让数据库来判断

在讲锁之前，先说一个更简单也更该优先考虑的思路： 把「读—判断—写」压缩成一条 SQL，让判断发生在数据库内部。

❌ 在应用里判断
const v = await repo.findBySku(sku)
if (v.remaining <= 0) {
  return c.json({ error: '已售罄' }, 409)
}
await repo.update(sku, {
  remaining: v.remaining - 1
})
✅ 让数据库判断
const rows = await db
  .update(vacations)
  .set({
    remaining: sql`${vacations.remaining} - 1`
  })
  .where(and(
    eq(vacations.sku, sku),
    gt(vacations.remaining, 0)   // ← 关键
  ))
  .returning({ left: vacations.remaining })

if (rows.length === 0) {
  return c.json({ error: '已售罄' }, 409)
}
★ 为什么这样就安全了

单条 UPDATE 在数据库内部是原子的 —— 数据库会对这一行加锁，判断和写入之间没有任何间隙可以插队。
WHERE remaining > 0 不成立时，这条语句影响 0 行， returning 返回空数组，你据此判断「抢完了」。
两个请求同时执行，数据库会让它们排队：第一个把 1 改成 0，第二个的 WHERE 不成立， 影响 0 行。不会超卖。

约束是最后一道防线

-- 库存不能为负，写进表定义里
ALTER TABLE vacations ADD CONSTRAINT remaining_non_negative
  CHECK (remaining >= 0);

-- 一个邮箱只能注册一次
CREATE UNIQUE INDEX idx_users_email ON users (lower(email));

-- 同一个用户对同一个套餐只能有一条「到季通知」
CREATE UNIQUE INDEX idx_listener ON in_season_listeners (email, sku);

有了唯一约束，「先查再插」的竞态就变成了一个可以捕获的错误：

// ❌ 有竞态：两个请求可能同时通过检查
const existing = await db.select().from(users).where(eq(users.email, email))
if (existing.length) return c.json({ error: '邮箱已注册' }, 409)
await db.insert(users).values({ email, ... })

// ✅ 直接插，让数据库拒绝重复
try {
  await db.insert(users).values({ email, ... })
} catch (err) {
  if (isUniqueViolation(err)) {
    return c.json({ error: '邮箱已注册' }, 409)
  }
  throw err
}

// ✅ 或者用 upsert 语义，完全不需要判断
await db.insert(inSeasonListeners)
  .values({ email, sku })
  .onConflictDoNothing()
💡 这个思路叫「乐观执行」

与其小心翼翼地先检查再动手（检查结果随时可能过期），不如直接动手，让数据库告诉你行不行。 代码更短，而且没有竞态窗口。
应用层的检查仍然有价值 —— 用来给出友好的错误提示 —— 但它不能作为正确性的依据。 真正的保证必须在数据库层。

两种锁

原子更新解决不了所有问题。当一次操作要读出数据、在应用里做复杂计算、再写回去时， 就需要锁了。

乐观锁：假设不会冲突，冲突了就重试

export const articles = sqliteTable('articles', {
  id: text('id').primaryKey(),
  title: text('title').notNull(),
  body: text('body').notNull(),
  version: integer('version').notNull().default(1),   // ← 版本号
})

export async function updateArticle(
  id: string,
  patch: { title?: string; body?: string },
  expectedVersion: number
) {
  const rows = await db
    .update(articles)
    .set({ ...patch, version: expectedVersion + 1 })
    .where(and(
      eq(articles.id, id),
      eq(articles.version, expectedVersion)   // ← 版本必须没变
    ))
    .returning()

  if (rows.length === 0) {
    throw new HTTPException(409, {
      message: '这篇文章已被他人修改，请刷新后重试',
    })
  }
  return rows[0]
}

悲观锁：先占住，别人等着

await db.transaction(async (tx) => {
  // FOR UPDATE：锁住这一行，直到事务结束
  const [account] = await tx
    .select()
    .from(accounts)
    .where(eq(accounts.id, id))
    .for('update')

  // 在应用里做复杂计算（这段时间别人读这一行会被阻塞）
  const fee = calculateComplexFee(account, request)

  if (account.balance < fee) {
    throw new HTTPException(400, { message: '余额不足' })
  }

  await tx.update(accounts)
    .set({ balance: account.balance - fee })
    .where(eq(accounts.id, id))
})
乐观锁悲观锁
假设冲突很少见冲突很常见
做法写入时检查版本，冲突了报错/重试读取时就加锁，别人排队等
适合后台文章编辑、用户资料修改秒杀、账户余额、票务座位
优点不阻塞，吞吐高不会失败，逻辑简单
缺点冲突时用户要重做并发低；有死锁风险；持锁期间不能干慢活
边缘环境可用需要真正的事务型数据库，KV 上做不了
⚠ 持锁的时候绝不能做这三件事
  1. 调用外部 API。对方慢 5 秒，你就锁了 5 秒，所有等这一行的请求全部堆积。
  2. 等待用户输入。「锁住座位等他填完表单」—— 用户去泡了杯咖啡，锁就一直在。
  3. 按不同顺序锁多行。A 先锁 1 再锁 2，B 先锁 2 再锁 1 → 死锁。 规则：永远按同一个固定顺序加锁（比如按主键升序）。

幂等：重复请求不造成重复后果

上面讲的都是「多个不同用户同时操作」。还有另一类问题：同一个请求被发了两次。

为什么会重复说明
用户双击提交按钮最常见，前端禁用按钮能挡住大部分但不是全部
用户网络卡了刷新页面如果没用第 8 章的 303 重定向，浏览器会重新提交
客户端自动重试第 20 章讲过：响应超时了，但服务器其实处理成功了
第三方 webhook 重投支付平台没收到你的 200，就会一直重发
队列的重试下一章会讲：至少一次投递意味着可能投递多次
★ 幂等的定义

一个操作执行一次和执行 N 次，对系统状态的影响相同。
SET balance = 100 是幂等的。balance = balance - 10 不是。
注意「幂等」说的是结果，不是不执行。重复请求可以照常返回成功， 只是不能产生第二笔订单。

幂等键

export const idempotencyKeys = sqliteTable('idempotency_keys', {
  key: text('key').primaryKey(),
  userId: text('user_id').notNull(),
  responseBody: text('response_body', { mode: 'json' }).notNull(),
  createdAt: integer('created_at', { mode: 'timestamp' }).notNull(),
})

app.post('/api/v1/orders', async (c) => {
  const key = c.req.header('Idempotency-Key')
  if (!key) {
    throw new HTTPException(400, { message: '缺少 Idempotency-Key 请求头' })
  }

  const userId = c.get('user').id

  // 1. 这个键处理过吗？
  const [seen] = await db.select().from(idempotencyKeys)
    .where(and(eq(idempotencyKeys.key, key), eq(idempotencyKeys.userId, userId)))

  if (seen) {
    // 处理过了，原样返回上次的结果
    return c.json(seen.responseBody as object, 200, { 'Idempotent-Replay': 'true' })
  }

  // 2. 没处理过：业务 + 记键，同一个事务
  const body = await c.req.json()

  try {
    const result = await db.transaction(async (tx) => {
      const order = await createOrderIn(tx, userId, body)
      await tx.insert(idempotencyKeys).values({
        key, userId,
        responseBody: { orderId: order.id },
        createdAt: new Date(),
      })
      return { orderId: order.id }
    })
    return c.json(result, 201)
  } catch (err) {
    // 两个请求同时到达时，慢的那个会在这里撞上主键冲突
    if (isUniqueViolation(err)) {
      const [now] = await db.select().from(idempotencyKeys)
        .where(eq(idempotencyKeys.key, key))
      return c.json(now.responseBody as object, 200)
    }
    throw err
  }
})
💡 键从哪来

客户端生成，用 crypto.randomUUID()，并且在重试时使用同一个键 —— 这是关键。如果每次重试都换个新键，幂等就失效了。
表单场景可以在渲染页面时生成一个键放进隐藏字段，这样用户刷新重复提交也能被识别。
别忘了给这张表加过期清理（比如保留 24 小时），否则它会无限增长。

多实例带来的额外麻烦

上面的方案都依赖数据库来做仲裁。一旦状态跑到数据库之外，事情就变复杂了。

⚠ 这些「优化」会悄悄破坏正确性
  • 进程内缓存。「我把库存缓存在内存里减少查询」—— 三个实例三份缓存， 全都是过期的（第 12 章讲过）。
  • 进程内的锁。JavaScript 里用一个 Map 记「这个 sku 正在处理中」—— 只对当前进程有效，另外两个实例根本不知道。
  • KV 上做计数器。Cloudflare KV 是最终一致的， get 到的值可能是几秒前的。用它做「限量 100 个」必然超发。
需求用什么
强一致的计数、余额、库存关系型数据库的原子更新 / 事务
Cloudflare 上的强一致状态Durable Objects（每个对象全球单实例，天然串行）
限流计数（可以差一点点）Redis INCR，或 Cloudflare Rate Limiting
分布式锁Redis 的 SET key val NX EX 30；但先想想能不能不用
★ 分布式锁比你想的难

自己实现的分布式锁几乎总是有 bug：持锁的进程崩了怎么办（要有超时）？ 超时了但它其实还活着，两个进程同时以为自己持锁怎么办？释放锁时， 怎么保证你释放的是自己那把而不是别人的？
结论：能用数据库的原子操作解决，就别上分布式锁。 单条 UPDATE ... WHERE 能解决的问题，不要用一百行锁代码去解决。

怎么把竞态测出来

这是本章最实用的一节。竞态之所以难缠，是因为普通测试碰不到它。 但你可以主动制造并发： 

import { describe, it, expect, beforeEach } from 'vitest'

describe('库存扣减', () => {
  beforeEach(async () => {
    await resetDb()
    await seedVacation({ sku: 'HR199', remaining: 1 })   // 只有 1 份
  })

  it('20 个并发请求只能成功 1 个', async () => {
    // 关键：同时发出，而不是 for 循环里 await
    const results = await Promise.all(
      Array.from({ length: 20 }, () =>
        app.request('/vacations/HR199/book', { method: 'POST' })
      )
    )

    const ok = results.filter((r) => r.status === 200).length
    const soldOut = results.filter((r) => r.status === 409).length

    expect(ok).toBe(1)          // ← 有竞态的实现会得到 2、3 甚至 20
    expect(soldOut).toBe(19)

    // 更重要：验证数据库最终状态
    const v = await repo.findBySku('HR199')
    expect(v.remaining).toBe(0)
    expect(await countOrders('HR199')).toBe(1)
  })

  it('重复的幂等键只创建一个订单', async () => {
    const key = crypto.randomUUID()
    const send = () =>
      app.request('/api/v1/orders', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json', 'Idempotency-Key': key },
        body: JSON.stringify({ sku: 'HR199' }),
      })

    const [a, b] = await Promise.all([send(), send()])

    const bodyA = await a.json()
    const bodyB = await b.json()
    expect(bodyA.orderId).toBe(bodyB.orderId)     // 同一个订单
    expect(await countOrders('HR199')).toBe(1)
  })
})
💡 让竞态窗口变大，更容易复现

如果并发测试偶尔通过偶尔失败，说明窗口太窄。在「读」和「写」之间人为插一个延迟， 可以让 bug 稳定复现： 

const v = await repo.findBySku(sku)

// 只在测试环境生效的「竞态放大器」
if (process.env.RACE_DELAY) {
  await new Promise((r) => setTimeout(r, Number(process.env.RACE_DELAY)))
}

await repo.update(sku, { remaining: v.remaining - 1 })

修好之后再跑一遍：正确的实现加了延迟也应该通过。 这是验证「你是真修好了」还是「只是把窗口变窄了」的好办法。

自查清单

★ 在代码里找这些模式
  • ☐ 有没有「先 SELECT 判断，再 INSERT/UPDATE」的地方？ → 改成原子更新或依赖唯一约束
  • ☐ 有没有 x = x + 1 形式的读改写？ → 改成 SET x = x + 1 让数据库算
  • ☐ 表单编辑有没有可能静默覆盖别人的修改？→ 加版本号
  • ☐ 创建订单、扣款、发消息的接口，重复调用会怎样？→ 加幂等键
  • ☐ 有没有状态存在进程内存里？→ 挪到数据库或共享存储
  • ☐ 关键的业务约束（余额非负、唯一性）有没有写进数据库约束？
  • ☐ 持有锁的代码块里有没有网络调用？
  • ☐ 有没有至少一个并发测试？

小结

  • check-then-act 是所有竞态的根源：读和写之间的间隙会被别人插队。
  • 事务保证「全成或全败」，不保证「别人不插队」—— 两者是不同的问题。
  • 优先用原子更新（UPDATE ... WHERE 条件）把判断交给数据库。
  • 数据库约束（UNIQUE、CHECK）是最后一道防线，应用层检查只负责友好提示。
  • 乐观锁适合冲突少的编辑场景，悲观锁适合冲突多的抢占场景；持锁期间不做慢操作。
  • 幂等键让重复请求安全；键必须由客户端生成并在重试时复用。
  • 能用数据库原子操作就别上分布式锁。
  • 用 Promise.all 写并发测试，用人为延迟放大竞态窗口。

动手练习

  1. 给云雀旅行加一个「限量套餐」：remaining 字段初始为 1。先用有竞态的写法实现下单，然后写一个 20 并发的测试，看着它失败。
  2. 改成原子更新，让测试通过。再加上 RACE_DELAY=50 跑一次，确认仍然通过。
