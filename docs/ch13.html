第 13 章

持久化

到现在为止，我们的数据都存在内存里，重启就没。这一章给云雀旅行接上真正的存储： 数据库存结构化数据，对象存储放文件，KV 存会话。

本章目标

  • 知道四种存储各自适合装什么
  • 用一个抽象层把数据库细节挡在业务代码之外
  • 用 Drizzle ORM 定义表结构、写迁移、做增删改查
  • 把会话存储换成真正能用于生产的实现
  • 避开 N+1 查询、缺索引这些经典性能陷阱

四种存储

为什么不能用文件系统

// 第 8 章我们这样存了上传的照片
await writeFile(join('./data/photos', name), buffer)

这在本地能用，上线后有三个问题：

  • 扩不了容。两个实例各自有一份磁盘，A 存的文件 B 读不到（第 12 章讲过）。
  • 会丢。容器重启、实例替换，本地磁盘上的东西就没了。
  • 边缘环境根本没有可写磁盘。Workers 上这行代码直接报错。

正确做法是对象存储。以 Cloudflare R2 为例（S3 兼容，用法几乎一样）：

type Bindings = { BUCKET: R2Bucket }

app.post('/upload', async (c) => {
  const body = await c.req.parseBody()
  const photo = body.photo
  if (!(photo instanceof File)) return c.json({ error: '缺少文件' }, 400)

  const key = `photos/${crypto.randomUUID()}.jpg`

  await c.env.BUCKET.put(key, await photo.arrayBuffer(), {
    httpMetadata: { contentType: photo.type },
  })

  // 文件本身进对象存储，元信息进数据库
  await db.saveContestEntry({ email: String(body.email), photoKey: key })

  return c.json({ ok: true, key })
})

先建抽象层

在写任何数据库代码之前，先定义「业务需要什么操作」。 业务代码只认这个接口，不认数据库： 

export type Vacation = {
  sku: string
  name: string
  slug: string
  description: string
  price: number
  tags: string[]
  inSeason: boolean
  available: boolean
  maximumGuests: number
}

export interface VacationRepo {
  list(opts?: { available?: boolean }): Promise<Vacation[]>
  findBySku(sku: string): Promise<Vacation | null>
  addInSeasonListener(email: string, sku: string): Promise<void>
}
★ 抽象层的两个真实收益

① 测试变简单。写一个基于数组的内存实现，测处理函数时完全不需要数据库。
② 数据库能换。本教程会先用 SQLite 再展示 Postgres —— 业务代码一行不改。
代价是多写一层。但这层很薄，值得。

用 Drizzle 定义表

Drizzle 是目前对 Hono 最友好的 ORM： 轻量、类型推导极强、支持 SQLite / D1 / Postgres / MySQL，而且能在边缘环境跑。 

npm install drizzle-orm
npm install -D drizzle-kit

import { sqliteTable, text, integer, real, index } from 'drizzle-orm/sqlite-core'

export const vacations = sqliteTable(
  'vacations',
  {
    sku: text('sku').primaryKey(),
    slug: text('slug').notNull().unique(),
    name: text('name').notNull(),
    category: text('category'),
    description: text('description').notNull().default(''),
    price: real('price').notNull(),
    // SQLite 没有数组类型，用 JSON 文本存
    tags: text('tags', { mode: 'json' }).$type<string[]>().notNull().default([]),
    inSeason: integer('in_season', { mode: 'boolean' }).notNull().default(false),
    available: integer('available', { mode: 'boolean' }).notNull().default(true),
    maximumGuests: integer('maximum_guests').notNull().default(10),
    createdAt: integer('created_at', { mode: 'timestamp' }).notNull(),
  },
  (t) => ({
    // 经常按 available 过滤，加个索引
    availableIdx: index('idx_vacations_available').on(t.available),
  })
)

export const inSeasonListeners = sqliteTable('in_season_listeners', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  email: text('email').notNull(),
  sku: text('sku').notNull().references(() => vacations.sku),
  createdAt: integer('created_at', { mode: 'timestamp' }).notNull(),
})

// 类型可以从表定义自动推导出来，不用手写
export type VacationRow = typeof vacations.$inferSelect
export type NewVacation = typeof vacations.$inferInsert
ⓘ 命名风格：数据库用蛇形，代码用驼峰

SQL 世界的惯例是 in_season，JavaScript 的惯例是 inSeason。 Drizzle 让你在一处同时声明两者：inSeason: integer('in_season')。 左边给代码用，右边是真实列名。两边都保持地道，不用做转换。

迁移

不要手动改生产数据库的表结构。用迁移文件 —— 它是「数据库结构的版本控制」，能被提交、被 review、被自动执行。 

import { defineConfig } from 'drizzle-kit'

export default defineConfig({
  schema: './src/db/schema.ts',
  out: './drizzle',
  dialect: 'sqlite',
})

npx drizzle-kit generate

增删改查

import { drizzle } from 'drizzle-orm/d1'
import { eq, and, desc } from 'drizzle-orm'
import { vacations, inSeasonListeners } from './schema'
import type { VacationRepo, Vacation } from './types'

export function createVacationRepo(d1: D1Database): VacationRepo {
  const db = drizzle(d1)

  return {
    async list(opts = {}) {
      const conditions = []
      if (opts.available !== undefined) {
        conditions.push(eq(vacations.available, opts.available))
      }

      const rows = await db
        .select()
        .from(vacations)
        .where(conditions.length ? and(...conditions) : undefined)
        .orderBy(desc(vacations.createdAt))

      return rows.map(toVacation)
    },

    async findBySku(sku) {
      const rows = await db
        .select()
        .from(vacations)
        .where(eq(vacations.sku, sku))
        .limit(1)

      return rows[0] ? toVacation(rows[0]) : null
    },

    async addInSeasonListener(email, sku) {
      await db.insert(inSeasonListeners)
        .values({ email, sku, createdAt: new Date() })
        .onConflictDoNothing()          // 重复订阅不报错（这也是一种防并发的手段，见第 21 章）
    },
  }
}

function toVacation(row: typeof vacations.$inferSelect): Vacation {
  return {
    sku: row.sku,
    slug: row.slug,
    name: row.name,
    description: row.description,
    price: row.price,
    tags: row.tags,
    inSeason: row.inSeason,
    available: row.available,
    maximumGuests: row.maximumGuests,
  }
}

在应用里接上去：

type Bindings = { DB: D1Database; BUCKET: R2Bucket }
type Variables = { repo: VacationRepo }

const app = new Hono<{ Bindings: Bindings; Variables: Variables }>()

// 每个请求构造一次仓库（Workers 上不能在模块顶层拿 c.env）
app.use('*', async (c, next) => {
  c.set('repo', createVacationRepo(c.env.DB))
  await next()
})

app.get('/vacations', async (c) => {
  const vacations = await c.get('repo').list({ available: true })
  return c.html(<VacationsPage vacations={vacations} />)
})

换成 PostgreSQL

如果你要用 Postgres，Drizzle 的写法几乎一样，只是驱动和列类型不同： 

// schema：改用 pg-core
import { pgTable, text, boolean, doublePrecision, jsonb, timestamp } from 'drizzle-orm/pg-core'

export const vacations = pgTable('vacations', {
  sku: text('sku').primaryKey(),
  name: text('name').notNull(),
  price: doublePrecision('price').notNull(),
  tags: jsonb('tags').$type<string[]>().notNull().default([]),
  inSeason: boolean('in_season').notNull().default(false),
  createdAt: timestamp('created_at').notNull().defaultNow(),
})

// 驱动：边缘环境要用基于 HTTP 的驱动
import { drizzle } from 'drizzle-orm/neon-http'
import { neon } from '@neondatabase/serverless'

const sql = neon(c.env.DATABASE_URL)
const db = drizzle(sql)

// 查询代码完全一样
const rows = await db.select().from(vacations).where(eq(vacations.available, true))
⚠ 边缘环境不能用传统数据库驱动

pg、mysql2 这些经典驱动依赖 TCP socket 和连接池 —— Workers 上没有。而且边缘节点是短暂的，「连接池」这个概念本身就不成立。
解决方案是 HTTP 驱动：Neon、Supabase、PlanetScale 都提供了 把 SQL 包在 HTTP 请求里发送的驱动。延迟略高，但能用，而且不需要管连接数。

把会话存储换掉

第 9 章我们用了 MemoryStore，并说过它不能上生产。现在换成 KV：

import type { SessionStore, SessionData } from './session-store'

export function createKVSessionStore(kv: KVNamespace): SessionStore {
  const key = (id: string) => `sess:${id}`

  return {
    async get(id) {
      return await kv.get<SessionData>(key(id), 'json')
    },
    async set(id, data, ttlSeconds) {
      // KV 自带过期，不用自己清理
      await kv.put(key(id), JSON.stringify(data), { expirationTtl: ttlSeconds })
    },
    async destroy(id) {
      await kv.delete(key(id))
    },
  }
}

用 Redis 的版本同样简单：

import { Redis } from '@upstash/redis'

export function createRedisSessionStore(url: string, token: string): SessionStore {
  const redis = new Redis({ url, token })    // 基于 HTTP，边缘可用
  return {
    async get(id) { return await redis.get(`sess:${id}`) },
    async set(id, data, ttl) { await redis.set(`sess:${id}`, data, { ex: ttl }) },
    async destroy(id) { await redis.del(`sess:${id}`) },
  }
}

应用代码一个字都不用改 —— 这就是第 9 章定义 SessionStore 接口的回报。

ⓘ KV 是最终一致的

Cloudflare KV 为了全球快速读取，牺牲了强一致性：你写入后， 其他地区的节点可能要几秒才能读到新值。
这对会话来说通常没问题（同一个用户大概率打到同一个区域）。 但对「余额」「库存」这种数据绝对不行 —— 那些要用 D1、Durable Objects 或传统数据库。

三个性能陷阱

① N+1 查询

❌ 101 次查询
const vacations = await repo.list()   // 1 次

for (const v of vacations) {          // 100 次
  v.reviews = await repo.getReviews(v.sku)
}
✅ 2 次查询
const vacations = await repo.list()   // 1 次
const skus = vacations.map(v => v.sku)

// 一次取回所有评论
const all = await repo.getReviewsBySkus(skus)  // 1 次

const grouped = Map.groupBy(all, r => r.sku)
for (const v of vacations) {
  v.reviews = grouped.get(v.sku) ?? []
}

这是最常见的性能杀手，而且在测试数据少的时候完全看不出来。 本地 10 条数据时两种写法都是几毫秒，线上 1000 条时一个 20 ms 一个 4 秒。

② 缺索引

-- 没有索引：数据库要扫描整张表
SELECT * FROM vacations WHERE slug = 'hood-river-day-trip';

-- 加上索引后：直接定位
CREATE INDEX idx_vacations_slug ON vacations(slug);

规则：出现在 WHERE、JOIN、ORDER BY 里的列， 多半需要索引。（但注意：索引对 LIKE '%关键词%' 这类前缀未知的查询完全无效， 那需要另一套工具，见第 14 章。）但索引会拖慢写入并占空间，别无脑给所有列都加。 用 EXPLAIN QUERY PLAN（SQLite）或 EXPLAIN ANALYZE（Postgres）看真实执行计划。

③ 查了不需要的数据

// ❌ 列表页只需要名字和价格，却把长描述和 JSON 都拉回来了
const rows = await db.select().from(vacations)

// ✅ 只取需要的列
const rows = await db
  .select({ sku: vacations.sku, name: vacations.name, price: vacations.price })
  .from(vacations)
  .limit(20)                      // 而且一定要分页
⚠ 永远要分页

「查出所有记录」这种接口在数据只有 50 条时工作良好，在有 50 万条时会拖垮数据库和应用。 列表接口从第一天就加 limit。

种子数据

开发时需要一些初始数据。写个可重复执行的脚本：

const SEED = [
  {
    sku: 'HR199', slug: 'hood-river-day-trip', name: '胡德河一日游',
    description: '在哥伦比亚河上扬帆，然后在胡德河品尝精酿啤酒。',
    price: 99.95, tags: ['一日游', '帆船', '啤酒'],
    inSeason: true, available: true, maximumGuests: 16,
  },
  {
    sku: 'OC39', slug: 'oregon-coast-getaway', name: '俄勒冈海岸周末游',
    description: '享受海风和沿岸的古朴小镇。',
    price: 269.95, tags: ['周末游', '海岸'],
    inSeason: false, available: true, maximumGuests: 8,
  },
]

for (const v of SEED) {
  await db.insert(vacations)
    .values({ ...v, createdAt: new Date() })
    .onConflictDoUpdate({ target: vacations.sku, set: { name: v.name, price: v.price } })
}
console.log(`已写入 ${SEED.length} 条度假套餐`)
💡 种子脚本要能重复跑

用 onConflictDoUpdate（也叫 upsert）而不是 insert。 这样你随时可以重新执行它来重置或更新开发数据，不会因为主键冲突报错。

小结

  • 文件不要存本地磁盘，存对象存储；元信息存数据库。
  • 先定义数据访问接口，业务代码只认接口。测试写内存实现，生产写真实实现。
  • Drizzle 在一处定义表结构，同时得到 SQL 和 TypeScript 类型。
  • 表结构变更一律走迁移文件，不要手改生产库。
  • 边缘环境要用基于 HTTP 的数据库驱动。
  • 三个性能陷阱：N+1 查询、缺索引、查了不需要的数据。列表接口永远要分页。
  • 索引对「以 X 开头」有效，对「中间含 X」无效 —— 那是搜索问题，见下一章。

动手练习

  1. 用 Drizzle 定义 vacations 表，生成迁移并应用到本地 SQLite，跑通种子脚本。
  2. 把 /vacations 页面改成从数据库读数据。
  3. 写一个 InMemoryVacationRepo（数据存数组里），用它给页面处理函数写单元测试，全程不碰数据库。
  4. 往表里塞 1 万条假数据，对比「有 slug 索引」和「没有」时按 slug 查询的耗时。用 EXPLAIN QUERY PLAN 看看数据库到底做了什么。
  5. 把第 9 章的会话存储换成 KV 或 Redis 实现，确认重启服务器后登录状态还在。
