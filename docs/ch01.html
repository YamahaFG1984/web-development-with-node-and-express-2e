第 1 章

认识 Hono

在写第一行代码之前，先花十分钟搞清楚：Hono 到底是什么，它和 Express 有什么不同， 以及为什么「Web 标准」这四个字值得你重新学一个框架。

本章目标

  • 理解 JavaScript 服务端的两次转折：Node.js 与 Web 标准运行时
  • 说清楚 Hono 的四个特点：小、快、通用、类型安全
  • 分清「服务端渲染」和「单页应用」，知道 Hono 在两种架构里各扮演什么角色
  • 对 Hono 生态有个整体印象，知道后面会用到哪些包

JavaScript 的两次革命

第一次革命发生在 2009 年。Ryan Dahl 把 Chrome 的 V8 引擎从浏览器里抠出来，配上一套 I/O 库， 做成了 Node.js。JavaScript 第一次能在服务器上跑。前端工程师不用再切换到 PHP、 Ruby 或 Java 的思维模式，一门语言可以从数据库写到按钮点击。

在 Node.js 上，Express 迅速成为事实标准。它非常成功 —— 成功到十几年过去， 大量教程、公司代码库、面试题仍然默认你会 Express。本教程的原书就是讲 Express 的。

第二次革命发生得更安静。大约从 2018 年起，JavaScript 的运行环境不再只有「浏览器」和「Node.js」两种了：

Cloudflare Workers、Deno Deploy、Vercel Edge、Bun、AWS Lambda@Edge……这些新环境有个共同点： 它们不实现 Node.js 的 API，而是实现浏览器早就有的 fetch 标准。 于是 Express 在这些平台上要么跑不起来，要么要靠厚厚的兼容层。

★ 关键洞察

Express 把 Node.js 的 http.IncomingMessage 和 http.ServerResponse 包装了一层。 这两个对象是 Node.js 私有的，浏览器里没有，Workers 里也没有。 Hono 换了个基座：它包装的是 Request 和 Response —— 这两个对象所有现代 JavaScript 环境都有。

Hono 是什么

Hono（日语「炎」，读 ho-no）由 Yusuke Wada 在 2021 年创建，最初是为 Cloudflare Workers 写的小框架， 后来发展成一个跨运行时的通用 Web 框架。官网对它的描述是 「Fast, lightweight, built on Web Standards」。拆开看：

🧩

小（Small）

核心 hono/tiny 预设压缩后约 14 kB，零运行时依赖。在按冷启动计费的边缘平台上，体积直接等于钱。

⚡

快（Fast）

内置多个路由器实现，启动时根据你注册的路由自动挑最合适的那个。路由匹配基本不占时间。

🌐

通用（Universal）

基于 Web 标准，所以 Node、Bun、Deno、Workers、Lambda、Vercel 都能跑同一份业务代码。

🔢

类型安全

路由的路径参数、请求体、返回值都有类型。前端可以直接 import 后端的类型，接口改了当场编译报错。

最小的 Hono 应用长这样：

import { Hono } from 'hono'

const app = new Hono()

app.get('/', (c) => c.text('你好，云雀旅行！'))

export default app

注意最后一行：export default app。我们没有调用 listen()，也没有指定端口。 因为「怎么监听端口」是运行时的事，不是框架的事。在 Cloudflare Workers 上，平台会拿走这个默认导出； 在 Node.js 上，我们会在第 2 章加一行 serve()。业务代码本身不用改。

Express（Node.js 专属）
const express = require('express')
const app = express()

app.get('/', (req, res) => {
  res.send('你好')
})

app.listen(3000)
Hono（跨运行时）
import { Hono } from 'hono'
const app = new Hono()

app.get('/', (c) => {
  return c.text('你好')
})

export default app

两个差别值得现在就记住：

  1. Hono 只有一个上下文参数 c，不是 req, res 两个。请求信息在 c.req 里。
  2. Hono 的处理函数要 return 一个 Response，不是调用 res.send() 去「发送」。 这是纯函数式的思路：处理函数不产生副作用，它只是算出一个响应。

服务端渲染与单页应用

在决定用什么框架之前，先想清楚你要造哪种东西。今天的 Web 应用大致分两类：

很多人以为 SPA「赢了」，SSR 已经过时。实际情况更微妙：

  • 需要 SEO、首屏要快、内容为主的站点（博客、文档、营销页、电商列表），SSR 仍然是更好的选择。
  • 交互复杂、用户会长时间停留的应用（后台管理、编辑器、看板），SPA 更合适。
  • 大部分真实产品是混合的：营销页 SSR，登录后的控制台 SPA，两者共用一个 Hono 后端。

一份代码，处处运行

「跨运行时」听起来像营销话术，我们来看它具体意味着什么。下面这段业务代码，一个字都不用改：

import { Hono } from 'hono'

export const app = new Hono()

app.get('/health', (c) => c.json({ ok: true, at: new Date().toISOString() }))

变的只是「怎么把它接到平台上」这一层：

运行时入口写法典型场景
Node.js serve({ fetch: app.fetch, port: 3000 })
来自 @hono/node-server		 传统服务器、Docker、内网系统
Bun export default app 本地开发、追求启动速度
Deno Deno.serve(app.fetch) 脚本化部署、Deno Deploy
Cloudflare Workers export default app 全球边缘、按请求计费
AWS Lambda export const handler = handle(app) 已有 AWS 基建
Vercel / Netlify export default handle(app) 和前端一起部署
ⓘ 什么是「边缘」

传统部署把代码放在一台（或一组）机器上，比如新加坡的机房。北京用户的请求要跨海往返。 边缘计算把你的代码复制到全球几百个数据中心，用户请求就近落地。 代价是：这些边缘环境资源受限、没有文件系统、不能装原生扩展、执行时间有上限。 这正是它们不实现完整 Node.js API 的原因，也是 Hono 存在的原因。

Hono 的生态

Hono 核心刻意保持得很小。真正的能力来自三圈：

最里圈是 hono 包本身：Hono 类、路由器、Context。

中间圈仍然在 hono 这个 npm 包里，但通过子路径按需引入，比如 import { cors } from 'hono/cors'。 没用到的部分不会进你的构建产物。这是 Hono 保持「小」的秘诀 —— 它不是功能少，而是默认不加载。

最外圈是独立发布的包，命名空间是 @hono/。它们要么和特定运行时绑定（@hono/node-server）， 要么依赖第三方库（@hono/zod-validator 依赖 Zod）。

许可证

Hono 及其官方扩展都采用 MIT 许可证 —— 最宽松的开源许可证之一：你可以在闭源商业项目里随便用， 只要保留版权声明。

但你的项目会依赖几十上百个包，它们的许可证不一定都是 MIT。特别要注意 GPL： GPL 有「传染性」，用了 GPL 代码的项目通常也必须以 GPL 开源。商业项目里引入 GPL 依赖前一定要确认。 常见的宽松许可证还有 Apache 2.0（要求保留声明文件）和 BSD（类似 MIT）。

💡 实用建议

在项目里跑一次 npx license-checker --summary（或 npx licensee）， 看看依赖树里都有什么许可证。第一次跑的结果通常会让人有点惊讶。

小结

  • Node.js 让 JavaScript 上了服务器；Web 标准让 JavaScript 上了各种服务器。
  • Express 绑定 Node.js 的 req/res；Hono 绑定标准的 Request/Response，因此跨运行时。
  • Hono 处理函数接收一个上下文 c，返回一个 Response，而不是「发送」响应。
  • Hono 核心很小，能力靠 hono/xxx 子模块和 @hono/ 扩展按需加载。
  • SSR 和 SPA 各有适用场景，Hono 两种都能承担，还能混着来。

动手练习

  1. 打开 hono.dev，在首页的在线编辑器里把 c.text() 改成 c.json({ hello: 'world' })，观察响应头 Content-Type 的变化。
  2. 在浏览器控制台执行 new Request('https://a.com/x?q=1')，看看这个标准对象有哪些属性。这就是 Hono 里 c.req.raw 的东西。
  3. 想一想你手上或想做的某个项目：它更接近 SSR 还是 SPA？如果两者都有，边界应该划在哪里？
