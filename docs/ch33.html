上线

云雀旅行终于要见人了。这一章讲域名、DNS、部署平台的选择， 以及怎么把「发布」变成一件不需要勇气的日常操作。

本章目标

  • 看懂 DNS 记录，把域名指向你的应用
  • 根据项目特点选择部署平台
  • 把云雀旅行部署到 Cloudflare Workers 和传统服务器
  • 搭一条自动化的发布流水线
  • 准备好回滚方案

域名与 DNS

常见记录类型

类型作用例子
A域名 → IPv4 地址meadowlarktravel.com → 203.0.113.10
AAAA域名 → IPv6 地址meadowlarktravel.com → 2001:db8::1
CNAME域名 → 另一个域名（别名）www → meadowlark.pages.dev
MX这个域名的邮件由谁接收配邮箱服务时用
TXT任意文本。用于域名验证、SPF、DKIM第 11 章的发信配置
NS这个域名由哪些 DNS 服务器负责换 DNS 服务商时改这个
ⓘ TTL 与「DNS 生效要多久」

每条记录有个 TTL（生存时间），告诉各级缓存「这个结果可以存多久」。 默认常见是 3600 秒（1 小时）。
迁移前的技巧：提前一两天把 TTL 调到 300 秒， 这样切换时最多 5 分钟就全网生效；切换完成稳定后再调回去。

⚠ 根域名不能用 CNAME

DNS 规范不允许根域名（meadowlarktravel.com，也叫 apex）配 CNAME。 但很多平台只给你一个域名而不是 IP。
解决办法：用支持 CNAME 展平（也叫 ALIAS / ANAME）的 DNS 服务商 —— Cloudflare、Route53 等都支持。它们在解析时自动把 CNAME 转成 A 记录返回。

选择部署平台

平台适合注意
Cloudflare Workers 全球分发、按量计费、想要极低冷启动。配套有 D1、KV、R2、队列 受限运行时，没有文件系统，单请求有 CPU 时间上限
Deno Deploy Deno 项目，配置极少 生态比 Node 小
Vercel / Netlify 前端和 API 一起部署，预览环境体验好 长任务和 WebSocket 支持有限
Fly.io / Railway / Render 要完整的 Node 环境、要跑后台任务、要连传统数据库 要自己管实例数量和扩缩容
自己的 VPS + Docker 有合规要求、要完全控制、成本敏感 系统更新、证书、监控、备份全都归你
★ 怎么选

先问一个问题：「我需要文件系统、长连接、或者跑几分钟的后台任务吗？」
不需要 → 边缘平台（Workers / Deno Deploy / Vercel），最省心。
需要 → 容器平台（Fly.io / Railway）或自己的服务器。

因为 Hono 基于 Web 标准，选错了也不是灾难 —— 换平台主要是改入口文件和部署配置， 业务代码基本不动。

npx wrangler d1 migrations apply meadowlark --remote

# 部署

npx wrangler deploy --env staging      # 预发布

# 看线上日志
npx wrangler tail

部署到 Node 服务器

import { serve } from '@hono/node-server'
import { app } from './app'

const port = Number(process.env.PORT) || 3000

const server = serve({ fetch: app.fetch, port }, (info) => {
  console.log(`服务器已启动：http://localhost:${info.port}`)
})

// 优雅关闭：让手头的请求处理完再退出
for (const signal of ['SIGTERM', 'SIGINT'] as const) {
  process.on(signal, () => {
    console.log(`收到 ${signal}，正在关闭`)
    server.close(() => process.exit(0))
    setTimeout(() => process.exit(1), 10_000).unref()
  })
}

FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY --from=build /app/dist ./dist
COPY public ./public
USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s \
  CMD node -e "fetch('http://localhost:3000/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
CMD ["node", "dist/server.js"]

自动化发布

name: Deploy

on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm test

  deploy:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run build

      - name: 应用数据库迁移
        run: npx wrangler d1 migrations apply meadowlark --remote
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}

      - name: 部署
        run: npx wrangler deploy
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}

      - name: 冒烟测试
        run: |
          sleep 10
          curl -sf https://meadowlarktravel.com/health || exit 1
⚠ 数据库迁移必须向后兼容

部署过程中，会有一小段时间是新旧两个版本同时在跑。 如果迁移直接删掉了一个列，旧版本代码立刻报错。
安全的做法是分两次发布：
① 先加新列，新旧代码都能跑 → 部署新代码 → 确认稳定
② 下次发布再删旧列
麻烦，但这是零停机发布的必要代价。

上线检查清单

★ 第一次上线前逐项确认
  • ☐ 域名解析正确，www 和根域名都能访问（且互相跳转统一）
  • ☐ HTTPS 生效，HTTP 自动跳转（第 21 章）
  • ☐ 所有环境变量和密钥都在生产环境配好了
  • ☐ 数据库迁移已应用，种子数据已就位
  • ☐ NODE_ENV=production
  • ☐ 404 和 500 页面是自定义的，不泄露内部信息
  • ☐ /health 端点正常，已接入外部可用性监控（第 12 章）
  • ☐ 错误上报已接通，故意触发一次确认能收到
  • ☐ 有 robots.txt 和 sitemap.xml
  • ☐ favicon、Open Graph 标签（分享到社交平台时的预览图）
  • ☐ 数据库有自动备份，并且你恢复演练过一次
  • ☐ 知道怎么回滚，而且演练过
⚠ 没验证过的备份等于没有备份

「我们有每日备份」这句话在真正需要恢复时经常变成 「备份文件是空的 / 格式不对 / 三个月前就停了没人发现」。
现在就做一次恢复演练：把备份还原到一个临时数据库，确认数据完整。

回滚

# Cloudflare Workers：回到上一个版本
npx wrangler rollback

# Docker：换回上一个镜像标签
docker compose up -d --no-deps app:v1.4.2

# Git：撤销那次合并（保留历史，比 reset 安全）
git revert -m 1 <merge-commit>
git push
★ 出问题时先回滚，再排查

线上出故障时，本能反应是「让我看看哪里错了」。
正确的顺序是：先回滚，恢复服务，然后再慢慢查。 用户不关心原因，只关心网站能不能用。而且回滚之后你可以在没有压力的情况下分析。
前提是回滚必须很快很可靠 —— 所以要提前演练。

小结

  • DNS 把域名映射到服务器；迁移前先把 TTL 调小。
  • 需不需要文件系统和长任务，决定了你该用边缘平台还是容器平台。
  • Hono 换平台只改入口文件，业务代码不动。
  • 发布要自动化：检查 → 迁移 → 部署 → 冒烟测试。
  • 数据库迁移必须向后兼容，删列要等下一次发布。
  • 回滚和备份恢复都要演练过才算数。出故障时先回滚再排查。

动手练习

  1. 用 dig meadowlarktravel.com（或 nslookup）查一个你熟悉的网站，看看它的 A 记录、CNAME 和 TTL。
  2. 把云雀旅行部署到 Cloudflare Workers 的免费额度上，绑定一个你自己的域名（或者用平台提供的 *.workers.dev）。
  3. 配一条 GitHub Actions 流水线：推送到 main 就自动跑测试并部署。故意让一个测试失败，确认它没有部署。
  4. 做一次回滚演练：部署一个明显有问题的版本，然后用 wrangler rollback 恢复，计时看要多久。
  5. 对照上线清单，把你项目里还没做的项列出来。
