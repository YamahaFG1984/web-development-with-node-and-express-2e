第 17 章

静态资源

一个典型页面里，HTML 只占几十 KB，剩下的几 MB 全是图片、CSS 和 JavaScript。 用户感受到的「快不快」，主要由这部分决定。这一章讲怎么把它们又快又省地送出去。

本章目标

  • 分清静态资源和动态内容，知道各自的优化手段
  • 在不同运行时上正确配置 serveStatic
  • 理解 CDN 的工作方式和它为什么能大幅提速
  • 掌握缓存三件套：Cache-Control、ETag、内容指纹
  • 解决「改了文件但用户看到的还是旧版」这个经典问题

什么算静态资源

类型例子特点
样式与脚本main.css、app.js构建产物，内容变了文件名就该变
图片logo、照片、图标体积最大的一块，优化收益最高
字体.woff2阻塞文字渲染，要小心处理
其他favicon.ico、robots.txt、下载文件基本不变
★ 一条分界线

静态资源：给定 URL，返回的字节永远一样，和是谁在请求无关。可以放 CDN，可以缓存一年。
动态内容：需要执行代码才能算出来，可能因用户而异。不能盲目缓存。
用这条线判断：「如果我把这个响应存下来发给另一个用户，会出问题吗？」

性能的三个维度

用 Hono 提供静态资源

// Node.js
import { serveStatic } from '@hono/node-server/serve-static'
app.use('/*', serveStatic({ root: './public' }))

// Bun
import { serveStatic } from 'hono/bun'
app.use('/*', serveStatic({ root: './public' }))

// Deno
import { serveStatic } from 'hono/deno'
app.use('/*', serveStatic({ root: './public' }))

常用选项

app.use(
  '/static/*',
  serveStatic({
    root: './public',
    // 去掉 URL 前缀再去找文件：/static/img/a.png → ./public/img/a.png
    rewriteRequestPath: (path) => path.replace(/^\/static/, ''),

    // 在响应上补充头
    onFound: (path, c) => {
      c.header('Cache-Control', 'public, max-age=31536000, immutable')
    },

    // 文件不存在时
    onNotFound: (path, c) => {
      console.warn(`静态文件缺失：${path}`)
    },
  })
)

Cloudflare Workers 上不一样

Workers 上不用 serveStatic —— 静态文件由平台直接托管， 根本不会进入你的代码，因此更快也更便宜： 

name = "meadowlark"
main = "src/index.ts"
compatibility_date = "2025-01-01"

[assets]
directory = "./public"
binding = "ASSETS"
# 找不到对应文件时，才交给你的 Worker 代码处理
not_found_handling = "single-page-application"
ⓘ 这是边缘架构的一个优势

传统服务器上，每个图片请求都要唤醒你的应用进程去读文件。 在 Workers 上，静态资源在边缘节点直接命中，你的代码只在真正需要动态逻辑时才执行。 省下的不只是延迟，还有账单（按请求计费的平台通常不对静态资源计费）。

CDN

💡 部署在 Workers 上的话，你已经在用 CDN 了

Cloudflare Workers、Vercel、Netlify 这些平台本身就跑在 CDN 网络上。 你不需要额外配置 —— 静态资源和你的代码都已经分发到全球边缘节点了。 只有部署在单台服务器上时，才需要单独接一个 CDN。

缓存

浏览器缓存有两种模式，理解这两者的区别是本章的核心：

Cache-Control 速查

写法含义用在哪
public, max-age=31536000, immutable缓存一年，且永不重新验证带内容指纹的 JS/CSS
public, max-age=3600缓存一小时图片等不常变的资源
no-cache可以缓存，但每次都要问服务器「变了吗」HTML 页面
no-store完全不缓存，一个字节都不留含个人信息的页面、API 响应
private, max-age=0只允许浏览器缓存，CDN 不许缓存登录后的个性化页面
⚠ no-cache 不是「不缓存」

这是命名最坑的一对：
no-cache = 「可以存，但用之前必须问我一下」（协商缓存）
no-store = 「一个字节都别存」（真正的不缓存）
想让敏感页面不被缓存，用 no-store。

ETag

import { etag } from 'hono/etag'

app.use('/*', etag())

这个中间件会根据响应内容算一个哈希放进 ETag 头。 浏览器下次请求时带上 If-None-Match，内容没变就返回 304。 

# 第一次
GET /logo.png
← 200 OK
  ETag: "a1b2c3d4"
  Content-Length: 48213

# 第二次
GET /logo.png
  If-None-Match: "a1b2c3d4"
← 304 Not Modified          ← 没有响应体，只有几十字节的头

Cache API 中间件

在支持 Cache API 的运行时（Workers、Deno）上，可以把动态生成的响应也缓存起来：

import { cache } from 'hono/cache'

app.get(
  '/api/v1/vacations',
  cache({
    cacheName: 'meadowlark-v1',
    cacheControl: 'public, max-age=300',    // 缓存 5 分钟
    // 按语言分别缓存，避免中文用户拿到英文版
    vary: ['Accept-Language'],
  }),
  listVacations
)
⚠ 千万别缓存带个人信息的响应

如果 /api/me 被 CDN 缓存了，第二个用户就会拿到第一个用户的资料。 这是真实发生过的重大事故。
规则：任何依赖 Cookie、Authorization 头或会话的响应， 必须设 Cache-Control: private, no-store。

改了文件用户却看到旧版

这是缓存带来的经典问题，也是有标准解法的问题。

❌ 固定文件名 + 长缓存
<script src="/js/app.js"></script>

Cache-Control: max-age=31536000
你改了 app.js 并发布，但用户浏览器里缓存的旧版还有 364 天才过期。 新 HTML 配旧 JS，页面直接坏掉。
✅ 内容指纹 + 长缓存
<script src="/js/app-a1b2c3.js"></script>

Cache-Control: max-age=31536000, immutable
内容一变，哈希就变，文件名就变，URL 就变 —— 浏览器认为这是个全新的资源， 必然重新下载。
★ 记住这个组合

HTML 用 no-cache（很小，每次验证一下）， 带指纹的资源用 max-age=31536000, immutable（很大，永久缓存）。
这样发布新版本时，用户只需重新下载几 KB 的 HTML， HTML 里的新文件名会自动触发新资源的下载，旧资源静静躺在缓存里等着过期。

Vite 默认就是这么做的，你不用手动改文件名：

$ npm run build

dist/index.html                    0.46 kB
dist/assets/index-DiwrgTda.css     1.23 kB
dist/assets/index-C2vZs9Xy.js    143.61 kB

// 配合上面的构建产物设置缓存头
app.use('/assets/*', serveStatic({
  root: './public',
  onFound: (_path, c) => {
    c.header('Cache-Control', 'public, max-age=31536000, immutable')
  },
}))

app.use('/*', serveStatic({
  root: './public',
  onFound: (_path, c) => {
    c.header('Cache-Control', 'no-cache')
  },
}))

图片

图片通常占页面体积的六到八成，优化收益最高：

🖼

选对格式

照片用 AVIF / WebP，比 JPEG 小 30–50%。图标和插图用 SVG（矢量、可缩放、体积小）。

📏

不要超尺寸

显示宽度 400px 的位置，不要放 4000px 的原图。用 srcset 按屏幕提供不同尺寸。

⏳

懒加载

首屏之外的图片加 loading="lazy"，一个属性的事。

📏

写上宽高

给 <img> 写 width 和 height，避免图片加载后页面跳动。

<picture>
  <source srcset="/img/hood-river.avif" type="image/avif">
  <source srcset="/img/hood-river.webp" type="image/webp">
  <img
    src="/img/hood-river.jpg"
    alt="胡德河上的帆船"
    width="800" height="600"
    loading="lazy"
    decoding="async"
  >
</picture>

小结

  • 静态资源 = 「同一个 URL 永远返回同样字节」，这决定了它能被缓存和分发。
  • 优化顺序：减体积 → 上 CDN → 调缓存。最快的请求是不发生的请求。
  • Workers 上静态资源由平台托管，不经过你的代码。
  • no-cache 是「用前验证」，no-store 才是「不缓存」。
  • 黄金组合：HTML 用 no-cache，带指纹的资源用 immutable 长缓存。
  • 永远不要缓存含个人信息的响应。

动手练习

  1. 用 curl -I http://localhost:3000/img/logo.png 看看当前的响应头。有 Cache-Control 吗？有 ETag 吗？
  2. 接上 etag() 中间件，用 curl -H 'If-None-Match: "..."' 验证第二次请求返回 304。
  3. 给 /assets/* 配上一年缓存，给其他静态文件配 no-cache。在浏览器 Network 面板里刷新页面，观察哪些资源显示「from disk cache」。
  4. 找一张页面上最大的图片，转成 WebP，对比体积。然后用 <picture> 做格式回退。
  5. 想一想你的应用里有哪些响应绝对不能被 CDN 缓存。给它们加上 private, no-store。
