安全

安全不是上线前加的一个功能，而是贯穿每一章的一条线。 这一章把散落在前面的安全知识收拢起来，再补上认证、授权和几种最常见的攻击。

本章目标

  • 配好 HTTPS，理解反向代理背后的协议判断
  • 一行接上安全响应头，理解 CSP 在防什么
  • 搞懂 CSRF 的原理和两道防线
  • 正确存储密码，实现会话认证和 JWT 认证

HTTPS

没有 HTTPS，所有内容都是明文传输：同一个 WiFi 下的人能看到你的密码， 运营商能往页面里插广告，中间人能篡改你下载的 JavaScript。

今天没有理由不用 HTTPS：证书免费（Let's Encrypt），主流平台自动配置， 而且浏览器把很多能力（地理位置、摄像头、Service Worker）设成了 HTTPS 独占。

部署方式证书怎么来
Cloudflare Workers / Vercel / Netlify自动，什么都不用做
自己的服务器 + Nginx/CaddyCaddy 全自动；Nginx 配 certbot 自动续期
云厂商负载均衡在控制台申请托管证书
本地开发mkcert 生成本地信任的证书，或者直接用 http

代理背后的坑

function isSecure(c: Context) {
  const proto = c.req.header('x-forwarded-proto')
  if (proto) return proto.split(',')[0].trim() === 'https'
  return new URL(c.req.url).protocol === 'https:'
}

// 强制跳转 HTTPS
app.use('*', async (c, next) => {
  if (isProduction && !isSecure(c)) {
    const url = new URL(c.req.url)
    url.protocol = 'https:'
    return c.redirect(url.toString(), 301)
  }
  await next()
})
⚠ 只信任你自己的代理发来的头

X-Forwarded-Proto 是个普通请求头，任何人都能伪造。 只有当你确定请求一定经过自己的代理（且代理会覆盖这个头）时才能信任它。 如果应用可以被直接访问，攻击者就能伪造这个头绕过你的 HTTPS 检查。

安全响应头

import { secureHeaders } from 'hono/secure-headers'

app.use('*', secureHeaders())

这一行会加上一整组头。逐个看看它们在防什么：

响应头防的是
Strict-Transport-Security告诉浏览器「以后只用 HTTPS 访问我」，防降级攻击
X-Content-Type-Options: nosniff禁止浏览器猜测内容类型。防止上传的「图片」被当成脚本执行
X-Frame-Options: SAMEORIGIN禁止别人把你的页面嵌进 iframe，防点击劫持
Referrer-Policy控制跳转时泄露多少来源 URL 信息
Content-Security-Policy最强的一道：限定只能从哪些来源加载脚本、样式、图片

CSP：XSS 的最后一道防线

app.use('*', secureHeaders({
  contentSecurityPolicy: {
    defaultSrc: ["'self'"],
    scriptSrc: ["'self'"],                          // 只允许自己域名下的脚本
    styleSrc: ["'self'", "'unsafe-inline'"],
    imgSrc: ["'self'", 'data:', 'https://cdn.meadowlarktravel.com'],
    connectSrc: ["'self'", 'https://api.meadowlarktravel.com'],
    frameAncestors: ["'none'"],                     // 谁都不能嵌我
    objectSrc: ["'none'"],
    upgradeInsecureRequests: [],
  },
}))
★ CSP 为什么重要

假设你的模板某处漏掉了转义，攻击者成功注入了 <script src="https://evil.com/steal.js">。
有 CSP 的话，浏览器会拒绝加载这个脚本，因为 evil.com 不在 scriptSrc 白名单里。
CSP 是「假设我的其他防护已经失败了」之后的兜底。纵深防御的典范。

💡 先用报告模式

CSP 配紧了很容易把自己的功能搞坏（第三方统计脚本、内联样式）。 先用 Content-Security-Policy-Report-Only 上线， 观察浏览器控制台报告了哪些违规，调整好再切成强制模式。

CSRF

两道防线

// 第一道：SameSite Cookie（第 9 章讲过）
setCookie(c, 'sid', id, {
  httpOnly: true,
  secure: true,
  sameSite: 'Lax',    // 跨站 POST 不会带上这个 Cookie
})

// 第二道：Hono 的 CSRF 中间件
import { csrf } from 'hono/csrf'

app.use('*', csrf({ origin: 'https://meadowlarktravel.com' }))

csrf() 中间件检查请求的 Origin 头是否属于你的站点， 不匹配就拒绝。对于表单提交场景，这已经足够。

ⓘ 用令牌的做法

更传统的方案是「双重提交令牌」：服务器给每个表单生成一个随机 token， 同时放在隐藏字段和 Cookie 里，提交时比对两者是否一致。 攻击者的页面读不到你的 Cookie，所以造不出正确的隐藏字段。
今天 SameSite=Lax + Origin 校验对绝大多数应用已经够用。 需要更严格时（比如支付），再叠加令牌。

💡 纯 API 通常不需要 CSRF 防护

CSRF 依赖「浏览器自动带 Cookie」。如果你的 API 用 Authorization: Bearer 头做认证，浏览器不会自动带上这个头， 攻击者也造不出来 —— 天然免疫 CSRF。
用 Cookie 认证就要防 CSRF，用 Bearer 令牌就不用。

密码

⚠ 关于密码存储的三条铁律
  1. 永远不要存明文。数据库一旦泄露，所有用户在其他网站的账号也跟着完蛋 （因为很多人复用密码）。
  2. 不要用 MD5 或 SHA-256。它们设计目标是「快」， 现代显卡每秒能试几十亿次，一个 8 位密码几分钟就能爆破出来。
  3. 用专门的密码哈希算法：Argon2id（首选）、bcrypt、scrypt。 它们故意设计得慢且消耗内存，让爆破成本高到不可行。
// Node.js / Bun：用 Argon2
import { hash, verify } from '@node-rs/argon2'

const passwordHash = await hash(plainPassword)      // 注册时
const ok = await verify(passwordHash, plainPassword) // 登录时

// 边缘运行时（Workers）：原生模块用不了，用 Web Crypto 的 PBKDF2
async function hashPassword(password: string): Promise<string> {
  const salt = crypto.getRandomValues(new Uint8Array(16))
  const key = await crypto.subtle.importKey(
    'raw', new TextEncoder().encode(password), 'PBKDF2', false, ['deriveBits']
  )
  const bits = await crypto.subtle.deriveBits(
    { name: 'PBKDF2', salt, iterations: 210_000, hash: 'SHA-256' },
    key, 256
  )
  return `pbkdf2$210000$${b64(salt)}$${b64(new Uint8Array(bits))}`
}
ⓘ 最好的密码方案是没有密码

自己实现密码认证意味着你要负责：安全存储、重置流程、防撞库、防暴力破解、 可能还有双因素认证。
能用第三方登录（Google / GitHub / 微信）就用 —— 见下文。 或者用「魔法链接」：用户输入邮箱，你发一封带一次性链接的邮件，点击即登录。 没有密码，就没有密码泄露。

认证与授权

认证 Authentication
你是谁？
验证身份。用户名密码、第三方登录、令牌。
失败返回 401。
授权 Authorization
你能做什么？
验证权限。角色、所有权、订阅等级。
失败返回 403。

方案一：会话认证（适合网页）

app.post('/login', zValidator('form', loginSchema), async (c) => {
  const { email, password } = c.req.valid('form')

  const user = await db.getUserByEmail(email)

  // 注意：用户不存在和密码错误要返回同样的信息和同样的耗时
  // 否则攻击者可以用它来枚举哪些邮箱注册过
  if (!user || !(await verify(user.passwordHash, password))) {
    return c.html(<LoginPage error="邮箱或密码不正确" />, 401)
  }

  const session = c.get('session')
  session.userId = user.id
  session.createdAt = Date.now()

  return c.redirect('/account', 303)
})

export const loadUser = createMiddleware<{ Variables: { user?: User } }>(
  async (c, next) => {
    const userId = c.get('session')?.userId
    if (userId) {
      const user = await db.getUserById(String(userId))
      if (user) c.set('user', user)
    }
    await next()
  }
)

export const requireLogin = createMiddleware(async (c, next) => {
  if (!c.get('user')) {
    // 记住原本想去的地方，登录后跳回来
    c.get('session').returnTo = c.req.path
    return c.redirect('/login', 303)
  }
  await next()
})

export function requireRole(...roles: string[]) {
  return createMiddleware(async (c, next) => {
    const user = c.get('user')
    if (!user) return c.redirect('/login', 303)
    if (!roles.includes(user.role)) {
      return c.html(<ForbiddenPage />, 403)
    }
    await next()
  })
}

app.use('*', loadUser)
app.use('/account/*', requireLogin)
app.use('/admin/*', requireRole('admin', 'staff'))

方案二：JWT（适合 API）

import { jwt, sign } from 'hono/jwt'

// 签发
app.post('/api/v1/auth/login', zValidator('json', loginSchema), async (c) => {
  const { email, password } = c.req.valid('json')
  const user = await db.getUserByEmail(email)

  if (!user || !(await verify(user.passwordHash, password))) {
    throw new HTTPException(401, { message: '邮箱或密码不正确' })
  }

  const token = await sign(
    {
      sub: user.id,
      role: user.role,
      exp: Math.floor(Date.now() / 1000) + 60 * 15,   // 15 分钟
    },
    c.env.JWT_SECRET
  )

  return c.json({ token })
})

// 验证：中间件会自动检查 Authorization: Bearer xxx
app.use('/api/v1/protected/*', (c, next) =>
  jwt({ secret: c.env.JWT_SECRET })(c, next)
)

app.get('/api/v1/protected/me', (c) => {
  const payload = c.get('jwtPayload')
  return c.json({ userId: payload.sub, role: payload.role })
})
⚠ JWT 的载荷是公开的

那三段只是 Base64 编码，不是加密。任何人复制粘贴到 jwt.io 就能看到全部内容。
不要往载荷里放密码、身份证号、任何敏感信息。 签名保证的是「这些内容没被改过」，不是「别人看不到」。

第三方登录

npm install @hono/oauth-providers

import { githubAuth } from '@hono/oauth-providers/github'

app.use('/auth/github', (c, next) =>
  githubAuth({
    client_id: c.env.GITHUB_CLIENT_ID,
    client_secret: c.env.GITHUB_CLIENT_SECRET,
    scope: ['read:user', 'user:email'],
  })(c, next)
)

app.get('/auth/github', async (c) => {
  const profile = c.get('user-github')
  if (!profile) throw new HTTPException(401, { message: '授权失败' })

  const authId = `github:${profile.id}`

  // 已有账号就用，没有就建一个
  let user = await db.getUserByAuthId(authId)
  if (!user) {
    user = await db.createUser({
      authId,
      name: profile.name ?? profile.login,
      email: profile.email ?? null,
      role: 'customer',
    })
  }

  // 从这里开始，走的是我们自己的会话逻辑
  c.get('session').userId = user.id
  return c.redirect(c.get('session').returnTo ?? '/account', 303)
})
★ 数据库设计要点

用 authId 这种带前缀的字段（github:12345、google:67890） 而不是把 GitHub ID 直接当主键。这样：
① 一个用户可以绑定多个登录方式；② 将来加新的登录渠道不用改表结构；
③ 不同平台的 ID 撞号了也不会出问题。

限流

没有限流的登录接口，等于邀请别人来撞库：

import { createMiddleware } from 'hono/factory'

export function rateLimit(opts: { limit: number; windowSec: number; kv: KVNamespace }) {
  return createMiddleware(async (c, next) => {
    const ip =
      c.req.header('cf-connecting-ip') ??
      c.req.header('x-forwarded-for')?.split(',')[0].trim() ??
      'unknown'

    const key = `rl:${c.req.path}:${ip}`
    const count = Number((await opts.kv.get(key)) ?? 0)

    if (count >= opts.limit) {
      c.header('Retry-After', String(opts.windowSec))
      throw new HTTPException(429, { message: '请求太频繁，请稍后再试' })
    }

    await opts.kv.put(key, String(count + 1), { expirationTtl: opts.windowSec })
    await next()
  })
}

// 登录接口：一分钟最多 5 次
app.use('/login', (c, next) =>
  rateLimit({ limit: 5, windowSec: 60, kv: c.env.RATE_LIMIT })(c, next)
)

小结

  • HTTPS 是底线；在代理后面要用 X-Forwarded-Proto 判断，且只信任自己的代理。
  • secureHeaders() 一行加上一组防护，CSP 是 XSS 的最后一道防线。
  • CSRF 靠 SameSite + Origin 校验；Bearer 令牌认证天然免疫。
  • 密码用专门的慢哈希算法；能不自己管密码就不管。
  • 认证问「你是谁」（401），授权问「你能做什么」（403）。
  • 会话认证适合网页，JWT 适合 API；JWT 载荷是公开的，有效期要短。
  • 登录类接口必须限流。

动手练习

  1. 接上 secureHeaders()，用 curl -I 看看多了哪些响应头。然后配一个 CSP，故意加载一个外部脚本，观察浏览器控制台的拦截报告。
  2. 实现完整的注册和登录流程，用 Argon2 或 PBKDF2 存密码。确认数据库里存的是哈希而不是明文。
  3. 实现 requireLogin 和 requireRole，保护 /account 和 /admin。用未登录状态访问，确认跳转到登录页并且登录后能跳回原页面。
  4. 做一个 JWT 版本的登录接口，用 curl 拿到令牌后访问受保护接口。把令牌粘到 jwt.io 上看看里面有什么。
  5. 给登录接口加限流，用循环发 10 次请求，确认第 6 次开始返回 429。
  6. 对照上面的清单，逐项检查你现在的项目。
