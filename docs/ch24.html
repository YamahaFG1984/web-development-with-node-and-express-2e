第 24 章

缓存架构

第 19 章讲的是 HTTP 缓存 —— 浏览器和 CDN 那一层。这一章讲应用内部的缓存： 查询结果、计算结果、外部调用结果。它能把响应时间降一个数量级， 也能制造出一整类只在高并发下才出现的故障。

本章目标

  • 看清缓存的四个层次，知道每层该放什么
  • 掌握 cache-aside 模式和它的失效顺序问题
  • 识别并解决三大经典故障：穿透、击穿、雪崩
  • 设计不会串数据的缓存键
  • 知道什么不该缓存，以及怎么监控缓存是否真的有用

缓存的四层

⚠ 先测量，再加缓存

「这里有点慢，加个缓存吧」是最常见的错误决策顺序。加缓存之前先回答：

  • 慢的是哪一段？（第 28 章的 trace 会告诉你）
  • 是不是缺个索引就解决了？（第 13 章）
  • 是不是 N+1 查询？（第 13 章）

缓存是用「数据可能是旧的」换性能。如果加个索引就能解决， 那你白白引入了一整类一致性问题。

Cache-Aside 模式

最常用的模式，逻辑很简单：先查缓存，没有就查库并回填。

async function getVacation(sku: string, env: Bindings): Promise<Vacation | null> {
  const key = `vacation:v1:${sku}`

  // 1. 查缓存
  const cached = await env.CACHE.get<Vacation>(key, 'json')
  if (cached) return cached

  // 2. 未命中，查数据库
  const vacation = await db.findBySku(sku)
  if (!vacation) return null

  // 3. 回填，设置过期时间
  await env.CACHE.put(key, JSON.stringify(vacation), { expirationTtl: 300 })

  return vacation
}

写入时怎么办：删除还是更新？

export async function updateVacation(sku: string, patch: Partial<Vacation>, env: Bindings) {
  // ① 先写库（这是唯一的真相来源）
  const updated = await db.update(sku, patch)

  // ② 再删缓存 —— 删除而不是更新
  await env.CACHE.delete(`vacation:v1:${sku}`)

  // ③ 关联缓存也要清（最容易漏的一步）
  await env.CACHE.delete(`vacation-list:v1:available`)

  return updated
}
★ 为什么是「删除」而不是「更新」
  • 删除是幂等的，重复执行没有副作用；写入不是（可能写回旧值）。
  • 删除让下次读取自然拉到最新值，不需要你在写入路径上重新组装完整对象。
  • 如果这条数据之后没人读，你就白算了一次 —— 删除是惰性的，更省。
⚠ 关联缓存是最容易漏的

改了一个度假套餐，你记得删 vacation:HR199。
但 vacation-list:available、search:海岸、 homepage:featured 里也有这条数据的副本 —— 它们全都过期了，而你不知道。
这就是下面「版本化键」要解决的问题。

三大经典故障

穿透：缓存空结果

const NOT_FOUND = '__nf__'

async function getVacation(sku: string, env: Bindings) {
  const key = `vacation:v1:${sku}`
  const cached = await env.CACHE.get(key)

  if (cached === NOT_FOUND) return null        // 命中「确实不存在」
  if (cached) return JSON.parse(cached)

  const vacation = await db.findBySku(sku)

  if (!vacation) {
    // 关键：把「不存在」也缓存起来，但 TTL 要短
    // 太长的话，这条数据真被创建出来时用户要等很久才能看到
    await env.CACHE.put(key, NOT_FOUND, { expirationTtl: 60 })
    return null
  }

  await env.CACHE.put(key, JSON.stringify(vacation), { expirationTtl: 300 })
  return vacation
}

击穿：单飞

/**
 * 同一时刻对同一个 key 只执行一次 fn，其余调用共享同一个 Promise。
 * 第 20 章那个 withCache 里已经用过这个思路，这里把它独立出来。
 */
export function createSingleflight<T>() {
  const inflight = new Map<string, Promise<T>>()

  return function run(key: string, fn: () => Promise<T>): Promise<T> {
    const existing = inflight.get(key)
    if (existing) return existing              // 已经有人在查了，跟着他

    const p = fn().finally(() => inflight.delete(key))
    inflight.set(key, p)
    return p
  }
}

const sf = createSingleflight<Vacation | null>()

async function getVacation(sku: string, env: Bindings) {
  const key = `vacation:v1:${sku}`
  const cached = await env.CACHE.get<Vacation>(key, 'json')
  if (cached) return cached

  // 1000 个并发请求走到这里，只有 1 个真的去查库
  return sf(key, async () => {
    const v = await db.findBySku(sku)
    if (v) await env.CACHE.put(key, JSON.stringify(v), { expirationTtl: 300 })
    return v
  })
}
⚠ 单飞只在单个进程内有效

跑 10 个实例的话，最坏情况是 10 个请求同时打到数据库 —— 比 1000 个好得多， 但不是 1 个。
要做到全局单飞，需要分布式锁 —— 但第 23 章说过，分布式锁的复杂度往往不值得。 通常「把并发从 1000 降到 10」已经足够了。

雪崩：TTL 加抖动

/** 在基准 TTL 上下浮动 20%，避免大批 key 在同一秒集体过期 */
function jitteredTtl(baseSeconds: number): number {
  const delta = baseSeconds * 0.2
  return Math.round(baseSeconds - delta + Math.random() * delta * 2)
}

await env.CACHE.put(key, value, { expirationTtl: jitteredTtl(300) })
★ 抖动这个手法你已经见过三次了

第 20 章的重试退避、第 27 章的 WebSocket 重连、这里的 TTL —— 全都要加随机抖动。
原理是同一个：任何「大量客户端在同一时刻做同一件事」的设计，都会制造尖峰。 把时刻打散，尖峰就变成了平缓的曲线。

缓存挂了要能活

async function getFromCache<T>(env: Bindings, key: string): Promise<T | null> {
  try {
    return await env.CACHE.get<T>(key, 'json')
  } catch (err) {
    // 缓存不可用不该让请求失败 —— 降级成直接查库
    log('warn', 'cache_unavailable', { key, error: String(err) })
    return null
  }
}
⚠ 但要小心「降级」变成「压垮」

缓存挂掉后所有流量直击数据库，很可能把数据库也拖死 —— 故障扩散了。
真正稳妥的做法是降级 + 限流：缓存不可用时， 对数据库的并发查询数设一个上限，超出的请求快速失败或返回降级内容， 保住数据库，牺牲一部分请求。这是第 20 章熔断思路的延伸。

缓存键设计

要素为什么例子
命名空间区分不同类型的数据，方便按前缀批量清理vacation:
版本号数据结构变了时，改版本号即可让所有旧缓存自然失效v2:
租户标识多租户下漏掉它就是跨租户数据泄露（第 21 章）t:{tenantId}:
唯一标识具体是哪条数据HR199
影响结果的参数语言、货币、权限等级都会改变返回内容:zh:CNY
// ❌ 危险：不同租户、不同语言的用户会拿到彼此的数据
const key = `vacation:${sku}`

// ✅
const key = `t:${tenantId}:vacation:v2:${sku}:${locale}:${currency}`
★ 版本号解决了「关联缓存漏删」的问题

改了数据结构（比如给 Vacation 加了个字段）之后，你不需要去清理成千上万个旧键 —— 把代码里的 v1 改成 v2，所有旧缓存瞬间"失效" （它们还在，但再也不会被读到，等 TTL 到了自然消失）。
这和第 19 章的「内容指纹」、第 14 章的「索引别名切换」是同一个模式： 不修改旧的，而是换一个新的名字。

用「版本键」批量失效

/**
 * 列表类缓存最难精确失效。技巧：用一个「代」计数器嵌进键里。
 * 任何一条数据变化时，把计数器 +1，所有旧列表缓存一次性作废。
 */
async function getVacationList(env: Bindings, filter: string) {
  const gen = (await env.CACHE.get(`gen:vacations`)) ?? '0'
  const key = `vacation-list:v1:g${gen}:${filter}`

  const cached = await env.CACHE.get(key, 'json')
  if (cached) return cached

  const list = await db.list(filter)
  await env.CACHE.put(key, JSON.stringify(list), { expirationTtl: jitteredTtl(300) })
  return list
}

/** 任何写操作之后调用 */
async function bumpVacationGeneration(env: Bindings) {
  const cur = Number((await env.CACHE.get('gen:vacations')) ?? '0')
  await env.CACHE.put('gen:vacations', String(cur + 1))
  // 旧的 g0 键还在，但再也没人会用这个键去查了，TTL 到了自己消失
}

什么该缓存，什么不该

适合缓存不该缓存
读多写少的数据（商品、文章、配置）每次都在变的数据（实时库存、余额）
计算昂贵的结果（统计报表、推荐列表）本来就很快的查询（主键取单条，几毫秒）
外部 API 结果（第 20 章的天气）涉及正确性的判断（权限、库存扣减）
渲染好的 HTML 片段用户隐私数据（除非键里有用户标识且存储可信）
会话数据（第 9 章）一次性的东西（验证码用完即弃，不是缓存是状态）
⚠ 绝对不要缓存权限判断结果

「把 can(user, 'order:delete') 的结果缓存 5 分钟」看起来很合理 —— 直到你把一个员工降权或者移出团队，他还能继续操作 5 分钟。
权限相关的判断要么不缓存，要么在权限变更时立即主动失效。 同理，第 21 章说的「离职后会话要立即失效」也是这个道理。

进程内缓存 vs 共享缓存

进程内（Map）共享（Redis / KV）
延迟0 —— 就是内存读取1–10 ms（网络往返）
一致性差：N 个实例 N 份，各自过期好：所有实例看到同一份
失效没法主动失效其他实例的删一次全局生效
容量受实例内存限制可以很大
重启全部丢失（冷启动尖峰）保留
适合不常变的配置、编译好的模板、路由表业务数据
★ 两级缓存：又快又一致（大部分时候）

进程内缓存放非常短的 TTL（几秒），后面挡着共享缓存。
这样热点数据的大部分请求在内存里就返回了，同时「数据最多旧几秒」是可接受的。
但要清楚地知道：你接受了「最长 N 秒的不一致」这个代价。 

const local = new Map<string, { value: unknown; expiresAt: number }>()

async function twoTier<T>(env: Bindings, key: string, load: () => Promise<T>): Promise<T> {
  const now = Date.now()

  // L1：进程内，5 秒
  const hit = local.get(key)
  if (hit && hit.expiresAt > now) return hit.value as T

  // L2：共享缓存
  const shared = await env.CACHE.get<T>(key, 'json')
  if (shared) {
    local.set(key, { value: shared, expiresAt: now + 5000 })
    return shared
  }

  // L3：数据源
  const fresh = await load()
  await env.CACHE.put(key, JSON.stringify(fresh), { expirationTtl: jitteredTtl(300) })
  local.set(key, { value: fresh, expiresAt: now + 5000 })
  return fresh
}
⚠ 进程内缓存要设上限

new Map() 会无限增长 —— 每个不同的 key 都往里塞一条， 这就是内存泄漏。必须用 LRU 之类的有界结构，或者定期清理过期项。
「本地跑得好好的，线上跑几天就 OOM」，这是最常见的原因之一。

监控

★ 没有监控的缓存，你不知道它有没有用
async function cachedGet<T>(env: Bindings, key: string, load: () => Promise<T>, c: Context) {
  const start = Date.now()
  const cached = await env.CACHE.get<T>(key, 'json')

  if (cached) {
    c.get('log')('info', 'cache', {
      result: 'hit',
      // 用键的前缀分组，别把完整 key 当维度 —— 高基数问题（第 28 章）
      namespace: key.split(':')[0],
      durationMs: Date.now() - start,
    })
    return cached
  }

  const value = await load()
  await env.CACHE.put(key, JSON.stringify(value), { expirationTtl: jitteredTtl(300) })

  c.get('log')('info', 'cache', {
    result: 'miss',
    namespace: key.split(':')[0],
    durationMs: Date.now() - start,
  })
  return value
}
指标怎么解读
命中率低于 50% 说明缓存基本没起作用 —— 要么 TTL 太短，要么键设计太细碎
命中/未命中的耗时差如果差距不大，说明这个缓存不值得存在
缓存层错误率突然上升 = 缓存服务有问题，准备承受回源流量
内存使用 / 淘汰率淘汰率高说明容量不够，热点数据被挤出去了
💡 命中率 100% 也可能是坏事

它可能意味着 TTL 太长，用户一直在看过期的数据。
健康的命中率取决于业务 —— 商品详情页 95% 很正常，用户个人页 60% 可能就够了。 关键是你要知道这个数字，并且知道它为什么是这个值。

那句名言

计算机科学只有两件难事：缓存失效和命名。
—— Phil Karlton

这不只是个玩笑。缓存失效难，是因为它的难度不在写代码，而在知道该在什么时候失效什么：

难点表现
依赖关系不显式改了商品价格，谁知道首页推荐、搜索结果、购物车里都缓存了它？
失效是「负空间」忘了失效不会报错、不会崩溃 —— 只是数据悄悄错了几分钟
很难测试单元测试里缓存通常是关掉的；集成测试很少覆盖「改完之后立刻读」
问题延迟出现用户看到旧价格 → 下单 → 客服工单 → 三天后才追查到是缓存问题
★ 三条降低难度的原则
  1. 能用 TTL 就别用主动失效。「最多旧 5 分钟」如果业务能接受， 就不要去维护复杂的失效逻辑。TTL 是自愈的，主动失效是会漏的。
  2. 用版本号代替精确失效。改一个计数器让一整类缓存作废， 比追踪每一条依赖关系可靠得多。
  3. 把缓存收拢到数据访问层。和第 21 章的租户隔离同一个思路： 如果读写都必须经过 VacationRepo，那失效逻辑就只有一个地方要维护。
// 缓存和失效都在数据访问层内部，业务代码完全不知道缓存的存在
export function createCachedVacationRepo(db: DrizzleDb, cache: KVNamespace): VacationRepo {
  const base = createVacationRepo(db)

  return {
    async findBySku(sku) {
      return cachedGet(cache, `vacation:v2:${sku}`, () => base.findBySku(sku))
    },

    async update(sku, patch) {
      const result = await base.update(sku, patch)
      // 失效逻辑只在这一处，不会散落到十个 handler 里
      await cache.delete(`vacation:v2:${sku}`)
      await bumpGeneration(cache, 'vacations')
      return result
    },
  }
}

小结

  • 加缓存之前先确认瓶颈 —— 缺索引和 N+1 不该用缓存来掩盖。
  • Cache-aside：先更新数据库，再删除缓存（删除而非更新）。
  • 穿透 → 缓存空结果（短 TTL）；击穿 → 单飞；雪崩 → TTL 加抖动 + 降级限流。
  • 缓存键必须包含：命名空间、版本号、租户标识、影响结果的参数。
  • 版本号和「代计数器」让批量失效变得可靠，避免追踪每一条依赖。
  • 不要缓存权限判断和涉及正确性的数据。
  • 进程内缓存要设容量上限，否则就是内存泄漏。
  • 必须监控命中率 —— 否则你不知道这个缓存有没有用。
  • 能用 TTL 就别用主动失效；把缓存收拢到数据访问层。

动手练习

  1. 给第 13 章的 findBySku 加上 cache-aside，用日志统计命中率。刷新页面几十次，看看命中率是多少。
  2. 制造一次缓存穿透：循环请求 1000 个不存在的 SKU，观察数据库查询次数。然后加上「缓存空结果」再测一遍。
  3. 制造一次击穿：让缓存过期，然后用 Promise.all 同时发 100 个请求，数一数数据库被查了几次。接上单飞后再数。
  4. 把 TTL 固定成 60 秒，一次性写入 100 个键，观察 60 秒后是否出现请求尖峰。加上抖动再看。
  5. 在多租户场景下故意写一个不含 tenantId 的缓存键，用两个租户的账号访问同一个资源，确认能复现数据串号。（然后修好它。）
  6. 改一条数据后立刻读取，确认拿到的是新值。再把「删缓存」那行注释掉，确认能复现脏数据。
