第 2 章

准备开发环境

装好工具，然后不用任何框架手写一个 Web 服务器。 只有亲手体会过没有框架的麻烦，你才会明白 Hono 每一个 API 在替你省什么。

本章目标

  • 装好 Node.js、包管理器和编辑器，能在终端里跑起一个脚本
  • 理解 Request / Response 这两个标准对象
  • 不用框架，手写路由和静态文件服务
  • 亲眼看到手写方案的问题，从而理解框架存在的理由

选一个运行时

Hono 支持很多运行时，但作为初学者，你只需要选一个。我的建议：

✅

Node.js（推荐）

生态最全，遇到问题搜得到答案，几乎所有 npm 包都能用。本教程默认用它。装 LTS 版本。

🐇

Bun

启动飞快，自带打包器和测试跑起来很爽。原生支持 TypeScript，省掉不少配置。适合已经熟悉 Node 的人。

🦎

Deno

默认安全（要显式给网络/文件权限），原生 TypeScript。配置最少，但生态相对小。

💡 别纠结

因为 Hono 基于 Web 标准，你现在选 Node，将来想换 Bun，业务代码基本不用动 —— 只改入口那几行。 所以先用你最熟的，把注意力放在概念上。

编辑器

用 VS Code。它对 TypeScript 的支持是同类里最好的， 而 TypeScript 恰好是 Hono 最大的卖点之一 —— 编辑器里的自动补全和红波浪线，就是 Hono 类型系统在替你干活的直观体现。

第一个服务器：完全不用框架

现在开始写代码。建一个目录，初始化项目： 

mkdir meadowlark
cd meadowlark
npm init -y
npm install @hono/node-server
npm install -D tsx typescript @types/node
ⓘ 这几个包是干嘛的
  • @hono/node-server —— 让 Node.js 能跑「标准 fetch 处理函数」的适配器。注意：本章还不会用到 Hono 本身，我们只借这个适配器把标准 API 接到 Node 上。
  • tsx —— 直接运行 TypeScript 文件，不用先编译。
  • typescript / @types/node —— 类型检查和 Node API 的类型定义。

新建 src/server.ts：

import { serve } from '@hono/node-server'

serve({
  port: 3000,
  fetch(request: Request) {
    return new Response('你好，世界！', {
      headers: { 'Content-Type': 'text/plain; charset=utf-8' },
    })
  },
})

console.log('服务器已启动：http://localhost:3000')

运行它：

npx tsx src/server.ts

浏览器打开 http://localhost:3000，你应该能看到「你好，世界！」。

这几行代码里没有任何框架。fetch 就是一个普通函数：收到一个 Request，返回一个 Response。 这就是整个 Web 标准服务端模型的全部。

★ 这为什么重要

你在浏览器里用 fetch() 发请求时，拿到的就是 Response 对象； Service Worker 里拦截请求，拿到的就是 Request 对象。 换句话说，你学会的这套东西，前端后端通用 —— 这是 Web 标准路线最大的红利。

手写路由

现在这个服务器不管你访问什么路径，都返回同一句话。我们让它区分首页和「关于」页 —— 这个把 URL 映射到不同处理逻辑的机制，就叫路由（routing）。 

import { serve } from '@hono/node-server'

serve({
  port: 3000,
  fetch(request: Request) {
    // 把 URL 字符串解析成结构化对象
    const url = new URL(request.url)
    // 去掉结尾斜杠、统一小写，避免 /About/ 匹配不上
    const path = url.pathname.replace(/\/+$/, '').toLowerCase()

    switch (path) {
      case '':
        return new Response('云雀旅行', {
          headers: { 'Content-Type': 'text/plain; charset=utf-8' },
        })
      case '/about':
        return new Response('关于云雀旅行', {
          headers: { 'Content-Type': 'text/plain; charset=utf-8' },
        })
      default:
        return new Response('404 - 页面不存在', {
          status: 404,
          headers: { 'Content-Type': 'text/plain; charset=utf-8' },
        })
    }
  },
})

试试 /、/about、/About/、/nope，还有带查询串的 /about?x=1。

⚠ 已经开始难受了

注意我们做了多少手工活：解析 URL、去尾部斜杠、转小写、每个分支都要重复写 Content-Type。 而且这个 switch 只能按路径分支 —— 如果 /about 的 GET 和 POST 要走不同逻辑呢？如果路径里有参数比如 /vacations/:sku 呢？switch 就不够用了。

手写静态文件服务

真实网站要返回 HTML 和图片，不是纯文本。这类不会变的文件叫静态资源。 建立目录结构： 

meadowlark/
├── package.json
├── public/
│   ├── home.html
│   ├── about.html
│   ├── 404.html
│   └── img/
│       └── logo.png
└── src/
    └── server.ts

随便写点 HTML 进去，比如 public/home.html：

<!doctype html>
<html lang="zh-CN">
  <head><meta charset="utf-8"><title>云雀旅行</title></head>
  <body>
    <img src="/img/logo.png" alt="云雀旅行">
    <h1>欢迎来到云雀旅行</h1>
    <p><a href="/about">关于我们</a></p>
  </body>
</html>

现在改服务器，让它读文件返回：

import { serve } from '@hono/node-server'
import { readFile } from 'node:fs/promises'
import { join } from 'node:path'

const PUBLIC = join(process.cwd(), 'public')

async function serveFile(relPath: string, contentType: string, status = 200) {
  try {
    const data = await readFile(join(PUBLIC, relPath))
    return new Response(data, {
      status,
      headers: { 'Content-Type': contentType },
    })
  } catch {
    return new Response('500 - 服务器内部错误', { status: 500 })
  }
}

serve({
  port: 3000,
  async fetch(request: Request) {
    const path = new URL(request.url).pathname.replace(/\/+$/, '').toLowerCase()

    switch (path) {
      case '':
        return serveFile('home.html', 'text/html; charset=utf-8')
      case '/about':
        return serveFile('about.html', 'text/html; charset=utf-8')
      case '/img/logo.png':
        return serveFile('img/logo.png', 'image/png')
      default:
        return serveFile('404.html', 'text/html; charset=utf-8', 404)
    }
  },
})
⚠ 问题更严重了
  • 每加一张图片，就要加一个 case。有 200 张图怎么办？
  • MIME 类型要自己查表：.png 是 image/png，.svg 是 image/svg+xml， .woff2 是 font/woff2……
  • 如果不写死路径而是直接拼接用户给的路径，用户请求 /../../etc/passwd 就能读到你系统上的任意文件 —— 这叫路径穿越漏洞，是个真实且常见的安全问题。
  • 没有缓存头，浏览器每次都重新下载 logo。

所以框架到底解决了什么

把上面遇到的麻烦列出来，你会发现它们正好对应 Hono 的几个核心 API：

手写时的麻烦Hono 的答案在第几章
URL 解析、尾斜杠、大小写路由器自动处理第 3、15 章
按 HTTP 方法分支app.get() / app.post()第 3 章
路径参数 /vacations/:skuc.req.param('sku')第 15 章
每次都写 Content-Typec.text() / c.json() / c.html()第 6 章

统一错误处理app.onError() / app.notFound()第 3、6 章

小结

  • Web 标准服务端模型只有一条规则：拿到 Request，返回 Response。
  • @hono/node-server 的 serve() 负责把这个标准模型接到 Node.js 上。
  • 不用框架也能写服务器，但路由、MIME、安全、错误处理都要自己造，而且很容易造错。
  • 框架的价值是让代码可维护，不是让代码「变得可能」。

动手练习

  1. 把上面的静态文件服务器跑起来，然后故意请求一个不存在的路径，确认返回的是 404 状态码（在浏览器开发者工具的 Network 面板里看）。
  2. 给服务器加一个 /api/time 路由，返回 JSON {"now": "..."}。提示：Response.json() 是个静态方法。
  3. 试着支持 public/ 下的任意文件（不再写死 case）。写完之后想一想：用户请求 /../src/server.ts 会发生什么？你会怎么防？
  4. 用 curl -i http://localhost:3000/about 看看完整的响应头。数一数你手动设置了几个头，浏览器又期待多少个。
