第 14 章

搜索

上一章你学会了用索引让查询变快。这一章从一个尴尬的事实开始： 那些索引对「搜索框」完全无效。 几乎每个项目都会先写一个 LIKE '%关键词%'，然后在数据涨到几万条时发现它撑不住。

本章目标

  • 理解 LIKE '%x%' 为什么用不上索引，以及它效果差在哪
  • 搞懂倒排索引和分词，知道中文为什么更麻烦
  • 用 PostgreSQL 全文检索和 SQLite FTS5 实现搜索
  • 判断什么时候该上专用搜索引擎
  • 解决最难的那个问题：索引和数据库怎么保持同步
  • 把搜索体验做对：高亮、分页、零结果、搜索分析

LIKE 为什么撑不住

-- 几乎每个项目的第一版搜索
SELECT * FROM vacations
WHERE name LIKE '%海岸%' OR description LIKE '%海岸%';

它有两个独立的问题：性能和效果。先看性能。

效果问题更严重

用户搜期望LIKE 的实际表现
「海岸 度假」同时含这两个词的结果找不到 —— 它在找连续的「海岸 度假」这个整串
「breweries」也匹配 brewery找不到 —— 不认识词形变化
「Hood River」不分大小写取决于数据库排序规则，很可能漏掉
「hod river」（拼错）猜到用户想搜什么零结果
任意词最相关的排在最前没有相关性概念，顺序基本随机
★ 搜索和查询是两件事

查询是精确的：「available = true 且 price < 200」，答案要么对要么错。
搜索是模糊的：「跟『海边玩水』有关的东西」，答案是一个按相关性排序的列表。
用查询的工具（WHERE + B-tree）去做搜索，就像用尺子量温度 —— 工具本身没问题，只是不对口。

倒排索引

全文检索的核心数据结构。理解它，后面所有工具的行为你都能预测。

建索引前要做的加工

步骤做什么例子
分词 Tokenize把句子切成词"Oregon coast trip" → ["Oregon", "coast", "trip"]
归一化统一大小写、去掉重音"Oregon" → "oregon"，"café" → "cafe"
词干化 Stemming还原到词根"breweries"、"brewery" → "breweri"
去停用词丢掉没有区分度的词the、a、of、的、了
⚠ 中文分词是另一个难度

英文靠空格就能切开。中文没有空格：「俄勒冈海岸度假」该切成什么？
「俄勒冈 / 海岸 / 度假」是对的，但机器不知道 —— 它需要词典或统计模型。

更麻烦的是歧义：「南京市长江大桥」可以切成「南京市 / 长江大桥」， 也可以切成「南京 / 市长 / 江大桥」。
后果很实际：如果分词器把「海岸度假」当成一个词，用户搜「海岸」就什么都搜不到。 所以中文项目一定要实际测一下分词结果，别假设它是对的。 

-- PostgreSQL 里可以直接看分词结果，调试时非常有用
SELECT to_tsvector('english', 'Enjoy the ocean air and quaint coastal towns');
-- → 'air':4 'coastal':7 'enjoy':1 'ocean':3 'quaint':6 'town':8
--   注意：the、and 被丢掉了，towns 被还原成 town，数字是词的位置

方案一：PostgreSQL 全文检索

如果你已经在用 Postgres，先试它 —— 不用引入新组件，而且支持事务。

-- ① 加一个生成列，自动维护 tsvector
ALTER TABLE vacations ADD COLUMN search_vector tsvector
  GENERATED ALWAYS AS (
    -- setweight 给字段分权重：A 最重要，D 最次要
    setweight(to_tsvector('english', coalesce(name, '')), 'A') ||
    setweight(to_tsvector('english', coalesce(category, '')), 'B') ||
    setweight(to_tsvector('english', coalesce(description, '')), 'C')
  ) STORED;

-- ② GIN 索引 —— 倒排索引在 Postgres 里的实现
CREATE INDEX idx_vacations_search ON vacations USING GIN (search_vector);
★ 生成列解决了同步问题

GENERATED ALWAYS AS ... STORED 意味着 name 或 description 一变，search_vector 自动跟着变， 而且在同一个事务里。
你不可能忘记更新索引 —— 因为根本没有「更新索引」这个步骤。 这是本章后面那个「同步」难题在单库方案下的最优解。 

import { sql } from 'drizzle-orm'

export async function searchVacations(q: string, limit = 20, offset = 0) {
  // websearch_to_tsquery 支持用户熟悉的语法："海岸" -攀岩 OR
  const query = sql`websearch_to_tsquery('english', ${q})`

  return db.execute(sql`
    SELECT
      sku, name, description, price,
      ts_rank(search_vector, ${query}) AS rank,
      -- 让数据库直接生成带高亮标记的摘要
      ts_headline('english', description, ${query},
                  'StartSel=<mark>, StopSel=</mark>, MaxWords=30') AS snippet
    FROM vacations
    WHERE search_vector @@ ${query}
      AND available = true
    ORDER BY rank DESC, packages_sold DESC
    LIMIT ${limit} OFFSET ${offset}
  `)
}
ⓘ 三种 tsquery 函数的区别
函数输入适合
to_tsquery'海岸 & 度假'，语法错了会报错程序构造的查询
plainto_tsquery纯文本，所有词按 AND 连接简单场景
websearch_to_tsquery支持 "引号短语"、-排除、OR用户输入，首选这个

永远不要把用户输入拼进 to_tsquery —— 一个多余的 & 就会让查询报错，页面直接 500。

⚠ 中文要装扩展

Postgres 内置的分词器不认识中文，to_tsvector('english', '海岸度假') 会把整串当成一个词。中文需要 zhparser 或 pg_jieba 扩展 —— 但很多托管 Postgres（包括一些 Serverless 服务）不允许装扩展。 选型时先确认这一点，否则做到一半才发现走不通。

方案二：SQLite FTS5

用 SQLite 或 Cloudflare D1 的话，FTS5 是内置的：

-- ① 建一张虚拟表专门放索引
CREATE VIRTUAL TABLE vacations_fts USING fts5(
  sku UNINDEXED,          -- 只存不索引，用来关联回主表
  name,
  description,
  content='vacations',    -- 外部内容模式：不重复存正文，省空间
  content_rowid='rowid',
  tokenize='porter unicode61'
);

-- ② 用触发器保持同步（FTS5 没有生成列）
CREATE TRIGGER vacations_ai AFTER INSERT ON vacations BEGIN
  INSERT INTO vacations_fts(rowid, sku, name, description)
  VALUES (new.rowid, new.sku, new.name, new.description);
END;

CREATE TRIGGER vacations_ad AFTER DELETE ON vacations BEGIN
  INSERT INTO vacations_fts(vacations_fts, rowid, sku, name, description)
  VALUES ('delete', old.rowid, old.sku, old.name, old.description);
END;

CREATE TRIGGER vacations_au AFTER UPDATE ON vacations BEGIN
  INSERT INTO vacations_fts(vacations_fts, rowid, sku, name, description)
  VALUES ('delete', old.rowid, old.sku, old.name, old.description);
  INSERT INTO vacations_fts(rowid, sku, name, description)
  VALUES (new.rowid, new.sku, new.name, new.description);
END;

export async function searchVacations(db: D1Database, q: string, limit = 20) {
  // bm25 的负数权重：绝对值越大越重要，name 的权重是 description 的 10 倍
  const { results } = await db
    .prepare(`
      SELECT v.sku, v.name, v.price,
             snippet(vacations_fts, 2, '<mark>', '</mark>', '…', 24) AS snippet,
             bm25(vacations_fts, 10.0, 1.0) AS rank
      FROM vacations_fts
      JOIN vacations v ON v.rowid = vacations_fts.rowid
      WHERE vacations_fts MATCH ?
        AND v.available = 1
      ORDER BY rank
      LIMIT ?
    `)
    .bind(toFtsQuery(q), limit)
    .all()

  return results
}

/** 用户输入不能直接进 MATCH —— FTS5 有自己的查询语法 */
function toFtsQuery(input: string): string {
  return input
    .replace(/["*():^-]/g, ' ')           // 去掉所有语法字符
    .split(/\s+/)
    .filter(Boolean)
    .map((term) => `"${term}"*`)          // 每个词加引号，末尾 * 支持前缀匹配
    .join(' AND ')
}
⚠ 用户输入永远要清洗

用户在搜索框里输入 a" OR "b 或者一个孤零零的 -， 直接拼进 MATCH 会导致语法错误 → 500 → 用户看到错误页。
这不是安全问题（参数绑定挡住了注入），而是可用性问题： 搜索框是用户唯一能往你系统里塞任意字符串的地方，它一定会收到奇怪的输入。

相关性排序

搜索的输出是一个排序的列表。排序质量比召回质量更影响体验 —— 用户基本只看前五条。 

-- 把业务信号混进排序
ORDER BY
  ts_rank(search_vector, query) * 0.6
  + LEAST(packages_sold / 100.0, 1.0) * 0.3
  + (1.0 / (1 + EXTRACT(EPOCH FROM now() - created_at) / 86400 / 30)) * 0.1
  DESC
💡 权重靠数据调，不靠拍脑袋

这些系数不可能一次调对。做法是：先上线一个粗糙版本，记录用户搜了什么、点了第几条 （本章最后一节），再根据真实数据调整。
「用户搜完点了第 8 条」是个强信号：说明前 7 条排错了。

方案三：专用搜索引擎

★ 什么时候该升级

数据库全文检索够用到什么时候？出现下面任何一条，就该考虑专用引擎了：

  • 需要拼写容错（用户打错字也要能搜到）
  • 需要输入即搜（每敲一个字符都要出结果，要求个位数毫秒）
  • 需要分面筛选（左侧「品类 (12) / 价格区间 (5)」那种带计数的过滤器）
  • 需要同义词配置（「笔电」= 「笔记本」= 「laptop」）
  • 搜索量大到拖累主库（搜索和事务抢同一份资源）
  • 需要中文分词但托管数据库装不了扩展
方案特点适合
Meilisearch开箱即用的拼写容错和输入即搜，配置极少，自托管简单中小项目的首选
Typesense和 Meilisearch 定位接近，分面和地理搜索更强电商类筛选场景
Algolia托管服务，体验最好，有边缘节点不想运维、预算充足
Elasticsearch / OpenSearch功能最全也最重，聚合分析强大规模、复杂需求、兼做日志分析
向量检索按语义而非关键词匹配（「海边玩水」能搜到「冲浪」）作为关键词搜索的补充，不是替代
import { MeiliSearch } from 'meilisearch'

const client = new MeiliSearch({ host: c.env.MEILI_HOST, apiKey: c.env.MEILI_KEY })
const index = client.index('vacations')

// 配置一次即可
await index.updateSettings({
  searchableAttributes: ['name', 'category', 'description'],   // 顺序即权重
  filterableAttributes: ['category', 'available', 'price'],
  sortableAttributes: ['price', 'packagesSold'],
  synonyms: { '笔电': ['笔记本', 'laptop'] },
})

// 查询
const res = await index.search(q, {
  limit: 20,
  filter: ['available = true', 'price < 300'],
  facets: ['category'],                       // 返回每个分类的命中数
  attributesToHighlight: ['name', 'description'],
})
⚠ 引入搜索引擎 = 引入一个新的数据副本

这是最容易被低估的成本。你现在有两份数据，它们会不一致： 用户改了标题但搜索结果还是旧的、商品下架了还能搜到、 删掉的数据还留在索引里。
下一节就是专门讲这个。数据库自带的全文检索之所以有吸引力， 很大程度上就是因为它没有这个问题。

最难的部分：索引同步

export async function reindexVacation(sku: string, env: Bindings) {
  const v = await getVacation(env.DB, sku)

  // 记录被删了 → 从索引里也删掉。这一步最容易忘
  if (!v) {
    await index.deleteDocument(sku)
    return
  }

  // 下架的商品不该被搜到 —— 用删除而不是加过滤条件，索引更小更快
  if (!v.available) {
    await index.deleteDocument(sku)
    return
  }

  // 幂等：同一个文档写多少次结果都一样
  await index.addDocuments([{
    id: v.sku,
    name: v.name,
    category: v.category,
    description: v.description,
    price: v.price,
    packagesSold: v.packagesSold,
    available: v.available,
  }])
}

全量重建兜底

/** 每天凌晨跑一次：把整个索引重建到一个新索引，然后原子切换 */
export async function rebuildSearchIndex(env: Bindings) {
  const tmpName = `vacations_${Date.now()}`
  const tmp = client.index(tmpName)
  await tmp.updateSettings(SEARCH_SETTINGS)

  let cursor: string | undefined
  do {
    const page = await listVacations(env.DB, { cursor, limit: 1000, available: true })
    await tmp.addDocuments(page.items.map(toSearchDoc))
    cursor = page.nextCursor
  } while (cursor)

  // 关键：交换别名，用户全程不会看到空索引
  await client.swapIndexes([{ indexes: ['vacations', tmpName] }])
  await client.deleteIndex(tmpName)
}
★ 别原地清空重建

「先 deleteAllDocuments() 再重新导入」这个做法很直觉，但在重建的那几分钟里， 所有用户搜索都是零结果。
正确做法是建一个新索引，导完之后原子地切换别名。 用户完全无感 —— 这和第 20 章「内容指纹」、第 32 章「零停机迁移」是同一个思路： 先准备好新的，再切换，最后清理旧的。

高亮的转义陷阱

⚠ 高亮片段带着 HTML 标签回来

ts_headline 和 snippet() 返回的是含 <mark> 的字符串。 JSX 会把它整个转义，用户看到的是字面的 <mark> 文本。
要渲染就得用第 7 章的 raw() —— 但这意味着关掉了 XSS 防护。 而摘要内容来自数据库，可能包含用户提交的文本。 

// ✅ 安全做法：让数据库用不可能出现在正文里的标记，自己转义后再替换
const snippet = row.snippet     // 用 StartSel=«HL», StopSel=«/HL» 之类的标记

function renderSnippet(s: string) {
  const escaped = s
    .replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;')
  // 转义之后才把自定义标记换成真标签
  return raw(escaped.replace(/«HL»/g, '<mark>').replace(/«\/HL»/g, '</mark>'))
}

<p class="snippet">{renderSnippet(row.snippet)}</p>

  controller = new AbortController()

★ 「零结果查询」清单是产品需求的直接来源

把 resultCount = 0 的查询按频次排序，你会看到三类东西：

  • 用词不一致：用户搜「民宿」，你的数据里写的是「客栈」→ 加同义词
  • 真实的缺货需求：一百个人搜「滑雪」而你没有滑雪产品 → 这是采购信号
  • 分词或拼写问题：搜「hood river」搜不到「Hood River」→ 是 bug

这份清单几乎不花成本就能拿到，但很少有团队真的去看。 另一个高价值指标是平均点击位置：如果用户平均点第 6 条，说明前 5 条排错了。

演进路线

阶段数据量方案
原型< 1000 条LIKE '%x%' 就行 —— 别提前优化
成长1 万 – 100 万数据库全文检索（Postgres FTS / SQLite FTS5）
成熟需要容错、分面、输入即搜Meilisearch / Typesense + 队列同步
规模化千万级、复杂聚合Elasticsearch，可能配合向量检索做语义补充
💡 从一开始就把搜索藏在接口后面

不管现在用什么实现，都把它包成一个函数： 

export interface SearchEngine {
  search(q: string, opts: SearchOptions): Promise<SearchResult>
  index(doc: SearchDoc): Promise<void>
  remove(id: string): Promise<void>
}

这样从 LIKE 升级到 FTS 再升级到 Meilisearch， 业务代码一行不用改。和第 13 章的 VacationRepo、 第 11 章的 Mailer 是同一个套路 —— 这个模式在本教程里已经第三次出现了。

小结

  • LIKE '%x%' 用不上索引（前缀未知 → 全表扫描），而且不分词、不排序、不容错。
  • 全文检索的核心是倒排索引：词 → 文档列表，多词查询就是求交集。
  • 中文分词需要词典或模型，托管数据库可能装不了扩展 —— 选型时先验证。
  • Postgres 的生成列 + GIN 索引能自动保持同步，这是它最大的优势。
  • 相关性 = 文本匹配度 + 业务信号，权重要靠真实数据调。
  • 引入搜索引擎 = 引入第二份数据副本，同步用队列，并有定时全量重建兜底。
  • 重建索引要「建新的 → 切别名 → 删旧的」，不要原地清空。
  • 零结果要给出路；高亮要小心 XSS；深分页用游标。
  • 记录查询词和点击位置，零结果清单是免费的产品需求。

  2. 换成 FTS5 或 Postgres 全文检索，同样的数据量再测一次，对比耗时。
  3. 搜「海岸 度假」这样的多词查询，确认 LIKE 版找不到而全文检索版能找到。
  4. 在搜索框里输入 a" OR "b 和一串 ((((，确认你的服务没有 500。
  5. 实现搜索结果高亮，然后往数据里插一条 description 含 <script>alert(1)</script> 的记录，搜到它，确认脚本没有执行。
  6. 把搜索包成 SearchEngine 接口，写一个基于数组的内存实现用于测试。
  7. 记录搜索日志，自己随便搜十几次（包括故意搜不存在的词），然后把「零结果查询」列出来看看。
