第 15 章

文件与媒体

第 8 章教了怎么接住一个上传的文件。这一章讲后面那一整条链路： 文件该存哪、怎么控制谁能看、图片怎么处理、大文件怎么办， 以及那些「上传了但从没被用到」的文件最后去了哪。

本章目标

  • 设计一条不经过你服务器的上传链路（预签名直传）
  • 设计存储键和数据库记录，让文件可追溯、可清理
  • 区分公开文件和私有文件，用签名 URL 做访问控制
  • 处理图片：什么时候预生成、什么时候按需生成
  • 防住上传相关的几类真实攻击
  • 处理大文件与断点续传

上传的三条路径

★ 为什么直传如此重要
  • 边缘平台有硬限制。Cloudflare Workers 的请求体上限是几百 MB 甚至更低， 而且整个文件要过一遍你的 CPU 时间预算 —— 一个 200 MB 的视频直接就超了。
  • 省带宽和内存。1000 个用户同时传 50 MB 的文件， 经过服务器意味着你要吞下 50 GB 流量并且在内存里缓冲。
  • 用户更快。浏览器直连对象存储的边缘节点，比绕道你的服务器近得多。

预签名直传

export const uploads = sqliteTable('uploads', {
  id: text('id').primaryKey(),
  ownerId: text('owner_id').notNull(),
  // 对象存储里的键，由服务端生成，客户端无权指定
  storageKey: text('storage_key').notNull().unique(),
  originalName: text('original_name').notNull(),
  contentType: text('content_type').notNull(),
  sizeBytes: integer('size_bytes').notNull(),
  // pending = 已签发但还没确认；ready = 可用；failed = 校验没过
  status: text('status', { enum: ['pending', 'ready', 'failed'] }).notNull(),
  // 关联到哪个业务对象。为 null 的就是「孤儿」，等着被清理
  attachedTo: text('attached_to'),
  createdAt: integer('created_at', { mode: 'timestamp' }).notNull(),
})

import { AwsClient } from 'aws4fetch'

const MAX_BYTES = 20 * 1024 * 1024
const ALLOWED = new Set(['image/jpeg', 'image/png', 'image/webp', 'application/pdf'])

const requestSchema = z.object({
  filename: z.string().min(1).max(255),
  contentType: z.string(),
  sizeBytes: z.number().int().positive(),
})

app.post('/api/v1/uploads', requireLogin, zValidator('json', requestSchema), async (c) => {
  const { filename, contentType, sizeBytes } = c.req.valid('json')
  const user = c.get('user')

  // ① 在签发之前校验 —— 而不是在文件传完之后
  if (!ALLOWED.has(contentType)) {
    throw new HTTPException(415, { message: '不支持的文件类型' })
  }
  if (sizeBytes > MAX_BYTES) {
    throw new HTTPException(413, { message: '文件不能超过 20 MB' })
  }
  if (await isOverQuota(c.env.DB, user.id)) {
    throw new HTTPException(403, { message: '存储配额已用完' })
  }

  // ② 键由服务端生成：用户 ID 做前缀便于配额统计和批量删除
  const id = crypto.randomUUID()
  const ext = safeExtension(filename, contentType)
  const storageKey = `u/${user.id}/${id}${ext}`

  await db.insert(uploads).values({
    id, ownerId: user.id, storageKey,
    originalName: filename.slice(0, 255),
    contentType, sizeBytes,
    status: 'pending', createdAt: new Date(),
  })

  // ③ 签一个短期有效的 PUT URL
  const aws = new AwsClient({
    accessKeyId: c.env.R2_ACCESS_KEY_ID,
    secretAccessKey: c.env.R2_SECRET_ACCESS_KEY,
    service: 's3',
  })
  const signed = await aws.sign(
    new Request(`${c.env.R2_ENDPOINT}/${c.env.R2_BUCKET}/${storageKey}`, {
      method: 'PUT',
      headers: { 'Content-Type': contentType, 'Content-Length': String(sizeBytes) },
    }),
    { aws: { signQuery: true }, headers: { 'X-Amz-Expires': '300' } }
  )

  return c.json({ id, uploadUrl: signed.url })
})

// 确认端点：客户端传完后调用，服务端去核实
app.post('/api/v1/uploads/:id/complete', requireLogin, async (c) => {
  const record = await getUpload(c.env.DB, c.req.param('id'))

  if (!record || record.ownerId !== c.get('user').id) {
    throw new HTTPException(404, { message: '找不到这个上传记录' })
  }

  // 关键：去对象存储实际核对，不要相信客户端说「我传好了」
  const head = await c.env.BUCKET.head(record.storageKey)

  if (!head) {
    throw new HTTPException(400, { message: '文件不存在，可能上传失败了' })
  }
  if (head.size !== record.sizeBytes) {
    await c.env.BUCKET.delete(record.storageKey)
    await markFailed(c.env.DB, record.id)
    throw new HTTPException(400, { message: '文件大小与声明不符' })
  }

  await markReady(c.env.DB, record.id)
  await c.env.TASKS.send({ type: 'process-upload', id: record.id })

  return c.json({ id: record.id, status: 'ready' })
})
⚠ 没有第 ⑤ 步的话会怎样

客户端声明「我要传 1 MB 的 jpeg」，拿到签名 URL 之后传了一个 500 MB 的文件， 然后直接调 complete 说传好了。
虽然签名里可以约束 Content-Length（上面就这么做了）， 但不同存储服务的支持程度不一 —— 服务端 head() 核实一遍是唯一可靠的兜底。

写法问题

/** 扩展名只从白名单取，且以 contentType 为准 —— 不信任用户给的文件名 */
const EXT_BY_TYPE: Record<string, string> = {
  'image/jpeg': '.jpg',
  'image/png': '.png',
  'image/webp': '.webp',
  'application/pdf': '.pdf',
}

function safeExtension(filename: string, contentType: string): string {
  return EXT_BY_TYPE[contentType] ?? ''
}
★ 原始文件名只用于「显示」和「下载时的名字」

它是用户提供的数据，和留言内容没有本质区别 —— 存进数据库、渲染时转义（第 7 章）、 但永远不用它来构造路径。
下载时通过响应头把它还给用户：

访问控制

// 私有文件：每次访问都做权限判断，然后签一个短期 URL
app.get('/files/:id', requireLogin, async (c) => {
  const record = await getUpload(c.env.DB, c.req.param('id'))
  if (!record || record.status !== 'ready') return c.notFound()

  // 权限判断在这里做 —— 下一章会讲怎么让它成为结构性保证
  if (!(await canAccess(c.get('user'), record))) {
    throw new HTTPException(403, { message: '没有权限访问这个文件' })
  }

  const url = await signGetUrl(c.env, record.storageKey, { expiresIn: 300 })

  // 302 到签名 URL，文件内容仍然由对象存储直接吐给浏览器
  return c.redirect(url, 302)
})
⚠ 私有文件的响应绝不能被缓存

上面这个 /files/:id 端点如果被 CDN 缓存了， 第二个用户会拿到第一个用户的 302 目标。
必须设 Cache-Control: private, no-store（第 20 章讲过这条铁律）。 签名 URL 的有效期也要短 —— 它一旦被复制出去，在过期前就是有效的。

图片处理

原图往往是 4000×3000 的几 MB 大图，而页面上只显示 400px 宽。 直接发原图是第 20 章说的「体积」问题里最大的一块。

策略做法取舍
预生成 上传后用队列生成固定的几个尺寸 访问快、可预测；但尺寸写死，加一个新尺寸要重跑全量
按需生成 请求 ?w=400 时现场处理并缓存 灵活；但首次访问慢，而且必须限制参数
托管服务 Cloudflare Images、imgix、Cloudinary 省事，功能全；按量付费 
const SIZES = [
  { name: 'thumb', width: 200 },
  { name: 'medium', width: 800 },
  { name: 'large', width: 1600 },
]

export async function processUpload(id: string, env: Bindings) {
  const record = await getUpload(env.DB, id)
  if (!record || !record.contentType.startsWith('image/')) return

  const object = await env.BUCKET.get(record.storageKey)
  if (!object) return

  const original = await object.arrayBuffer()

  for (const size of SIZES) {
    // 生成 WebP：体积通常比 JPEG 小 30%（第 20 章）
    const resized = await resizeImage(original, { width: size.width, format: 'webp' })
    await env.BUCKET.put(`${record.storageKey}/${size.name}.webp`, resized, {
      httpMetadata: {
        contentType: 'image/webp',
        // 派生图是不可变的：键变了内容才变，可以长缓存（第 20 章的内容指纹思路）
        cacheControl: 'public, max-age=31536000, immutable',
      },
    })
  }

  await markProcessed(env.DB, id)
}
⚠ 按需生成必须限制参数取值

/img/abc?w=400 看起来很方便，但攻击者可以请求 ?w=1、?w=2、?w=3……几千个不同的宽度， 每一个都触发一次真实的图片处理，把你的 CPU 和账单打爆。
对策：只接受白名单里的几个宽度（[200, 400, 800, 1600]）， 或者给参数加签名。

上传相关的攻击

★ 用户上传的文件是你系统里最危险的输入
攻击原理对策
伪装类型 把 .php / .svg 改名成 .jpg；Content-Type 是客户端说了算的 读文件头几个字节验真实类型（magic number），不信任声明
SVG 里的脚本 SVG 是 XML，可以内嵌 <script>。用户头像变成 XSS 要么禁用 SVG，要么用 DOMPurify 清洗，要么用独立域名承载用户内容
解压炸弹 一张 10 KB 的 PNG 解压后是 50000×50000 像素，处理时吃光内存 处理前检查图片尺寸，设置像素总数上限
EXIF 隐私 手机照片带 GPS 坐标 —— 用户发张自拍就暴露了家庭住址 默认剥离 EXIF（保留方向信息即可）
恶意文档 带宏的 Office 文件、恶意 PDF，你成了分发渠道 公开分发的文件要接病毒扫描（ClamAV / VirusTotal）
路径穿越 文件名是 ../../config 键由服务端生成（前面已解决） 
/** 读文件头判断真实类型，不看扩展名也不看 Content-Type */
const MAGIC: [string, number[]][] = [
  ['image/jpeg', [0xff, 0xd8, 0xff]],
  ['image/png',  [0x89, 0x50, 0x4e, 0x47]],
  ['application/pdf', [0x25, 0x50, 0x44, 0x46]],
  // WebP: RIFF....WEBP
  ['image/webp', [0x52, 0x49, 0x46, 0x46]],
]

export function sniffType(head: Uint8Array): string | null {
  for (const [type, sig] of MAGIC) {
    if (sig.every((b, i) => head[i] === b)) return type
  }
  return null
}
★ 用独立域名承载用户上传的内容

把用户文件放在 usercontent-example.net（不是你主域名的子域名）， 这样即使某个文件被当作 HTML 执行，它也拿不到你主站的 Cookie， 因为同源策略把它隔离开了（第 21 章）。
GitHub 用 githubusercontent.com、Google 用 googleusercontent.com —— 都是这个原因。

大文件

// 超过 100 MB 用分片上传：并发传、能续传、单片失败只重传那一片
app.post('/api/v1/uploads/multipart', requireLogin, async (c) => {
  const { filename, contentType, sizeBytes } = c.req.valid('json')
  const storageKey = `u/${c.get('user').id}/${crypto.randomUUID()}`

  const upload = await c.env.BUCKET.createMultipartUpload(storageKey, {
    httpMetadata: { contentType },
  })

  const PART_SIZE = 10 * 1024 * 1024
  const partCount = Math.ceil(sizeBytes / PART_SIZE)

  // 给每一片签一个 URL，客户端可以并发上传
  const parts = await Promise.all(
    Array.from({ length: partCount }, (_, i) =>
      signPartUrl(c.env, storageKey, upload.uploadId, i + 1)
    )
  )

  return c.json({ uploadId: upload.uploadId, partSize: PART_SIZE, parts })
})
⚠ 未完成的分片上传会一直占着存储费用

用户传到一半关掉浏览器，那些已上传的分片不会自动消失，但也不可见 —— 你在桶里看不到它们，账单上却看得到。
对策：在对象存储上配一条生命周期规则，「7 天未完成的分片上传自动中止」。 这是一条设置一次就永久生效的规则，值得现在就去配。

孤儿文件

这是文件存储最容易被忽略的一块：上传了但从来没被用上的文件。 

/** 每天跑一次 */
export async function cleanupOrphans(env: Bindings) {
  const cutoffPending = new Date(Date.now() - 24 * 3600_000)
  const cutoffUnattached = new Date(Date.now() - 7 * 24 * 3600_000)

  const orphans = await db.select().from(uploads).where(
    or(
      and(eq(uploads.status, 'pending'), lt(uploads.createdAt, cutoffPending)),
      and(isNull(uploads.attachedTo), lt(uploads.createdAt, cutoffUnattached))
    )
  ).limit(1000)

  for (const o of orphans) {
    // 顺序很重要：先删文件，再删记录。
    // 反过来的话，删记录成功、删文件失败，就再也找不到这个文件了
    await env.BUCKET.delete(o.storageKey)
    await env.BUCKET.delete(`${o.storageKey}/thumb.webp`)
    await db.delete(uploads).where(eq(uploads.id, o.id))
  }

  log('info', 'orphans_cleaned', { count: orphans.length })
}
💡 删除也可以先软后硬

直接删对象是不可逆的。更稳的做法是先移到 trash/ 前缀下， 再用存储的生命周期规则「trash/ 下的对象 30 天后自动删除」。
这样误删有 30 天的后悔窗口，而且不用你写代码去做最终清理。

成本

费用项说明
存储量按 GB·月计。派生图（缩略图）会让总量翻倍甚至三倍，别忘了算进去
出站流量通常是最贵的一项。S3 出站流量费远高于存储费；R2 免出站费，这是它最大的卖点
请求数PUT 通常比 GET 贵一个数量级。别在循环里频繁小写入
处理按需生成图片时，CPU 时间也是钱（见上面的参数白名单）
★ 控制成本的三招
  1. CDN 缓存。派生图设 immutable 长缓存（第 20 章）， 绝大部分请求根本到不了对象存储。
  2. 该删就删。孤儿清理 + 生命周期规则。
  3. 按用户配额。不设上限的话，一个用户就能把你的账单顶穿。

小结

  • 让文件不经过你的服务器：签发短期 URL 让浏览器直传对象存储。
  • 签发之前校验类型、大小、配额；传完之后服务端 head() 核实。
  • 存储键由服务端生成（u/{userId}/{uuid}.ext），原始文件名只用于显示和下载。
  • 私有文件放私有桶 + 签名 URL；「猜不到的 URL」不是访问控制。
  • 图片预生成几个固定尺寸；按需生成必须限制参数取值，否则是账单炸弹。
  • 用文件头判断真实类型；剥离 EXIF；用独立域名承载用户内容。
  • 大文件用分片上传，并配生命周期规则清理未完成的分片。
  • 孤儿文件必须有定时清理，删除时先删文件后删记录。

动手练习

  1. 把第 8 章那个「经过服务器」的上传改成预签名直传。在浏览器 Network 面板确认文件请求的目标域名不是你的服务器。
  2. 拿到签名 URL 后，故意用它上传一个比声明大得多的文件，然后调 complete。确认服务端拒绝了并清理掉了文件。
  3. 实现 sniffType，把一个 .txt 改名成 .jpg 上传，确认被识别出来。
  4. 做一个私有文件端点，用另一个账号的登录态去访问，确认返回 403。再检查响应头有没有 no-store。
  5. 写孤儿清理任务。先手动造几条 pending 记录，把创建时间改成两天前，跑一遍看是否被清掉。
  6. 算一笔账：如果 1 万个用户各传 20 张 3 MB 的照片，每张生成 3 个尺寸，总存储是多少？按你选的服务商，一个月多少钱？
