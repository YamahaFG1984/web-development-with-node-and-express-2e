第 16 章

时间与国际化

时间看起来是所有数据类型里最简单的一个。它不是。 「用户看到的时间差了 8 小时」「定时任务在夏令时那天跑了两次」「跨年那天的报表数字对不上」—— 这些 bug 有一个共同点：写代码的人和用户不在同一个时区。

本章目标

  • 分清三种时间类型，知道各自该用什么列类型存
  • 掌握「存 UTC、显示本地」这条铁律，以及它的例外
  • 理解时区标识符和偏移的区别，为什么只存偏移是错的
  • 用 Intl API 做格式化，不引入任何日期库
  • 做语言协商，选择合适的多语言 URL 策略
  • 避开定时任务、复数、排序这几个常见坑

时间有三种，不是一种

类型PostgreSQLSQLite / D1JavaScript
时刻 timestamptz 整数（毫秒时间戳） Date
本地日期时间 timestamp（无 tz）+ 单独一列存时区 TEXT '2026-09-06 09:00' 字符串
日期 date TEXT '1990-03-14' 字符串
⚠ Postgres 的 timestamp 和 timestamptz 名字都在骗人

timestamptz 听起来像「带时区的时间戳」，但它不存储时区 —— 它把输入转成 UTC 存起来，读取时按会话时区转换显示。
timestamp（不带 tz）则完全不做转换，存什么读什么。
结论：需要「时刻」就用 timestamptz，这是 99% 的情况。 真的需要记住「用户当时选的是哪个时区」，得额外加一列存时区标识符。

铁律：存 UTC，显示本地

// ✅ 存储：永远是 UTC
await db.insert(orders).values({
  createdAt: new Date(),          // Date 内部就是 UTC 毫秒数
})

// ❌ 这些写法都在制造问题
const bad1 = new Date().toLocaleString()          // 变成服务器时区的字符串
const bad2 = '2026-09-06 22:30'                   // 没有时区信息，谁知道是哪里的 22:30
const bad3 = new Date('2026-09-06')               // 被当成 UTC 午夜，不是本地午夜
⚠ new Date('2026-09-06') 和 new Date('2026/09/06') 结果不同

前者是 ISO 格式，被解析成 UTC 午夜；后者不是 ISO 格式， 被解析成本地午夜。差一个时区。
这是 JavaScript 日期 API 最著名的坑之一。 永远显式指定：new Date('2026-09-06T00:00:00Z')， 或者干脆不要把纯日期转成 Date。

时区标识符 vs 偏移

❌ 只存偏移
{ timezoneOffset: -480 }   // 分钟
{ timezone: '+08:00' }
这只是某一刻的偏移。 纽约夏天是 −4，冬天是 −5 —— 存了偏移就无法推算其他日期。
✅ 存 IANA 时区标识符
{ timezone: 'Asia/Shanghai' }
{ timezone: 'America/New_York' }
这是一套规则：包含历史上和未来的所有夏令时切换。 任何日期都能算出正确偏移。
★ 时区规则是政治决定，会变

某个国家宣布取消夏令时、某个地区改了偏移 —— 这些事每年都在发生， IANA 时区数据库一年更新好几次。
所以「未来的时刻」不能预先算成 UTC 存起来。
「2027 年 3 月 15 日上午 9 点在上海开会」应该存成 { localDateTime: '2027-03-15 09:00', timezone: 'Asia/Shanghai' }， 到时候再算 —— 万一规则变了，会议仍然在「上午 9 点」，这才是用户要的。

几件反直觉的事

你以为实际上
一天有 24 小时夏令时切换那天是 23 或 25 小时
「明天同一时间」= 现在 + 24h跨越夏令时时会差一小时。要用日历运算，不是加毫秒数
一分钟有 60 秒存在闰秒（虽然大多数系统会抹平它）
「今天」是确定的取决于你在哪。同一瞬间，北京是 7 号，洛杉矶还是 6 号
时区偏移是整小时印度是 +5:30，尼泊尔是 +5:45
UTC 和 GMT 一样日常等价，但严格来说是两个不同的标准
// ❌ 「统计今天的订单」—— 谁的今天？
const start = new Date()
start.setHours(0, 0, 0, 0)          // 服务器时区的午夜，不是用户的

// ✅ 明确按某个时区计算日期边界
function dayBoundsInTz(date: Date, timeZone: string) {
  // 用 Intl 取出该时区下的年月日
  const parts = new Intl.DateTimeFormat('en-CA', {
    timeZone, year: 'numeric', month: '2-digit', day: '2-digit',
  }).formatToParts(date)
  const get = (t: string) => parts.find((p) => p.type === t)!.value
  const ymd = `${get('year')}-${get('month')}-${get('day')}`

  // 再把该时区的 00:00 和次日 00:00 转回 UTC
  return {
    start: zonedTimeToUtc(`${ymd}T00:00:00`, timeZone),
    end: zonedTimeToUtc(`${ymd}T00:00:00`, timeZone, { addDays: 1 }),
  }
}
ⓘ 关于日期库

zonedTimeToUtc 这类时区换算，原生 API 目前还比较别扭。 实践中用 date-fns-tz 或 Luxon。
但不要用 Moment.js —— 它已官方停止维护，而且体积大、对象可变（容易误改）。
未来的答案是 Temporal（TC39 提案），它把本章讲的三种时间类型做成了 Temporal.Instant、Temporal.PlainDateTime、Temporal.PlainDate 三个独立的类 —— 类型系统直接杜绝了混用。留意它的落地进度。

格式化：用 Intl，别造轮子

Intl 是所有现代 JavaScript 运行时内置的，零依赖，而且比任何库都懂各地习惯。 

const when = new Date('2026-09-06T14:30:00Z')

// 日期时间
new Intl.DateTimeFormat('zh-CN', {
  dateStyle: 'long', timeStyle: 'short', timeZone: 'Asia/Shanghai',
}).format(when)
// → 2026年9月6日 22:30

new Intl.DateTimeFormat('en-US', {
  dateStyle: 'long', timeStyle: 'short', timeZone: 'America/New_York',
}).format(when)
// → September 6, 2026 at 10:30 AM

// 相对时间：「3 天前」
const rtf = new Intl.RelativeTimeFormat('zh-CN', { numeric: 'auto' })
rtf.format(-3, 'day')    // → 3天前
rtf.format(1, 'day')     // → 明天　（numeric:'auto' 才会说「明天」而不是「1天后」）

// 货币 —— 注意不同语言的符号位置和分隔符都不同
new Intl.NumberFormat('zh-CN', { style: 'currency', currency: 'CNY' }).format(1234.5)
// → ¥1,234.50
new Intl.NumberFormat('de-DE', { style: 'currency', currency: 'EUR' }).format(1234.5)
// → 1.234,50 €

// 列表
new Intl.ListFormat('zh-CN', { type: 'conjunction' }).format(['帆船', '啤酒', '风筝'])
// → 帆船、啤酒和风筝

服务端渲染的难题：服务器不知道用户时区

⚠ 请求里没有时区信息

HTTP 请求头里有 Accept-Language（语言），但没有时区。 服务端渲染时你不知道该用哪个时区格式化。

方案做法取舍
用户设置 让用户在账号里选，存进数据库 最准确。登录用户首选
浏览器上报 首次访问时 JS 读 Intl.DateTimeFormat().resolvedOptions().timeZone，写进 Cookie 自动，准确。但首屏拿不到
渲染 UTC，前端转换 服务端输出 <time datetime="…Z">，前端脚本改写显示 首屏可能闪一下，但对匿名用户最省事
边缘平台的地理信息 Cloudflare 提供 cf.timezone 零成本猜测，可作为默认值。但用 VPN 的用户会被猜错 
// 推荐的组合：服务端输出机器可读的 UTC + 一个合理的默认显示
export const TimeStamp: FC<{ at: Date; tz: string; locale: string }> = ({ at, tz, locale }) => (
  <time
    datetime={at.toISOString()}
    data-format="datetime"
    title={new Intl.DateTimeFormat(locale, { dateStyle: 'full', timeStyle: 'long', timeZone: tz }).format(at)}
  >
    {new Intl.DateTimeFormat(locale, { dateStyle: 'medium', timeStyle: 'short', timeZone: tz }).format(at)}
  </time>
)

// 前端渐进增强：如果浏览器时区和服务端猜的不一样，就地修正
const tz = Intl.DateTimeFormat().resolvedOptions().timeZone
document.cookie = `tz=${tz}; path=/; max-age=31536000; samesite=lax`

for (const el of document.querySelectorAll('time[data-format]')) {
  const at = new Date(el.dateTime)
  el.textContent = new Intl.DateTimeFormat(navigator.language, {
    dateStyle: 'medium', timeStyle: 'short', timeZone: tz,
  }).format(at)
}
★ <time datetime> 是个被低估的标签

它让机器能读到精确时刻（搜索引擎、屏幕阅读器、爬虫）， 而显示文本可以是「3 天前」这种人类友好的形式。
这也是下一节可访问性的一个例子：语义化标签让辅助技术能理解内容。

定时任务的时区

⚠ cron 表达式默认是 UTC

0 9 * * * 在 Cloudflare Workers 上是UTC 早上 9 点， 也就是北京时间下午 5 点。
「每天早上给用户发日报」如果按 UTC 跑，中国用户会在下午收到， 美西用户会在凌晨 2 点收到。 

// ❌ 一个固定时刻发给所有人
// crons = ["0 9 * * *"]

// ✅ 每小时跑一次，只处理「此刻当地正好 9 点」的用户
export async function sendDailyDigests(env: Bindings) {
  const now = new Date()

  // 找出当前时刻本地时间是 9 点的所有时区
  const targetZones = ALL_TIMEZONES.filter((tz) => localHourIn(now, tz) === 9)

  for (const tz of targetZones) {
    let cursor: string | undefined
    do {
      const page = await getUsersByTimezone(env.DB, tz, { cursor, limit: 500 })
      // 投递任务，不在这里直接发（第 26 章）
      await env.TASKS.sendBatch(
        page.items.map((u) => ({ body: { type: 'daily-digest', userId: u.id } }))
      )
      cursor = page.nextCursor
    } while (cursor)
  }
}
★ 幂等在这里又一次救命

秋季夏令时切换那天，某些时区的「9 点」会出现两次 —— 上面这个任务会跑两遍。
如果没有第 24 章说的幂等保护（比如用 (userId, 日期) 做唯一约束）， 那天所有用户会收到两封日报。
这是个很好的例子：时区问题往往表现为并发/重复问题。

国际化：文案

❌ 拼接字符串
<p>
  {t('you_have')} {count} {t('new_messages')}
</p>
不同语言的语序不同。 日语的动词在句尾，阿拉伯语从右往左。 拼接出来的句子在很多语言里读不通。
✅ 整句作为一个条目
<p>{t('inbox.unread', { count })}</p>

// zh: "你有 {count} 条新消息"
// ja: "新着メッセージが {count} 件あります"
译者拿到完整句子，可以自由调整语序。

复数不只有单数和复数

// 英语有 2 种形式，中文只有 1 种，俄语有 4 种，阿拉伯语有 6 种
// 别自己写 if (n === 1)
const pr = new Intl.PluralRules('ru-RU')
pr.select(1)    // 'one'
pr.select(2)    // 'few'
pr.select(5)    // 'many'
pr.select(1.5)  // 'other'

// 文案文件里为每种形式提供一条
const messages = {
  'inbox.unread': {
    one:   '{count} новое сообщение',
    few:   '{count} новых сообщения',
    many:  '{count} новых сообщений',
    other: '{count} нового сообщения',
  },
}

type Messages = Record<string, string | Record<string, string>>

export function createTranslator(locale: string, messages: Messages) {
  const plural = new Intl.PluralRules(locale)

  return function t(key: string, vars: Record<string, unknown> = {}): string {
    let template = messages[key]

    // 复数：根据 count 选择形式
    if (typeof template === 'object') {
      const form = plural.select(Number(vars.count ?? 0))
      template = template[form] ?? template.other ?? key
    }
    if (typeof template !== 'string') return key    // 缺翻译时回退到 key，不要崩

    return template.replace(/\{(\w+)\}/g, (_, name) => {
      const v = vars[name]
      // 数字也要本地化格式
      return typeof v === 'number' ? new Intl.NumberFormat(locale).format(v) : String(v ?? '')
    })
  }
}
💡 缺翻译时该显示什么

不要崩溃，也不要显示空白。回退顺序通常是： 当前语言 → 默认语言 → key 本身。
开发环境下可以把缺失的 key 打进日志（第 29 章），这样上线前就能发现漏翻的条目。

语言协商与 URL 策略

import { languageDetector } from 'hono/language'

app.use('*', languageDetector({
  supportedLanguages: ['zh', 'en', 'ja'],
  fallbackLanguage: 'zh',
  // 优先级：URL 路径 > Cookie > 浏览器偏好
  order: ['path', 'cookie', 'header'],
  lookupFromPathIndex: 0,
}))

app.use('*', async (c, next) => {
  const locale = c.get('language')
  c.set('t', createTranslator(locale, await loadMessages(locale)))
  await next()
})

// 根路径按浏览器偏好重定向到具体语言，别让 / 直接渲染
app.get('/', (c) => c.redirect(`/${c.get('language')}/`, 302))
//                                                       ↑ 302 不是 301
⚠ 语言重定向必须用 302，不能用 301

301 是永久重定向，浏览器和 CDN 会缓存它。 一个英语用户访问后，/ → /en/ 这个跳转被缓存下来， 后面的中文用户也会被送到英文页面。
第 6 章讲过 301 的缓存特性，这里是它咬人的一个具体场景。

语言之外的本地化

方面坑
排序中文按拼音还是笔画？德语的 ä 排在哪？用 Intl.Collator，别用 a.localeCompare(b) 的默认行为
姓名「姓」「名」两个字段在很多文化里不成立。用一个 fullName 字段 + 可选的 displayName
地址邮编不一定是数字，州/省不一定存在，顺序也完全不同。别写死表单结构
电话存 E.164 格式（+8613800138000），显示时再按当地习惯格式化
数字德语用 1.234,56，法语用空格分隔。解析用户输入的数字时尤其危险
货币金额和币种必须一起存。日元没有小数位，某些货币有三位
文本长度德语通常比英语长 30%，按钮会被撑破。设计时留余量
RTL阿拉伯语、希伯来语从右往左。用 CSS 逻辑属性（margin-inline-start）代替 margin-left
// 排序：Intl.Collator 比 localeCompare 快得多（可复用），而且能配置
const collator = new Intl.Collator('zh-CN', { sensitivity: 'base', numeric: true })
names.sort(collator.compare)

// numeric: true 让 "第2章" 排在 "第10章" 前面，而不是按字符串比较
★ 金额永远和币种一起存

{ amount: 100 } 是一个 bug 等着发生 —— 100 什么？
{ amountMinor: 10000, currency: 'CNY' }：用最小货币单位（分）存整数， 避开浮点误差（第 13 章提过），并且币种寸步不离。
注意日元的最小单位就是 1 日元，没有「分」—— 所以「除以 100」这种硬编码也是错的，要按币种查小数位数。

💡 让 CI 跑在一个「难搞」的时区下

如果 CI 和开发机都是 UTC，所有时区 bug 都会藏起来。 在 CI 里设 TZ=Pacific/Chatham（UTC+12:45，带夏令时）或 TZ=Asia/Kolkata（+5:30，无夏令时）—— 非整点偏移能立刻暴露一大类假设错误。

小结

  • 时间有三种：时刻、本地日期时间、纯日期。混用是所有时间 bug 的根源。
  • 存 UTC、显示本地；时区转换只在系统边界发生。
  • 存 IANA 时区标识符（Asia/Shanghai），不要存偏移。
  • 未来的时刻不能预先算成 UTC —— 时区规则会变。
  • 一天不总是 24 小时；「今天」取决于你在哪。
  • 用 Intl 做所有格式化，零依赖且比手写正确。
  • 定时任务默认 UTC；「本地时间几点」的需求要每小时扫一遍 + 幂等保护。
  • 文案以整句为单位，复数用 Intl.PluralRules。
  • 公开页面的语言要放在 URL 路径里；语言重定向用 302 不是 301。
  • 金额和币种一起存，用最小货币单位的整数。
  • CI 跑在非整点偏移的时区下，能暴露一大类隐藏假设。
