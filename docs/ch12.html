第 12 章

生产环境考量

离上线还有九章，但现在就该想这些事了。在本地跑得好好的应用， 一到生产环境会遇到完全不同的问题：配置、并发、崩溃、监控。提前想清楚，比上线后半夜救火便宜得多。

本章目标

  • 用环境变量区分开发/测试/生产，并做到跨运行时通用
  • 理解「进程扩容」和「边缘天然扩容」两种模型的区别
  • 正确处理未捕获异常，避免服务器静默死掉
  • 加上健康检查、日志和错误上报
  • 做一次压力测试，知道自己的应用大概能扛多少

执行环境

同一份代码，在不同环境要有不同行为：开发时打详细日志、显示错误堆栈；生产时压缩输出、 隐藏内部信息、连生产数据库。区分方式是环境变量 NODE_ENV： 

NODE_ENV=development npm run dev     # 开发（默认）
NODE_ENV=test npm test               # 测试
NODE_ENV=production node dist/server.js   # 生产
⚠ 只用这三个值

development / test / production 是约定俗成的， 很多库会根据它们改变行为。别发明 staging 这种值放进 NODE_ENV —— 库不认识它，会当成非生产环境处理。 需要区分预发布环境的话，另开一个变量，比如 APP_ENV=staging， 同时保持 NODE_ENV=production。 

import { logger } from 'hono/logger'
import { compress } from 'hono/compress'
import { config, isProduction } from './config'

if (isProduction) {
  app.use(compress())
  app.use(logger(structuredLog))     // 生产：结构化 JSON 日志，便于机器分析
} else {
  app.use(logger())                  // 开发：人类可读的彩色输出
}

app.onError((err, c) => {
  console.error(err)
  return c.json(
    {
      error: '服务器内部错误',
      // 只有非生产环境才暴露堆栈
      ...(isProduction ? {} : { message: err.message, stack: err.stack }),
    },
    500
  )
})
★ 让环境差异尽可能小

每加一处 if (isProduction)，就多一条「本地跑得好好的，线上却挂了」的可能路径。 开发和生产用一样的数据库类型、一样的 Node 版本、一样的构建产物。 差异只留给：日志格式、错误详情、密钥、外部服务地址。

跨运行时读配置

这是 Hono 项目特有的一个问题：不同运行时读环境变量的方式不一样。

运行时怎么读配置放哪
Node.jsprocess.env.KEY.env 文件 / 系统环境变量
Bunprocess.env.KEY（兼容）或 Bun.env.env（自动加载）
DenoDeno.env.get('KEY')系统环境变量
Cloudflare Workersc.env.KEYwrangler.toml / Secrets / .dev.vars

Hono 提供了统一入口：

import { env } from 'hono/adapter'

app.get('/config-demo', (c) => {
  const { DATABASE_URL, COOKIE_SECRET } = env<{
    DATABASE_URL: string
    COOKIE_SECRET: string
  }>(c)

  return c.text('配置读取成功')
})
ⓘ 注意 Workers 上的一个重要差别

在 Node 上你可以在模块顶层读 process.env，随便用。
在 Cloudflare Workers 上，环境变量只在请求上下文里可用 —— 模块顶层读不到 c.env。
所以别写 const db = createDb(process.env.DATABASE_URL) 这种顶层初始化， 要写成 const db = createDb(c.env.DATABASE_URL) 或者用惰性初始化。 这是从 Node 迁到 Workers 时最常踩的坑。

扩容

两种思路：

★ 一个真实的教训

原书作者讲过一个故事：他做了一个抽奖活动，用文件记录中奖人数，满 50 人就停止。 结果服务器是负载均衡的两台 —— 每台各自数到 50，最后送出了 100 份奖品。
这个 bug 在本地永远复现不出来。写代码时就假设「随时会有第二个实例」， 比上线后再改便宜一百倍。

Node 上的集群模式

一个 Node 进程只用一个 CPU 核心。有 8 核就该跑 8 个进程。 PM2 一行命令搞定： 

pm2 start dist/server.js -i max --name meadowlark

或者用 Node 内置的 cluster：

import cluster from 'node:cluster'
import { availableParallelism } from 'node:os'

if (cluster.isPrimary) {
  const n = availableParallelism()
  console.log(`启动 ${n} 个工作进程`)
  for (let i = 0; i < n; i++) cluster.fork()

  // 有进程死了就补一个
  cluster.on('exit', (worker, code, signal) => {
    console.error(`工作进程 ${worker.process.pid} 退出（${code}/${signal}），正在重启`)
    cluster.fork()
  })
} else {
  await import('./server.js')
}

边缘环境不需要操心这些

未捕获的异常

路由里抛出的异常会被 Hono 的 onError 接住，服务器不会挂。 但异步代码里的「游离」异常不一样： 

app.get('/ok', (c) => {
  throw new Error('这个会被 onError 接住')     // ✅ 安全
})

app.get('/danger', (c) => {
  setTimeout(() => {
    throw new Error('这个没人接')               // ❌ 整个进程会崩
  }, 100)
  return c.text('已受理')
})

app.get('/danger2', async (c) => {
  doSomethingAsync()      // ❌ 忘了 await，Promise 被拒绝时无人处理
  return c.text('已受理')
})

原因是：setTimeout 的回调执行时，已经脱离了请求的上下文， Hono 的 try/catch 早就退出了。Node 只能选择终止整个进程 —— 因为它无法判断程序还处于什么状态。 

process.on('uncaughtException', (err) => {
  console.error('未捕获异常：', err)
  reportToSentry(err)
  // 清理资源，然后退出。让进程管理器拉起一个干净的新进程
  server.close(() => process.exit(1))
  // 兜底：10 秒还没关掉就强杀
  setTimeout(() => process.exit(1), 10_000).unref()
})

process.on('unhandledRejection', (reason) => {
  console.error('未处理的 Promise 拒绝：', reason)
  reportToSentry(reason)
})

// 优雅关闭：收到停止信号时，先处理完手头的请求
process.on('SIGTERM', () => {
  console.log('收到 SIGTERM，正在优雅关闭')
  server.close(() => process.exit(0))
})
⚠ 不要用它「兜底继续跑」

有人写 process.on('uncaughtException', err => console.log(err)) 然后不退出， 以为这样服务器就永远不会挂。这非常危险：程序现在处于未知状态， 可能有连接没关、有事务没提交、有内存在泄漏。正确做法是记录、上报、退出、重启。

监控

健康检查端点

app.get('/health', (c) => c.json({ status: 'ok' }))

// 更有用的版本：真的去摸一下依赖
app.get('/health/deep', async (c) => {
  const checks: Record<string, string> = {}
  let healthy = true

  try {
    await db.ping()
    checks.database = 'ok'
  } catch {
    checks.database = 'fail'
    healthy = false
  }

  return c.json({ status: healthy ? 'ok' : 'degraded', checks }, healthy ? 200 : 503)
})
💡 两个端点各有用途

/health 给负载均衡器用：只回答「这个进程还活着吗」，必须极快、不查依赖。 如果它因为数据库慢而超时，负载均衡会把健康的实例也摘掉，小故障变成全面瘫痪。
/health/deep 给运维看板用：告诉你到底哪个依赖出问题了。

结构化日志

开发时 console.log('用户登录了') 很好读。生产时你需要能被机器检索的日志： 

function log(level: string, msg: string, extra: Record<string, unknown> = {}) {
  console.log(JSON.stringify({
    level,
    msg,
    time: new Date().toISOString(),
    ...extra,
  }))
}

app.use(async (c, next) => {
  const start = Date.now()
  const id = c.get('requestId')
  await next()
  log('info', 'request', {
    requestId: id,
    method: c.req.method,
    path: c.req.path,
    status: c.res.status,
    durationMs: Date.now() - start,
  })
})

这样你就能在日志系统里查询「过去一小时所有 500 响应」或「p99 耗时超过 1 秒的接口」。

⚠ 日志里不要写这些

密码、令牌、完整的 Cookie、身份证号、完整银行卡号、以及任何用户隐私数据。 日志通常保留很久、被很多人看到、还会同步到第三方服务。 「不小心把用户密码打进日志」是真实且高频的数据泄露原因。

外部监控

ⓘ 这一节只是入门

日志、指标、追踪三者怎么配合，告警怎么设计才不会让人麻木，SLO 怎么定 —— 第 28 章会系统地讲。

  • 可用性监控：UptimeRobot、Better Stack 等，从外部每分钟请求一次 /health。 必须在外部 —— 你的服务器整个挂了的话，跑在上面的监控也一起挂了。
  • 错误追踪：Sentry 之类。它会聚合相同的错误、附上堆栈和上下文、超过阈值就告警。 比翻日志有效得多。
app.onError((err, c) => {
  Sentry.captureException(err, {
    tags: { path: c.req.path, method: c.req.method },
    extra: { requestId: c.get('requestId') },
  })
  return c.json({ error: '服务器内部错误' }, 500)
})

压力测试

上线前你至少该知道：应用大概能扛多少并发？哪个接口最慢？ 用 autocannon： 

npx autocannon -c 50 -d 10 http://localhost:3000/vacations
# -c 50  50 个并发连接
# -d 10  持续 10 秒

┌─────────┬──────┬──────┬───────┬──────┬─────────┬─────────┬───────┐
│ Stat    │ 2.5% │ 50%  │ 97.5% │ 99%  │ Avg     │ Stdev   │ Max   │
├─────────┼──────┼──────┼───────┼──────┼─────────┼─────────┼───────┤
│ Latency │ 2 ms │ 4 ms │ 11 ms │ 18 ms│ 4.82 ms │ 3.11 ms │ 89 ms │
└─────────┴──────┴──────┴───────┴──────┴─────────┴─────────┴───────┘

Req/Sec   9856
2xx       98560
non-2xx   0
★ 看 p99，不要看平均值

平均 4.8 ms 听起来很棒，但 1% 的用户等了 18 ms 以上。当接口变复杂后， 这个尾部会拉得很长 —— 平均 50 ms、p99 3 秒的情况很常见， 意味着每 100 个用户就有 1 个觉得你的网站「卡死了」。 性能问题永远藏在尾部。

压测的正确用法是比较，而不是看绝对数字：

  • 加了一个新功能后，同样的压测数据变差了多少？
  • 加了缓存之后提升了多少？
  • 数据从 100 条涨到 10 万条后，响应时间是线性增长还是爆炸增长？

小结

  • NODE_ENV 只用三个标准值；环境差异越少越好。
  • 用 env(c) 跨运行时读配置；Workers 上不能在模块顶层读环境变量。
  • 水平扩容的前提是无状态：会话、文件、计数器都要放共享存储。
  • 未捕获异常要记录、上报、退出、重启，不要装作没事继续跑。
  • /health 要快且不查依赖；日志要结构化且不含敏感信息。
  • 压测看 p99，用它做版本间的对比。

动手练习

  1. 给应用加上 /health 端点，用 curl 确认它返回 200 且响应极快。
  2. 写一个 /danger 路由，在 setTimeout 里抛异常，观察服务器真的崩掉了。然后加上 uncaughtException 处理，确认它记录后正常退出。
  3. 用 autocannon 压测你的首页，记下 p99。然后在处理函数里加一个 await new Promise(r => setTimeout(r, 50))，再压一次，对比差异。
  4. 检查你现在的代码：有没有存在模块级变量里的状态？如果同时跑三个实例会出什么问题？
