第 31 章

维护

上线不是终点。一个项目八成的生命周期是在上线之后度过的。 这一章讲怎么让它活过三年 —— 而不是变成一个没人敢碰的黑箱。

本章目标

  • 为项目制定一个符合实际的长期计划
  • 建立依赖更新的日常节奏，避免「三年不动，一动就崩」
  • 识别并处理技术债
  • 让「隐形故障」显形
  • 把重复的代码提炼成可复用的中间件和库

先想清楚这个项目要活多久

不同寿命的项目，值得投入的维护成本完全不同。上线前就该说清楚：

类型预期寿命该做什么
活动页 / 一次性项目 几周到几个月 写好下线日期。到期真的下线，不要让它变成没人管的僵尸
内部工具 一到三年 基本的测试和文档。明确写出「谁负责」
核心产品 多年 完整的测试、监控、依赖更新流程、值班机制
★ 「没有计划」也是一种计划，而且是最糟的那种

最常见的情况是：一个「临时」项目上线了，三年后它变成了业务关键系统， 但从来没人给过它测试、文档或维护预算。原作者早就离职了， 没人知道它怎么部署，也没人敢改它。
在 README 里写一句「这个项目预期服务到 X 时间，负责人是 Y」， 成本是一分钟，价值是三年。

依赖更新

# 看看有哪些可以升
npm outdated

# 安全漏洞
npm audit
npm audit fix

# 交互式升级（推荐，能看清每个包跨了几个版本）
npx npm-check-updates -i

更好的做法是让机器人来提醒你。GitHub 自带的 Dependabot 配一个文件就行：

version: 2
updates:
  - package-ecosystem: npm
    directory: "/"
    schedule:
      interval: weekly
    open-pull-requests-limit: 5
    groups:
      # 把小版本更新合并成一个 PR，减少噪音
      minor-and-patch:
        update-types: ["minor", "patch"]
💡 有测试，升级才敢点合并

Dependabot 开的 PR 会自动跑你的 CI。如果测试是绿的， 小版本更新基本可以直接合并；大版本更新则需要人工看 CHANGELOG。
没有测试的项目，依赖更新只能靠祈祷。这是第 5 章那些测试的长期回报。

Node 和运行时版本

Node.js 的 LTS 版本大约 30 个月后停止支持。到期后不再有安全补丁 —— 这不是「可以拖一拖」的事。在 package.json 里声明你支持的版本， 并在日历上标好升级时间： 

{
  "engines": { "node": ">=20.0.0" }
}

技术债

技术债不全是坏事。为了赶上线期而临时写的糙代码，是主动借的债 —— 只要你记得它存在，并且打算还。 

// TODO(2026-03): 支持多币种后要重构这里
// FIXME: 大数据量下这个查询会超时，需要加分页。见 issue #142
// HACK: 临时绕过第三方接口的 bug，对方修复后（预计 4 月）删掉这段
⚠ 不带上下文的 TODO 等于垃圾

// TODO: 优化一下 —— 优化什么？谁写的？还需要吗？
三年后没人敢删（万一有用呢），也没人会做（不知道要做什么）。
每条 TODO 要包含：要做什么、为什么、什么时候、关联的 issue 编号。 做不到就别写，直接开个 issue。

什么时候该还债

信号说明
同一个地方反复出 bug这里的设计有问题，不只是这次写错了
「改这个要小心，会牵一发动全身」耦合太紧，该拆了
估一个小需求要三天不是需求复杂，是代码在阻碍你
新人上手要两周结构不清晰或文档缺失
没人敢碰某个文件最危险的信号。它迟早会炸
★ 别搞「重构冲刺」

「我们花两周专门重构」这种计划几乎总是失败：它没有产出可见价值， 第一个紧急需求来了就被砍掉，留下一堆半成品，比原来更乱。
更有效的是「童子军规则」：每次经过一段代码，让它比你来的时候好一点点。 改 bug 时顺手补个测试，加功能时顺手拆掉一个太长的函数。积少成多，而且永远不会被砍。

让隐形故障显形

最危险的故障是那种「网站看起来一切正常」的故障：

📧

邮件停了

API Key 过期，发信全部失败，但代码里 catch 住了没抛出来。用户注册后收不到确认邮件，也没人报告。

💳

支付回调失败

用户付了钱，但你的系统没收到通知，订单一直是「待支付」。

📈

数据没同步

定时任务在两个月前就悄悄失败了，报表数据一直停在那天。

💾

备份停了

存储桶权限变了，备份任务每次都失败。等到需要恢复时才发现。

★ 解法：监控「应该发生的事」，而不只是「不该发生的事」

错误监控只能发现「发生了错误」。但上面这些故障的特征是什么都没发生。 所以要反过来监控：

  • 心跳：定时任务每次成功后 ping 一个监控服务（如 Healthchecks.io）。 超时没收到 ping 就告警。
  • 业务指标：「过去一小时的订单数为 0」在半夜可能正常，在中午一定是出事了。
  • 合成监控：定期用脚本走一遍关键流程（注册 → 下单 → 收邮件），确认端到端是通的。
// 定时任务的心跳
export async function syncDailyReports(env: Env) {
  try {
    await doTheWork()
    // 成功了才 ping
    await fetch(env.HEARTBEAT_URL)
  } catch (err) {
    reportToSentry(err)
    throw err     // 让平台知道这次执行失败了
  }
}

提炼可复用的东西

维护期最常做的一件事，是发现「这段逻辑我已经写第三遍了」。 Hono 里最自然的复用单位是中间件： 

import { createMiddleware } from 'hono/factory'
import { z } from 'zod'

const schema = z.object({
  page: z.coerce.number().int().min(1).default(1),
  perPage: z.coerce.number().int().min(1).max(100).default(20),
})

export const pagination = createMiddleware<{
  Variables: { pagination: { limit: number; offset: number } }
}>(async (c, next) => {
  const parsed = schema.safeParse(c.req.query())
  if (!parsed.success) {
    return c.json({ error: { message: '分页参数不合法' } }, 400)
  }

  const { page, perPage } = parsed.data
  c.set('pagination', { limit: perPage, offset: (page - 1) * perPage })

  await next()
})

// 现在所有列表接口都能直接用
app.get('/api/v1/vacations', pagination, async (c) => {
  const { limit, offset } = c.get('pagination')
  const data = await repo.list({ limit, offset })
  return c.json({ data })
})

什么时候抽出去

💡 三次规则

第一次写：就那么写。
第二次写：注意到了，但还不动 —— 两处相似不代表它们会一直相似。
第三次写：抽出来。这时候你已经见过三个变体， 知道哪些部分是真的通用，哪些应该做成参数。
过早抽象的代价，往往比重复更高。

跨项目复用

如果你有多个 Hono 项目共用同一套中间件，可以发成私有 npm 包： 

{
  "name": "@meadowlark/hono-kit",
  "version": "1.2.0",
  "type": "module",
  "exports": {
    "./pagination": "./dist/pagination.js",
    "./session": "./dist/session.js",
    "./rate-limit": "./dist/rate-limit.js"
  },
  "peerDependencies": { "hono": "^4.0.0" }
}
ⓘ 注意 peerDependencies

共享库不应该把 hono 列进 dependencies，否则项目里会装两份 Hono， 导致类型不兼容和奇怪的运行时问题。用 peerDependencies 声明「我需要宿主项目提供 Hono」。

文档

文档不用多，但有几样是必须的。而且要放在代码仓库里， 这样它才会跟着代码一起演进：

文件回答什么问题
README.md这是什么？怎么在本地跑起来？（新人第一天要看的）
CONTRIBUTING.md怎么提交改动？分支怎么命名？提交信息什么格式？
docs/architecture.md系统由哪几块组成？数据怎么流动？
docs/runbook.md半夜出故障时看的：怎么回滚？日志在哪？谁能联系上？
docs/decisions/为什么选了 A 而不是 B？（避免三年后有人重新纠结同一个问题）
★ 记录「为什么」，而不是「是什么」

「这里用了 Drizzle」—— 看代码就知道，不用写。
「为什么用 Drizzle 而不是 Prisma：因为要跑在 Cloudflare Workers 上， Prisma 当时的边缘支持还不成熟」—— 这个必须写。
代码能表达「是什么」，只有文档能保存「为什么」。而「为什么」恰恰是最容易随人流失的东西。

日常节奏

💡 一个可执行的维护清单

每周（15 分钟）

  • 处理 Dependabot 的 PR
  • 扫一眼错误监控里的新增错误
  • 看一眼响应时间趋势有没有异常

每月（1 小时）

  • npm audit 并处理高危项
  • 检查证书、API Key、订阅的到期时间
  • 看看日志里有没有反复出现但没人管的告警

每季度（半天）

  • 做一次备份恢复演练
  • 回顾技术债清单，挑一两项还掉
  • 更新 README 和架构文档
  • 检查运行时和主要依赖的大版本升级计划

小结

  • 上线前就写清楚项目预期寿命和负责人。
  • 依赖更新的成本是指数增长的，每周一点点远比两年一次便宜。
  • 技术债要么带上下文记录下来，要么当场还掉。别写没有信息的 TODO。
  • 用童子军规则代替重构冲刺。
  • 监控「应该发生的事」，让隐形故障显形。
  • 三次规则决定什么时候抽象；共享库用 peerDependencies。
  • 文档记录「为什么」，尤其是运维手册和技术决策记录。

动手练习

  1. 给项目配上 Dependabot，看看第一批 PR 里有哪些包已经落后了很多个版本。
  2. 跑 npm audit，把高危漏洞处理掉。如果某个漏洞暂时无法修复，写下原因和影响评估。
  3. 搜一遍代码里的 TODO 和 FIXME。有多少条你已经不记得是什么意思了？把它们补全或删掉。
  4. 写一份 docs/runbook.md：假设你今晚不在，同事要处理线上故障，他需要知道什么？
  5. 找出你项目里写了三遍以上的逻辑，把它抽成一个中间件。
  6. 给一个定时任务加上心跳监控，然后故意让它失败，确认你收到了告警。
