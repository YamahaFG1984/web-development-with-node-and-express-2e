第 22 章

多租户与权限

第 21 章讲了「你是谁」和「你能做什么」。这一章讲一个更具体也更危险的问题： 怎么保证 A 公司的用户永远看不到 B 公司的数据。 这类漏洞不需要任何攻击技巧 —— 改一个 URL 里的数字就够了。

本章目标

  • 认识 IDOR：最常见也最容易写出来的越权漏洞
  • 选择多租户的隔离级别，理解各自的代价
  • 把权限检查从「记得写」变成「想漏都漏不掉」的结构性保证
  • 选择合适的权限模型：RBAC / ABAC / ReBAC
  • 给权限写测试，并留下审计日志

从一个五行代码的漏洞说起

app.get('/api/v1/orders/:id', requireLogin, async (c) => {
  const order = await db.select().from(orders)
    .where(eq(orders.id, c.req.param('id')))
  return c.json(order[0])
})

这段代码看起来完全正常：有登录检查，有参数绑定，没有 SQL 注入。 但它有一个致命问题 —— 它检查了「你登录了吗」，没检查「这是你的订单吗」。

★ 正确的写法：把归属写进查询条件
❌ 查完再判断
const order = await getOrder(id)
if (order.userId !== user.id) {
  throw new HTTPException(403)
}
return c.json(order)
能用，但依赖你每次都记得写那个 if。 十个接口里漏一个就是漏洞。
✅ 归属是查询的一部分
const [order] = await db.select().from(orders)
  .where(and(
    eq(orders.id, id),
    eq(orders.userId, user.id)   // ←
  ))

if (!order) return c.notFound()
查不到就是查不到。不存在「查到了但不该给你」这个中间状态。
ⓘ 返回 404 还是 403？

403 等于告诉对方「这个 ID 是存在的，只是不属于你」—— 这本身就是信息泄露， 攻击者可以用它枚举出系统里有哪些 ID。
对「不属于你的资源」返回 404 更安全：从外部看， 「不存在」和「不是你的」应该完全无法区分。
例外：团队协作类产品里，403 加上「联系管理员申请权限」的提示体验更好。 这是安全和体验的权衡，要有意识地做选择。

多租户的三种隔离级别

当你的产品服务多个组织（公司、团队、工作区）时，「数据隔离」从一个功能变成了架构决策。

让漏写变得不可能

「每次查询都记得加 tenant_id」是一条纪律。 纪律在赶工期、新人入职、复制粘贴时都会失效。我们要把它变成结构。

方案一：数据访问层强制注入

import { and, eq, type SQL } from 'drizzle-orm'

/**
 * 租户作用域的数据访问层。
 * 关键设计：构造时必须传 tenantId，之后所有方法自动带上它。
 * 业务代码拿不到「不带租户条件」的查询入口。
 */
export function createTenantDb(db: DrizzleDb, tenantId: string) {
  return {
    async findOrders(extra?: SQL) {
      return db.select().from(orders)
        .where(extra ? and(eq(orders.tenantId, tenantId), extra)
                     : eq(orders.tenantId, tenantId))
    },

    async findOrderById(id: string) {
      const [row] = await db.select().from(orders)
        .where(and(eq(orders.tenantId, tenantId), eq(orders.id, id)))
        .limit(1)
      return row ?? null
    },

    async createOrder(data: NewOrder) {
      // 写入时也强制打上租户标记，而且不接受调用方传入
      return db.insert(orders).values({ ...data, tenantId }).returning()
    },

    async updateOrder(id: string, patch: Partial<Order>) {
      const { tenantId: _ignored, ...safe } = patch as never   // 禁止改租户归属
      return db.update(orders).set(safe)
        .where(and(eq(orders.tenantId, tenantId), eq(orders.id, id)))
        .returning()
    },
  }
}

// 中间件里构造，业务代码只能通过它访问数据
app.use('/app/*', requireLogin, async (c, next) => {
  const tenantId = c.get('user').tenantId
  c.set('db', createTenantDb(rawDb, tenantId))
  await next()
})

app.get('/app/orders/:id', async (c) => {
  // 不可能忘记租户条件 —— 这个入口根本不提供「查全部」的能力
  const order = await c.get('db').findOrderById(c.req.param('id'))
  if (!order) return c.notFound()
  return c.json(order)
})
★ 关键在于「不给出危险的入口」

这个设计的价值不是「帮你加上 tenant_id」，而是业务代码根本拿不到 rawDb。 想写一个漏掉租户条件的查询，你得先绕过这一层 —— 而绕过是个显眼的动作， 在代码评审里一眼就能看见。
好的安全设计不是让人「不要犯错」，而是让犯错需要付出额外的、显眼的努力。

方案二：数据库行级安全（RLS）

PostgreSQL 可以把隔离下沉到数据库本身 —— 这样连写原始 SQL 都逃不掉： 

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id')::uuid);

-- 之后任何查询都会被自动追加这个条件，包括手写 SQL、包括误操作

// 每个请求开始时设置当前租户
await db.execute(sql`SET LOCAL app.tenant_id = ${tenantId}`)
⚠ RLS 的两个坑
  • 连接池会串。SET（不带 LOCAL）的作用域是连接， 而连接会被下一个请求复用 —— 如果忘了重置，B 租户的请求会用上 A 的设置。 必须用 SET LOCAL 并包在事务里。
  • 表的所有者绕过 RLS。默认情况下建表的那个用户不受策略约束。 应用要用一个独立的、非所有者的数据库角色连接，否则策略形同虚设。

方案三：让编译器帮忙

// 给「已确认属于某租户」的 ID 一个专门的类型
type TenantScoped<T> = T & { readonly __tenantChecked: unique symbol }

function scoped<T>(value: T, _proof: TenantProof): TenantScoped<T> {
  return value as TenantScoped<T>
}

// 敏感操作只接受已验证过的 ID
async function deleteOrder(id: TenantScoped<string>) { /* ... */ }

// 直接传原始 ID 会编译报错
await deleteOrder(c.req.param('id'))        // ✗ 类型不匹配
await deleteOrder(await verifyOwnership(c, c.req.param('id')))   // ✓
💡 三种方案叠加使用

它们不是互斥的，而是纵深防御（第 21 章 CSP 那一节的同一个思路）：
数据访问层挡住 99% 的疏忽 → RLS 兜住剩下的原始 SQL → 类型系统在编译期拦一层。
任何一层都可能被绕过，但三层同时失效的概率很低。

权限模型

一个够用的 RBAC 实现

export const PERMISSIONS = [
  'order:read', 'order:write', 'order:delete',
  'member:read', 'member:invite', 'member:remove',
  'billing:read', 'billing:manage',
] as const

export type Permission = (typeof PERMISSIONS)[number]

// 角色只是权限的命名集合
const ROLE_PERMISSIONS: Record<Role, readonly Permission[]> = {
  owner:  PERMISSIONS,
  admin:  ['order:read','order:write','order:delete','member:read','member:invite','billing:read'],
  member: ['order:read','order:write','member:read'],
  viewer: ['order:read','member:read'],
}

export function can(user: User, permission: Permission): boolean {
  return ROLE_PERMISSIONS[user.role].includes(permission)
}

export function requirePermission(permission: Permission) {
  return createMiddleware(async (c, next) => {
    const user = c.get('user')
    if (!user) throw new HTTPException(401, { message: '请先登录' })

    if (!can(user, permission)) {
      // 越权尝试要记日志 —— 这是入侵检测的信号（第 29 章）
      c.get('log')('warn', 'permission_denied', {
        userId: user.id, tenantId: user.tenantId,
        permission, path: c.req.path,
      })
      throw new HTTPException(403, { message: '没有权限执行这个操作' })
    }
    await next()
  })
}

app.delete('/app/orders/:id', requirePermission('order:delete'), handlers.deleteOrder)
★ 用权限判断，不要用角色判断

if (user.role === 'admin') 散落在几十个地方之后， 新增一个「财务」角色就要改几十处，而且一定会漏。
if (can(user, 'billing:manage')) 则只需要在角色定义那一张表里加一行。
角色是给人看的标签，权限才是代码该依赖的东西。

前端也要知道权限，但不能只靠前端

// 后端把权限清单一起返回，前端据此决定显示什么
app.get('/api/v1/me', requireLogin, (c) => {
  const user = c.get('user')
  return c.json({
    id: user.id,
    name: user.name,
    role: user.role,
    permissions: ROLE_PERMISSIONS[user.role],
  })
})
⚠ 前端隐藏按钮不是权限控制

前端的权限判断只影响显示：不给没权限的人看一个点了会报错的按钮。
但用户完全可以打开控制台直接调接口。每一个接口都必须独立做服务端检查， 哪怕对应的按钮在界面上根本不存在。
这和第 8 章「前端校验是体验，服务端校验是必须」是同一句话。

权限检查该放在哪一层

几个容易踩的坑

坑说明
批量接口忘了过滤 单条查询加了 tenant_id，但 POST /orders/batch-delete 接受一个 ID 数组时忘了 —— 传别人的 ID 就删掉了。批量操作要逐个校验归属，或者用 WHERE id IN (...) AND tenant_id = ? 并核对影响行数
关联查询泄露 订单加了租户条件，但 JOIN 出来的用户信息没加 —— 通过订单能看到别的租户的用户名和邮箱
聚合泄露 「全平台共 12345 个订单」这类统计忘了按租户过滤，泄露了商业信息
缓存串租户 缓存键是 order:1042 而不是 t:{tenantId}:order:1042 —— 下一章会详谈
越权提升 「修改成员信息」接口没排除 role 字段，普通成员把自己改成了 owner
邀请链接不失效 离职员工手里的旧邀请链接还能用；或者邀请链接没绑定邮箱，转发给谁谁就能进
文件没隔离 第 15 章的签名 URL 生成前没做归属检查 
// 修改成员信息：显式列出允许修改的字段，而不是排除不允许的
const updateMemberSchema = z.object({
  name: z.string().max(50).optional(),
  title: z.string().max(50).optional(),
  // 注意这里没有 role 和 tenantId —— 白名单而不是黑名单
})

app.patch('/app/members/:id', requirePermission('member:read'),
  zValidator('json', updateMemberSchema), async (c) => {
    const patch = c.req.valid('json')     // 多余的字段已被 Zod 剥掉
    // 改角色是另一个接口，需要另一个权限
    await c.get('db').updateMember(c.req.param('id'), patch)
    return c.json({ ok: true })
  })
★ 白名单，不是黑名单

delete patch.role 这种写法是黑名单 —— 将来加了 isSuperAdmin 字段， 没人会记得也去 delete 一下。
Zod schema 天然是白名单：没在 schema 里声明的字段直接消失。 这是第 8 章的校验器在安全上的额外收益。

给权限写测试

权限是少数「测试收益极高」的领域：规则明确、边界清晰，而且一旦出错后果严重。 

import { describe, it, expect, beforeEach } from 'vitest'

describe('订单接口的权限', () => {
  let tenantA: Tenant, tenantB: Tenant, orderA: Order

  beforeEach(async () => {
    await resetDb()
    tenantA = await createTenant('A 公司')
    tenantB = await createTenant('B 公司')
    orderA = await createOrder(tenantA, { total: 100 })
  })

  it('本租户成员能看到自己的订单', async () => {
    const res = await request(`/app/orders/${orderA.id}`, asMember(tenantA))
    expect(res.status).toBe(200)
  })

  it('其他租户看不到，且返回 404 而非 403', async () => {
    const res = await request(`/app/orders/${orderA.id}`, asMember(tenantB))
    expect(res.status).toBe(404)    // 不泄露「这个 ID 存在」
  })

  it('viewer 不能删除', async () => {
    const res = await request(`/app/orders/${orderA.id}`,
                              asRole(tenantA, 'viewer'), { method: 'DELETE' })
    expect(res.status).toBe(403)
    expect(await orderExists(orderA.id)).toBe(true)   // 确认真的没删
  })

  it('成员不能把自己提升为 owner', async () => {
    const me = await createMember(tenantA, 'member')
    await request(`/app/members/${me.id}`, asUser(me), {
      method: 'PATCH', json: { name: '新名字', role: 'owner' },
    })
    const after = await getMember(me.id)
    expect(after.role).toBe('member')      // 角色没被改掉
    expect(after.name).toBe('新名字')       // 但允许的字段改了
  })

  it('批量删除不能混入其他租户的 ID', async () => {
    const orderB = await createOrder(tenantB, { total: 200 })
    await request('/app/orders/batch-delete', asRole(tenantA, 'admin'), {
      method: 'POST', json: { ids: [orderA.id, orderB.id] },
    })
    expect(await orderExists(orderA.id)).toBe(false)
    expect(await orderExists(orderB.id)).toBe(true)    // B 的订单必须还在
  })
})
💡 建一张「权限矩阵」表格驱动测试

把「角色 × 操作 → 期望结果」列成一张表，然后用循环跑完所有组合。 这样新增角色或操作时，缺失的组合会立刻暴露出来。 

const MATRIX = [
  { role: 'owner',  action: 'delete', expect: 204 },
  { role: 'admin',  action: 'delete', expect: 204 },
  { role: 'member', action: 'delete', expect: 403 },
  { role: 'viewer', action: 'delete', expect: 403 },
  { role: 'viewer', action: 'read',   expect: 200 },
]

for (const { role, action, expect: code } of MATRIX) {
  it(`${role} 执行 ${action} 应返回 ${code}`, async () => {
    const res = await perform(action, asRole(tenantA, role))
    expect(res.status).toBe(code)
  })
}

审计日志

权限系统还需要回答一个事后问题：「这条数据是谁在什么时候改的？」 

export const auditLog = sqliteTable('audit_log', {
  id: text('id').primaryKey(),
  tenantId: text('tenant_id').notNull(),
  actorId: text('actor_id').notNull(),
  action: text('action').notNull(),           // 'order.delete'
  resourceType: text('resource_type').notNull(),
  resourceId: text('resource_id').notNull(),
  // 改了什么：只记变化的字段，别记全量（可能含敏感信息）
  changes: text('changes', { mode: 'json' }),
  ip: text('ip'),
  requestId: text('request_id'),               // 关联到第 29 章的日志
  createdAt: integer('created_at', { mode: 'timestamp' }).notNull(),
})
★ 审计日志和普通日志不是一回事
应用日志（第 29 章）审计日志
目的排查故障追责与合规
存在哪日志平台数据库，可查询、可导出
保留多久7–30 天数月到数年（可能有法规要求）
能否修改无所谓只能追加，不能改也不能删
谁看工程师客户、合规、法务

B2B 产品里，「谁改了这个配置」是客户会真实问出来的问题。 而且很多企业采购流程会直接要求你有这个功能。

自查清单

★ 逐条对照你的代码
  • ☐ 每个「按 ID 取资源」的接口，归属条件是写在查询里还是查完再判断？
  • ☐ 批量接口有没有逐个校验归属？
  • ☐ JOIN 出来的关联数据有没有一起过滤？
  • ☐ 统计和聚合接口有没有按租户过滤？
  • ☐ 更新接口用的是字段白名单吗？role、tenantId 能被改吗？
  • ☐ 定时任务、队列消费者走的是同一套数据访问层吗？
  • ☐ 文件下载（第 15 章）在签发 URL 前做了归属检查吗？
  • ☐ 缓存键包含租户标识吗？
  • ☐ 有没有至少一个「跨租户访问必须失败」的测试？
  • ☐ 越权尝试有记日志吗？
  • ☐ 成员离开团队后，他的会话、令牌、邀请链接都失效了吗？

小结

  • IDOR 是最常见的越权漏洞：检查了「登录了吗」却没检查「是你的吗」。
  • 把归属写进查询条件，让「查到了但不该给你」这个状态不存在。
  • 对不属于你的资源返回 404，避免泄露 ID 是否存在。
  • 多数 SaaS 用「共享表 + tenant_id」，所以隔离必须靠结构而非纪律： 租户作用域的数据访问层 + RLS + 类型，三层叠加。
  • 从 RBAC 开始；代码里判断权限而不是角色。
  • 路由层管「能不能做这类事」，数据层管「能不能碰这条数据」，两者正交。
  • 更新接口用字段白名单（Zod schema 天然如此）。
  • 权限一定要写测试，用权限矩阵驱动；越权尝试要记日志。
  • 审计日志是独立于应用日志的东西：进数据库、只追加、长期保留。

动手练习

  1. 在你的项目里找一个「按 ID 取资源」的接口，用另一个账号的登录态访问它。如果拿到了数据，你就找到了一个 IDOR。
  2. 实现 createTenantDb，把至少三个接口改成通过它访问。确认业务代码里再也拿不到未加租户条件的查询入口。
  3. 实现 can() 和 requirePermission()，把散落的 role === 'admin' 全部替换掉。
  4. 写一个跨租户测试：A 租户的用户访问 B 租户的资源，断言返回 404。让它跑在 CI 里（第 5 章）。
  5. 做一个「修改成员信息」接口，然后用 curl 在请求体里塞 "role": "owner"，确认它被忽略了。
  6. 给一张核心表加审计日志，改一条数据，然后从审计表里查出「谁在什么时候把什么改成了什么」。
  7. 对照自查清单过一遍你的项目。找到几处问题？
