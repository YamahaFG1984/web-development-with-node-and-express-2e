第 17 章

路由深入

路由是网站的目录结构，也是唯一会被用户收藏、被搜索引擎收录、被别人写进文章里的东西。 这一章先讲怎么设计 URL，再讲 Hono 的路由能力和它为什么这么快。

本章目标

  • 掌握 URL 设计的原则，写出十年后还能用的地址
  • 用好路径参数、通配符和正则约束
  • 用 app.route() 和 basePath() 把大应用拆成小模块
  • 理解 Hono 的多路由器机制，知道什么时候该换预设
  • 处理子域名路由

先想清楚 URL

网站管理员有责任分配那些两年后、二十年后、两百年后依然站得住的 URI。 这需要思考、组织和承诺。
—— Tim Berners-Lee，1998 年

这段话写于 1998 年，今天读依然成立。URL 改一次，所有收藏、外链、搜索排名全部作废。 下面这些原则值得在动手前花十分钟想一想：

💡 非改不可的时候，用 301

真的需要调整 URL 结构时，保留旧地址并 301 永久重定向到新地址。 搜索引擎会把权重转移过去，老书签也不会失效。留着这些重定向，别急着删。 

app.get('/old-vacations/:slug', (c) =>
  c.redirect(`/vacations/${c.req.param('slug')}`, 301)
)

路径模式

// 静态路径
app.get('/about', handler)

// 路径参数
app.get('/vacations/:slug', (c) => {
  const slug = c.req.param('slug')          // 'hood-river-day-trip'
})

// 多个参数
app.get('/contest/:year/:month', (c) => {
  const { year, month } = c.req.param()     // 一次拿全部
})

// 可选参数
app.get('/vacations/:region?', (c) => {
  const region = c.req.param('region')      // 可能是 undefined
})

// 正则约束：只匹配数字
app.get('/orders/:id{[0-9]+}', (c) => {
  const id = Number(c.req.param('id'))      // 保证能转成数字
})

// 约束版本号格式
app.get('/api/:version{v[0-9]+}/vacations', handler)

// 通配符
app.get('/files/*', (c) => {
  const path = c.req.path                   // '/files/a/b/c.png'
})

// 包含斜杠的参数
app.get('/files/:path{.+}', (c) => {
  const path = c.req.param('path')          // 'a/b/c.png'
})
★ 正则约束能省掉一堆校验

/orders/:id{[0-9]+} 意味着 /orders/abc 根本不会进你的处理函数， 而是走 404。你不用在函数里写 if (isNaN(id)) return 400。 让路由层挡掉明显非法的请求，处理函数就能只关心正常情况。

匹配顺序

// ❌ /vacations/new 会被第一条抢走，当成 slug='new'
app.get('/vacations/:slug', showVacation)
app.get('/vacations/new', newVacationForm)

// ✅ 具体的写前面
app.get('/vacations/new', newVacationForm)
app.get('/vacations/:slug', showVacation)

路由处理函数也是中间件

第 10 章说过：中间件和处理函数本质是一回事。 一个路由可以挂多个函数，只要不返回响应就继续往下走： 

app.get(
  '/admin/vacations/:sku',
  requireLogin,          // 中间件：没登录就重定向
  requireRole('admin'),  // 中间件：不是管理员就 403
  loadVacation,          // 中间件：查数据库，塞进 c
  (c) => c.html(<AdminVacationPage vacation={c.get('vacation')} />)
)

// loadVacation 长这样
const loadVacation = createMiddleware<{ Variables: { vacation: Vacation } }>(
  async (c, next) => {
    const v = await repo.findBySku(c.req.param('sku'))
    if (!v) return c.notFound()      // 拦截，后面不执行
    c.set('vacation', v)
    await next()
  }
)
💡 这是消除重复的好办法

如果有五个路由都要「按 sku 查出度假套餐，查不到就 404」， 把它写成中间件，五个处理函数就都能假设「c.get('vacation') 一定存在且有效」。

拆分大应用

所有路由堆在一个文件里，超过一两百行就没法看了。Hono 用 app.route() 组合子应用： 

import { Hono } from 'hono'

export const vacationRoutes = new Hono()
  .get('/', listVacations)                 // 实际路径 /vacations
  .get('/:slug', showVacation)             // 实际路径 /vacations/:slug
  .post('/:slug/notify', notifyWhenInSeason)

import { Hono } from 'hono'
import { cors } from 'hono/cors'

export const apiRoutes = new Hono()
  .use('*', cors())                        // 只对 API 生效
  .get('/vacations', apiListVacations)
  .get('/vacations/:sku', apiGetVacation)
  .delete('/vacations/:sku', apiDeleteVacation)

import { Hono } from 'hono'
import { vacationRoutes } from './routes/vacations'
import { apiRoutes } from './routes/api'
import { adminRoutes } from './routes/admin'

export const app = new Hono()

app.get('/', handlers.home)
app.get('/about', handlers.about)

app.route('/vacations', vacationRoutes)
app.route('/api/v1', apiRoutes)
app.route('/admin', adminRoutes)

basePath

// 给整个应用加前缀
const app = new Hono().basePath('/api/v2')

app.get('/vacations', handler)    // 实际是 /api/v2/vacations

为什么推荐链式写法

分开写：类型信息丢失
const api = new Hono()
api.get('/vacations', h1)
api.get('/vacations/:sku', h2)

export type AppType = typeof api
// AppType 里没有路由信息
// RPC 客户端用不了
链式写：类型一路累加
const api = new Hono()
  .get('/vacations', h1)
  .get('/vacations/:sku', h2)

export type AppType = typeof api
// AppType 包含全部路由的
// 路径、参数和返回值类型

这个差别在第 18 章（RPC 客户端）和第 5 章（testClient）时会变得非常重要。 养成链式写的习惯，将来想用这些特性时不用回头重构。

子域名

子域名适合承载「和主站关系不大」的部分：api.example.com、admin.example.com。 Hono 的路由默认不看域名，需要自己判断： 

const mainApp = new Hono()
const adminApp = new Hono()
const apiApp = new Hono()

const root = new Hono()

root.all('*', async (c) => {
  const host = c.req.header('host') ?? ''

  if (host.startsWith('admin.')) return adminApp.fetch(c.req.raw, c.env)
  if (host.startsWith('api.'))   return apiApp.fetch(c.req.raw, c.env)
  return mainApp.fetch(c.req.raw, c.env)
})

export default root
ⓘ 本地怎么测子域名

改 hosts 文件（macOS/Linux 是 /etc/hosts，Windows 是 C:\Windows\System32\drivers\etc\hosts）： 

127.0.0.1  meadowlark.local
127.0.0.1  admin.meadowlark.local
127.0.0.1  api.meadowlark.local

用 .local 后缀，避免和真实域名冲突。

⚠ 子域名对 SEO 不利

搜索引擎倾向于把子域名当作独立站点，权重不共享。 所以博客放 example.com/blog 比 blog.example.com 好。 子域名留给 API、后台这些不需要 SEO 的部分。

Hono 为什么快

Hono 有个别的框架没有的设计：它内置了多个路由器实现，启动时自动选一个。

预设

大多数人不需要改。但如果你的场景特殊，可以换预设：

引入方式用的路由器适合
import { Hono } from 'hono' SmartRouter [RegExp + Trie] 默认，绝大多数情况。长驻服务器，注册一次跑很久
import { Hono } from 'hono/quick' SmartRouter [Linear + Trie] 每个请求都要重新注册路由的环境（某些 FaaS）。注册极快，匹配稍慢
import { Hono } from 'hono/tiny' PatternRouter 对体积极度敏感的场景。代码最小，性能够用
💡 怎么判断该不该换

默认预设的取舍是：启动时多花一点时间做编译，换取之后每个请求都快。 这在服务器上是划算的（编译一次，服务几百万个请求）。 只有当「进程存活时间极短、每次只处理一两个请求」时，hono/quick 才更划算。 不确定就别改。

小结

  • URL 是长期承诺。全小写、连字符分词、不暴露技术细节、层级反映结构。
  • 路径参数支持正则约束，用它把非法请求挡在处理函数之外。
  • 具体路由写在通配路由前面。
  • 用 app.route() 拆分子应用，用链式写法保住类型信息。
  • 子域名要自己判断 host；子域名对 SEO 不友好，留给 API 和后台。
  • Hono 的多路由器机制默认就是最优解，不确定就别换预设。
