第 11 章

发送邮件

注册确认、密码重置、订单通知 —— 邮件是应用和用户之间最重要的异步通道。 这一章讲怎么把邮件发出去，怎么让它不进垃圾箱，以及为什么边缘环境要换一种发法。

本章目标

  • 搞懂 SMTP、MSA、MTA 分别是什么
  • 知道为什么边缘运行时要用 HTTP API 而不是 SMTP
  • 用 JSX 渲染邮件模板，同时生成 HTML 和纯文本两个版本
  • 把发信能力封装成一个可替换、可测试的服务
  • 了解发信送达率的基本功：SPF、DKIM、退订

邮件是怎么送到的

缩写全称干什么
SMTPSimple Mail Transfer Protocol发邮件用的协议，跑在 25 / 465 / 587 端口
MSAMail Submission Agent你把邮件交给它，它负责可靠地送出去。处理重试、退信、信誉
MTAMail Transfer Agent在服务器之间转发邮件的中转站
★ 不要自己搭邮件服务器

技术上你可以在自己的服务器上跑一个 SMTP 服务直接发信。实践中这是个坑： 新 IP 没有发信信誉，主流邮箱会把你的邮件全部判为垃圾邮件；反向 DNS、SPF、DKIM、DMARC 任何一项配错都会导致投递失败；还要处理退信、投诉、黑名单申诉。 用现成的邮件服务（Resend、SendGrid、Mailgun、AWS SES），免费额度足够学习和小项目。

「这个库在 Workers 上能不能用」，判断标准就是：它有没有用到 Node.js 独有的能力 —— 原始 socket、文件系统、子进程、原生扩展。用到了就不行。 这个思路在选数据库客户端（第 13 章）时同样适用。

发出第一封邮件

以 Resend 为例（其他服务大同小异）：注册账号， 验证一个域名，拿到 API Key，放进环境变量。 

RESEND_API_KEY=re_xxxxxxxxxxxxxxxxxxxx
MAIL_FROM="云雀旅行 <info@meadowlarktravel.com>"

export type Mail = {
  to: string | string[]
  subject: string
  html: string
  text: string
  replyTo?: string
}

export interface Mailer {
  send(mail: Mail): Promise<{ id: string }>
}

export function createResendMailer(apiKey: string, from: string): Mailer {
  return {
    async send(mail) {
      const res = await fetch('https://api.resend.com/emails', {
        method: 'POST',
        headers: {
          Authorization: `Bearer ${apiKey}`,
          'Content-Type': 'application/json',
        },
        body: JSON.stringify({
          from,
          to: Array.isArray(mail.to) ? mail.to : [mail.to],
          subject: mail.subject,
          html: mail.html,
          text: mail.text,
          reply_to: mail.replyTo,
        }),
      })

      if (!res.ok) {
        const detail = await res.text()
        throw new Error(`发信失败（${res.status}）：${detail}`)
      }

      return (await res.json()) as { id: string }
    },
  }
}

/** 开发环境用：只打印，不真发 */
export function createConsoleMailer(): Mailer {
  return {
    async send(mail) {
      console.log('─── 假装发了一封邮件 ───')
      console.log('收件人：', mail.to)
      console.log('主题：', mail.subject)
      console.log(mail.text)
      return { id: 'dev-' + crypto.randomUUID() }
    },
  }
}
★ 为什么要定义 Mailer 接口

定义接口的成本是十行代码，收益有三个：开发时不用真发邮件（用 console 版本， 也不会误发给真实用户）；测试时可以断言「发了几封、发给谁」； 将来换服务商只改一个文件。这是第 4 章「依赖只朝下」原则的具体应用。

邮件的头和格式

一封邮件和一个 HTTP 请求结构很像：有头，有正文。

头说明
From发件人。可以随便填 —— 这就是伪造发件人的原理，也是 SPF/DKIM 要解决的问题
To / Cc / Bcc收件人。群发一定要用 Bcc，否则每个人都能看到全部收件人邮箱
Reply-To用户点「回复」时发到哪。适合 no-reply 发信但希望回复到客服邮箱的场景
Subject主题。写清楚具体内容，别写「通知」
List-Unsubscribe让邮件客户端显示一键退订按钮。营销邮件必须有

永远同时发 HTML 和纯文本

邮件可以携带两个版本的正文，客户端自己选一个显示。为什么要费这个事：

  • 部分用户和部分客户端只显示纯文本。
  • 只有 HTML 没有纯文本的邮件，更容易被判为垃圾邮件。
  • 屏幕阅读器和搜索索引更喜欢纯文本。

用 JSX 写邮件模板

好消息：第 7 章学的 JSX 直接能用来渲染邮件。 坏消息：邮件里的 HTML 要按 2005 年的标准写。

⚠ 邮件客户端的 HTML 支持有多差
  • 没有 flexbox，没有 grid。布局要用 <table>。
  • 外部样式表基本无效，<style> 块部分客户端会剥掉。样式要写成行内 style 属性。
  • 不能有 <script>（会被直接删掉，而且很可疑）。
  • 背景图、圆角、阴影支持参差不齐。
  • Outlook 用 Word 的引擎渲染 HTML，是最难伺候的那个。

渲染成字符串

c.html() 是给 HTTP 响应用的。发邮件时我们需要的是字符串， 用 Hono 提供的 renderToString： 

// hono/jsx/dom/server 提供了把 JSX 渲染成字符串的能力
import { renderToString } from 'hono/jsx/dom/server'

export function renderEmail(element: unknown): string {
  return '<!doctype html>' + renderToString(element as never)
}

/** 从 HTML 生成一个够用的纯文本版本 */
export function htmlToText(html: string): string {
  return html
    .replace(/<style[\s\S]*?<\/style>/gi, '')
    .replace(/<br\s*\/?>/gi, '\n')
    .replace(/<\/(p|div|tr|h[1-6])>/gi, '\n')
    .replace(/<[^>]+>/g, '')
    .replace(/&nbsp;/g, ' ')
    .replace(/\n{3,}/g, '\n\n')
    .trim()
}
ⓘ 自动转换的纯文本只是「够用」

上面这个函数能应付通知类邮件。但对于重要的邮件（欢迎信、营销邮件）， 手写一版纯文本效果好得多 —— 自动转换出来的东西往往断行奇怪、链接丢失。 做法是让邮件模块同时导出 Html 组件和 text 函数。

串起来

import { OrderConfirmationEmail } from '../views/emails/order-confirmation'
import { renderEmail, htmlToText } from '../lib/render-email'

export const checkout = async (c: Context) => {
  const cart = c.get('session').cart
  const { name, email } = c.req.valid('form')

  const order = await db.createOrder({ cart, name, email })

  const html = renderEmail(
    <OrderConfirmationEmail
      customerName={name}
      orderNumber={order.number}
      items={order.items}
      total={order.total}
    />
  )

  try {
    await mailer.send({
      to: email,
      subject: `预订确认 · 订单 ${order.number}`,
      html,
      text: htmlToText(html),
      replyTo: 'support@meadowlarktravel.com',
    })
  } catch (err) {
    // 关键：发信失败不能让下单失败
    console.error('确认邮件发送失败', err)
  }

  return c.redirect(`/orders/${order.number}`, 303)
}
★ 发信失败不该阻断主流程

订单已经落库了，邮件没发出去是个次要问题。如果这里不 catch，用户会看到 500 错误页， 以为下单失败又下了一单。
更好的做法：把发信丢进队列异步处理。在 Cloudflare Workers 上可以用 c.executionCtx.waitUntil(promise) —— 响应立即返回，发信在后台继续。 

// Workers 上的写法：不阻塞响应
c.executionCtx.waitUntil(
  mailer.send({ ... }).catch((err) => console.error(err))
)
return c.redirect(`/orders/${order.number}`, 303)

群发和送达率

⚠ 不要用发通知邮件的方式发营销邮件

「给一万个订阅者发本周特惠」看起来只是循环调用发信接口，实际上你需要： 退订链接和退订状态管理、发送频率控制、退信处理、打开率统计、 分批避开服务商限额、以及各地的反垃圾邮件法规合规。 这种事交给 Mailchimp、Sendy 这类专门的营销邮件平台。 你的应用只负责发「事务性邮件」：注册确认、密码重置、订单通知。

让邮件不进垃圾箱的三件事

📧

SPF

在域名的 DNS 里声明「哪些服务器可以用我的域名发信」。邮件服务商会给你一条 TXT 记录，加上就行。

🔑

DKIM

给邮件加数字签名，收件方用你 DNS 里的公钥验证。同样是加一条 DNS 记录。

📜

DMARC

告诉收件方「SPF 或 DKIM 没通过时该怎么办」，并接收报告。

这三条 DNS 记录是发信的基本功。配好之后再注意：

  • 发件域名用你自己的域名，不要用 gmail.com 这种（会直接被 DMARC 拦下）。
  • 主题别写「免费」「限时」「点击这里」这类高风险词。
  • HTML 和纯文本都要有。
  • 图片要有 alt，而且不要整封信只有一张大图。
  • 提供真实的退订方式，并且真的执行退订。

💡 开发时看真实效果

想看邮件在真实客户端里长什么样，但又不想发给真人：用 Mailtrap 或 Mailpit 这类「邮件沙盒」—— 所有邮件都被拦在一个测试收件箱里，你能看到渲染结果，但它永远不会真的送出去。

小结

  • 用邮件服务商（MSA），不要自己搭 SMTP 服务器。
  • 边缘运行时不能开 TCP，所以用 HTTP API 而不是 Nodemailer。
  • 把发信封装成 Mailer 接口，开发用假实现，测试用 mock。
  • 邮件 HTML 要用表格布局 + 行内样式；HTML 和纯文本都要发。
  • 发信失败不能阻断主业务流程；能异步就异步。
  • SPF、DKIM、DMARC 三条 DNS 记录是送达率的地基。
