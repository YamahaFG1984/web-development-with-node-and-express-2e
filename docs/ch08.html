第 8 章

表单处理

到目前为止数据都是从服务器流向浏览器。现在反过来：用户填的东西怎么回到服务器？ 这一章讲三种编码格式、两种提交方式、一个必须做的校验，以及文件上传。

本章目标

  • 分清 urlencoded、json、multipart 三种请求体格式
  • 用 c.req.parseBody() 处理传统表单提交
  • 知道为什么表单提交后要用 303 重定向
  • 用 fetch 提交表单，不刷新页面
  • 用 Zod 做服务端校验，并把错误友好地显示出来
  • 接收文件上传并安全地保存

数据回传的两条路

⚠ 常见误解：POST 比 GET 安全

不对。两者都在同一个 HTTP 连接里传输。只有 HTTPS 才提供安全性； 没有 HTTPS 的话，POST 请求体和 GET 查询串一样是明文，中间人都能看到。 POST 的好处只是「不会出现在地址栏、浏览历史和服务器访问日志里」，这是隐私，不是加密。

HTML 表单

<form action="/newsletter/signup" method="POST">
  <input type="hidden" name="source" value="homepage">

  <label for="f-name">姓名</label>
  <input type="text" id="f-name" name="name" required>

  <label for="f-email">邮箱</label>
  <input type="email" id="f-email" name="email" required>

  <button type="submit">订阅</button>
</form>
属性作用
action提交到哪个 URL。省略则提交到当前地址
method默认是 GET，要 POST 必须显式写
name服务器靠它认字段。没有 name 的输入框不会被提交
id只给 <label for> 和 CSS/JS 用，不会传给服务器
⚠ hidden 字段不是秘密

type="hidden" 只是「不显示给用户」，任何人查看源代码或用开发者工具都能看到和修改它。 永远不要在里面放价格、用户角色、权限这类服务器需要信任的数据。 它适合放「这个表单来自哪个页面」这种无害的上下文信息。

三种编码格式

Content-Type长什么样什么时候用
application/x-www-form-urlencoded name=%E5%BC%A0&email=a%40b.com 普通表单的默认格式。和查询串一样的编码
multipart/form-data 用分隔符切开的多段数据，每段有自己的头 表单里有 <input type="file"> 时必须用
application/json {"name":"张","email":"a@b.com"} 用 fetch 提交时最常用

在 Hono 里接收表单

export const signupProcess = async (c: Context) => {
  // parseBody 同时支持 urlencoded 和 multipart
  const body = await c.req.parseBody()

  const name = String(body.name ?? '')
  const email = String(body.email ?? '')

  console.log(`新订阅：${name} <${email}>`)

  return c.redirect('/newsletter/thank-you', 303)
}

app.get('/newsletter', handlers.signupForm)
app.post('/newsletter/signup', handlers.signupProcess)
app.get('/newsletter/thank-you', handlers.signupThankYou)

parseBody 的几个选项

// 默认：同名字段只保留最后一个
const body = await c.req.parseBody()

// all: true —— 同名字段收集成数组（多选框、多文件）
const body = await c.req.parseBody({ all: true })
// <input name="tag" value="海岸"> <input name="tag" value="帆船">
// => body.tag 是 ['海岸', '帆船']

// dot: true —— 把 a.b 形式的字段名还原成嵌套对象
const body = await c.req.parseBody({ dot: true })
// <input name="contact.email">
// => body.contact.email

如果客户端发的是 JSON，用 c.req.json()：

const data = await c.req.json<{ name: string; email: string }>()

用 fetch 提交：不刷新页面

现代做法是拦截表单提交，自己用 fetch 发请求：

export const NewsletterPage: FC = () => (
  <Layout title="订阅通讯">
    <div id="signup-container">
      <form id="signup-form">
        <label for="f-name">姓名</label>
        <input type="text" id="f-name" name="name" required />

        <label for="f-email">邮箱</label>
        <input type="email" id="f-email" name="email" required />

        <button type="submit">订阅</button>
      </form>
    </div>

    <script src="/js/newsletter.js" defer></script>
  </Layout>
)

document.getElementById('signup-form').addEventListener('submit', async (evt) => {
  evt.preventDefault()   // 阻止浏览器自己提交

  const form = evt.target
  const container = document.getElementById('signup-container')

  try {
    const res = await fetch('/api/newsletter/signup', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        name: form.elements.name.value,
        email: form.elements.email.value,
      }),
    })

    if (!res.ok) throw new Error(`请求失败，状态码 ${res.status}`)

    await res.json()
    container.innerHTML = '<p><b>订阅成功，感谢！</b></p>'
  } catch (err) {
    container.innerHTML =
      '<p>抱歉，订阅时出了点问题，请<a href="/newsletter">重试</a>。</p>'
  }
})

app.post('/api/newsletter/signup', async (c) => {
  const { name, email } = await c.req.json<{ name: string; email: string }>()
  console.log(`新订阅：${name} <${email}>`)
  return c.json({ ok: true })
})
💡 用 /api/ 前缀区分两类端点

给浏览器直接访问的路由返回 HTML 或重定向；给 fetch 调用的路由返回 JSON。 用路径前缀把它们分开，将来加 CORS、限流、鉴权时可以整组处理（app.use('/api/*', ...)）。

校验：绝对不能省

HTML 的 required 和 type="email" 只是用户体验，不是安全措施。 攻击者用 curl 直接发请求，完全绕过浏览器。服务端必须重新校验一遍。

手写 if 很快会失控。用 Zod 描述「合法数据长什么样」：

npm install zod @hono/zod-validator

import { z } from 'zod'
import { zValidator } from '@hono/zod-validator'

const signupSchema = z.object({
  name: z.string().min(1, '请填写姓名').max(50, '姓名太长了'),
  email: z.string().email('邮箱格式不正确'),
  source: z.string().optional(),
})

app.post(
  '/api/newsletter/signup',
  zValidator('json', signupSchema),   // ← 校验中间件
  async (c) => {
    // 能走到这里，说明数据一定合法，而且类型是推导出来的
    const { name, email } = c.req.valid('json')
    await db.addSubscriber({ name, email })
    return c.json({ ok: true })
  }
)

zValidator 的第一个参数是数据来源，可以是 'json'、'form'、 'query'、'param'、'header'、'cookie'。

自定义错误响应

默认的 400 JSON 对 API 够用，但传统表单需要把错误显示回页面上：

app.post(
  '/newsletter/signup',
  zValidator('form', signupSchema, (result, c) => {
    if (!result.success) {
      // 把 Zod 的错误整理成 { 字段名: 错误信息 }
      const errors: Record<string, string> = {}
      for (const issue of result.error.issues) {
        errors[String(issue.path[0])] = issue.message
      }
      // 重新渲染表单，带上错误和用户已填的内容
      return c.html(<NewsletterForm errors={errors} values={result.data} />, 422)
    }
  }),
  async (c) => {
    const { name, email } = c.req.valid('form')
    await db.addSubscriber({ name, email })
    return c.redirect('/newsletter/thank-you', 303)
  }
)
★ 出错时一定要回填用户填过的内容

最让人恼火的表单体验是：填了十个字段，因为邮箱格式错了，回来发现全空了。 把 values 传回视图，用 value={values.name} 回填。 这是几行代码的事，但用户会记住。

文件上传

表单必须加 enctype：

<form
  method="POST"
  action="/contest/vacation-photo"
  enctype="multipart/form-data"
>
  <label for="f-email">邮箱</label>
  <input type="email" id="f-email" name="email" required />

  <label for="f-photo">度假照片</label>
  <input type="file" id="f-photo" name="photo" accept="image/*" required />

  <button type="submit">提交</button>
</form>

服务端 parseBody() 会把文件字段解析成标准的 File 对象： 

import { writeFile, mkdir } from 'node:fs/promises'
import { join, extname } from 'node:path'
import { randomUUID } from 'node:crypto'

const UPLOAD_DIR = './data/vacation-photos'
const MAX_SIZE = 5 * 1024 * 1024                      // 5 MB
const ALLOWED = new Set(['image/jpeg', 'image/png', 'image/webp'])

export const photoContest = async (c: Context) => {
  const body = await c.req.parseBody()
  const email = String(body.email ?? '')
  const photo = body.photo

  // ① 确认它真的是个文件
  if (!(photo instanceof File)) {
    return c.json({ error: '请选择一张照片' }, 400)
  }

  // ② 限制大小
  if (photo.size > MAX_SIZE) {
    return c.json({ error: '照片不能超过 5 MB' }, 413)
  }

  // ③ 限制类型
  if (!ALLOWED.has(photo.type)) {
    return c.json({ error: '只接受 JPEG / PNG / WebP 格式' }, 415)
  }

  // ④ 自己生成文件名，绝不使用用户提供的名字
  const ext = extname(photo.name).toLowerCase().slice(0, 6)
  const safeName = `${randomUUID()}${/^\.[a-z0-9]+$/.test(ext) ? ext : '.bin'}`

  await mkdir(UPLOAD_DIR, { recursive: true })
  const buffer = Buffer.from(await photo.arrayBuffer())
  await writeFile(join(UPLOAD_DIR, safeName), buffer)

  await db.saveContestEntry({ email, photoPath: safeName })

  return c.redirect('/contest/thank-you', 303)
}
⚠ 上传是攻击面最大的功能之一
  • 永远不要用用户给的文件名。它可能是 ../../etc/passwd，也可能是 shell.php。自己生成随机名，只保留经过白名单校验的扩展名。
  • 限制大小，否则一个几 GB 的上传就能撑爆你的磁盘或内存。
  • 不要相信 photo.type。它来自客户端，可以伪造。真正严格的做法是读文件头几个字节 判断真实类型（叫 magic number 检测）。
  • 上传目录不要放在能被当作代码执行的地方，也不要直接用 serveStatic 暴露出去。

Hono 还提供了一个中间件，在解析请求体之前就把超大请求挡掉：

import { bodyLimit } from 'hono/body-limit'

app.post(
  '/contest/vacation-photo',
  bodyLimit({
    maxSize: 5 * 1024 * 1024,
    onError: (c) => c.text('文件太大了', 413),
  }),
  handlers.photoContest
)
ⓘ 边缘环境没有文件系统

上面的 writeFile 在 Cloudflare Workers 上是跑不通的 —— 那里没有可写磁盘， 而且就算有，多个边缘节点之间也不共享。正确做法是传到对象存储（R2 / S3）。 第 13 章会讲这个。写代码时最好一开始就把「存文件」抽成一个函数，将来换实现只改一处。

用 fetch 上传文件

好消息：几乎不用改服务端代码，因为编码格式完全一样。

document.getElementById('photo-form').addEventListener('submit', async (evt) => {
  evt.preventDefault()

  // FormData 直接从 form 元素构造，浏览器自动设置正确的 Content-Type 和 boundary
  const body = new FormData(evt.target)

  const res = await fetch('/api/contest/vacation-photo', { method: 'POST', body })
  const json = await res.json()
  // ...更新界面
})
💡 别手动设 Content-Type

用 FormData 时不要自己写 headers: { 'Content-Type': 'multipart/form-data' }。 multipart 需要一个随机 boundary 分隔符，只有浏览器知道它是什么。你手动设了反而会破坏请求。

小结

  • 查询 用 GET + 查询串；提交 用 POST + 请求体。POST 不等于安全，HTTPS 才是。
  • 三种编码：urlencoded（普通表单）、multipart（带文件）、json（fetch）。
  • c.req.parseBody() 处理前两种，c.req.json() 处理第三种。
  • 表单提交后用 303 重定向，避免刷新重复提交。（它只能缓解，挡不住双击和客户端重试 —— 彻底的解法是第 20 章的幂等键。）
  • 前端校验是体验，服务端校验是必须。用 Zod + zValidator。
  • 文件上传要限大小、限类型、自己生成文件名，永远不信任客户端。

动手练习

  1. 做一个 /contact 联系表单，用 Zod 校验姓名、邮箱和留言（留言至少 10 个字）。校验失败时重新渲染表单，显示错误并回填已填内容。
  2. 用 curl -X POST -d "name=&email=notanemail" http://localhost:3000/newsletter/signup -i 绕过浏览器提交，确认服务端拦住了它。
  3. 给上传接口加上大小和类型限制，然后试着上传一个 .txt 文件（把它改名成 .jpg），看看你的校验有没有被骗过去。
  4. 把「保存文件」抽成 saveUpload(name, bytes): Promise<string> 这样一个函数，让处理函数不知道文件到底存在哪。
