第 22 章

后台任务与队列

第 11 章发邮件时，用户要一直等着邮件发完才能看到「下单成功」。 这一章讲一个能改变你系统架构的思路：请求路径上只做必须立刻做的事，其余的丢到后面去。

本章目标

  • 判断哪些操作该移出请求路径
  • 掌握三种「延后执行」的手段及各自的可靠性边界
  • 理解「至少一次投递」意味着什么，以及它为什么强制要求消费者幂等
  • 用 Cloudflare Queues 和 BullMQ 各实现一遍
  • 设计重试、退避与死信队列
  • 知道什么时候不该用队列

请求路径上的时间预算

回顾第 11 章那个下单接口，把每一步的耗时列出来：

怎么判断该不该移出去

问一个问题：「用户看到响应时，这件事必须已经完成吗？」

必须同步做可以异步做
校验输入（不合法就不该继续）发确认邮件 / 短信
写入核心业务数据（订单、支付记录）生成 PDF / 发票 / 报表
扣减库存（涉及正确性，见第 21 章）压缩、裁剪、转码上传的图片视频
返回用户马上要看的数据同步数据到 CRM / 数据仓库 / 搜索引擎
权限判断推送通知、发 webhook 给第三方
写审计日志、统计埋点
调用 AI 生成摘要、翻译、推荐
★ 一个额外的好处：故障隔离

同步架构下，邮件服务挂了 → 下单接口报 500 → 用户下不了单，公司损失收入。
异步架构下，邮件服务挂了 → 任务在队列里堆着 → 下单照常 → 服务恢复后邮件自动补发。
队列把「外部依赖的可用性」和「核心业务的可用性」解耦开了。这往往比性能提升更值钱。

三种延后执行的手段

① waitUntil：最轻量的那个

app.post('/api/v1/orders', async (c) => {
  const order = await createOrder(...)

  // 响应立刻返回，但运行时会等这个 Promise 结束才回收执行环境
  c.executionCtx.waitUntil(
    recordAnalytics({ event: 'order_created', orderId: order.id })
      .catch((err) => console.error('埋点失败', err))   // ← 必须自己 catch
  )

  return c.json({ orderId: order.id }, 201)
})
⚠ waitUntil 的三个限制
  1. 没有重试。失败就是失败了，没有任何人会再试一次。
  2. 没有持久化。进程/实例在任务跑完前被回收，任务直接消失，不留痕迹。
  3. 受执行时间上限约束。边缘平台对单次调用的 CPU 时间和墙钟时间都有限制。

所以它只适合「做成了最好，没做成也不影响正确性」的事。 发确认邮件用它是不合适的 —— 用户没收到邮件是个真问题。

ⓘ Node.js 上没有 waitUntil

c.executionCtx 是 Workers 等边缘运行时提供的。在 Node 上， 进程是长驻的，你直接 promise.catch(...) 不 await 就行 —— 但同样没有重试和持久化保证，而且要小心第 12 章讲的「未处理的 Promise 拒绝」。

队列的心智模型

「至少一次投递」是什么意思

绝大多数队列（SQS、Cloudflare Queues、RabbitMQ 默认配置、BullMQ）提供的是 at-least-once 保证：任务至少会被投递一次，但可能投递多次。 

消费者收到任务 → 处理成功 → 准备发送 ack → 此时网络断了 / 进程崩了
                                          ↓
                          队列没收到 ack，认为处理失败
                                          ↓
                                    重新投递这个任务
                                          ↓
                              同一个任务被处理了第二次
★ 这个推论极其重要

至少一次投递 ⇒ 你的任务处理逻辑必须是幂等的。
这不是「最好做一下」，而是「不做就一定会出事」—— 只是时间问题。
第 21 章讲的幂等技巧在这里全部适用，而且这次是强制的。

❌ 非幂等的任务
async function handle(task) {
  await mailer.send({
    to: task.email,
    subject: '订单确认',
  })
  await db.update(accounts)
    .set({ points: sql`points + 100` })
    .where(eq(accounts.id, task.userId))
}
// 重投一次 = 用户收到两封邮件
//            + 多得 100 积分
✅ 幂等的任务
async function handle(task) {
  // 用任务自带的唯一 id 做去重
  const claimed = await claimOnce(task.id)
  if (!claimed) return          // 处理过了，直接结束

  await mailer.send({
    to: task.email,
    subject: '订单确认',
    // 很多邮件服务也支持幂等键
    idempotencyKey: task.id,
  })
  await db.update(accounts)
    .set({ points: sql`points + 100` })
    .where(eq(accounts.id, task.userId))
}

/** 用一张表 + 唯一约束实现「只处理一次」*/
async function claimOnce(taskId: string): Promise<boolean> {
  try {
    await db.insert(processedTasks).values({ id: taskId, at: new Date() })
    return true            // 插入成功 = 我是第一个
  } catch (err) {
    if (isUniqueViolation(err)) return false   // 已经有人处理过了
    throw err
  }
}
⚠ 更严谨的做法：先做事，再标记，同一个事务

上面这个写法有个窄窗口：标记成功后、业务执行前崩溃，任务会被跳过（变成「至多一次」）。 如果业务本身在数据库里，把标记和业务放进同一个事务就能彻底解决 —— 和第 21 章的幂等键写法完全一样。
如果业务是外部调用（发邮件），就没法用事务，此时优先让外部服务承担去重 （传幂等键给它），这是最可靠的。

定义任务类型

export type Task =
  | { type: 'send-order-email'; id: string; orderId: string; email: string }
  | { type: 'generate-invoice'; id: string; orderId: string }
  | { type: 'sync-to-crm'; id: string; customerId: string }

export function newTask<T extends Task['type']>(
  type: T,
  payload: Omit<Extract<Task, { type: T }>, 'type' | 'id'>
): Task {
  return { type, id: crypto.randomUUID(), ...payload } as Task
}
💡 任务里放 ID，不放数据

投递 { orderId: 'o_123' }，而不是把整个订单对象塞进去。原因：
① 消息体有大小限制；
② 任务可能几分钟后才执行，那时数据可能已经变了 —— 你要的是最新数据，不是投递时的快照；
③ 消息可能被日志记录下来，里面别带敏感信息。

生产者

type Bindings = { TASKS: Queue<Task>; DB: D1Database }

app.post('/api/v1/orders', async (c) => {
  const order = await createOrder(...)     // 同步：必须完成

  // 异步：投递即返回，10 ms 左右
  await c.env.TASKS.send(
    newTask('send-order-email', { orderId: order.id, email: order.email })
  )

  // 批量投递更省事
  await c.env.TASKS.sendBatch([
    { body: newTask('generate-invoice', { orderId: order.id }) },
    { body: newTask('sync-to-crm', { customerId: order.customerId }) },
  ])

  return c.json({ orderId: order.id }, 201)
})

消费者

import { app } from './app'
import { handleTask } from './tasks/handlers'

export default {
  // HTTP 请求走 Hono
  fetch: app.fetch,

  // 队列消息走这里
  async queue(batch: MessageBatch<Task>, env: Bindings) {
    for (const msg of batch.messages) {
      try {
        await handleTask(msg.body, env)
        msg.ack()                      // 明确确认：处理成功
      } catch (err) {
        console.error('任务失败', {
          taskId: msg.body.id,
          type: msg.body.type,
          attempt: msg.attempts,
          error: String(err),
        })
        // 指数退避后重投；不调 retry 而是让它超时也可以，但显式更清楚
        msg.retry({ delaySeconds: Math.min(2 ** msg.attempts * 10, 900) })
      }
    }
  },
}

export async function handleTask(task: Task, env: Bindings) {
  switch (task.type) {
    case 'send-order-email':
      return sendOrderEmail(task, env)
    case 'generate-invoice':
      return generateInvoice(task, env)
    case 'sync-to-crm':
      return syncToCrm(task, env)
    default: {
      // 穷尽检查：将来加了新任务类型忘了处理，这里会编译报错
      const never: never = task
      throw new Error(`未知任务类型：${JSON.stringify(never)}`)
    }
  }
}

async function sendOrderEmail(
  task: Extract<Task, { type: 'send-order-email' }>,
  env: Bindings
) {
  // ① 幂等
  if (!(await claimOnce(task.id, env))) return

  // ② 取最新数据，而不是用投递时的快照
  const order = await getOrder(env.DB, task.orderId)
  if (!order) return          // 订单被删了，任务作废，不是错误

  // ③ 干活
  const html = renderEmail(<OrderConfirmationEmail order={order} />)
  await createMailer(env).send({
    to: task.email,
    subject: `预订确认 · ${order.number}`,
    html,
    text: htmlToText(html),
  })
}

实现：Node.js 上用 BullMQ

如果你部署在传统服务器上，BullMQ（基于 Redis）是最成熟的选择：

npm install bullmq ioredis

import { Queue } from 'bullmq'
import IORedis from 'ioredis'

const connection = new IORedis(process.env.REDIS_URL!, {
  maxRetriesPerRequest: null,        // BullMQ 要求
})

export const taskQueue = new Queue<Task>('meadowlark-tasks', {
  connection,
  defaultJobOptions: {
    attempts: 5,
    backoff: { type: 'exponential', delay: 2000 },
    removeOnComplete: { age: 3600, count: 1000 },   // 别让 Redis 无限增长
    removeOnFail: { age: 7 * 24 * 3600 },           // 失败的多留几天用于排查
  },
})

import { Worker } from 'bullmq'
import { handleTask } from './handlers'

// 注意：这是一个独立的进程，和 Web 服务分开部署
const worker = new Worker<Task>(
  'meadowlark-tasks',
  async (job) => {
    await handleTask(job.data)
  },
  { connection, concurrency: 5 }     // 同时处理 5 个任务
)

worker.on('failed', (job, err) => {
  console.error('任务失败', { id: job?.id, attempts: job?.attemptsMade, err: err.message })
  if (job && job.attemptsMade >= (job.opts.attempts ?? 1)) {
    reportToSentry(err, { taskId: job.id, data: job.data })   // 彻底失败了才告警
  }
})

// 优雅关闭：让正在处理的任务做完
for (const sig of ['SIGTERM', 'SIGINT'] as const) {
  process.on(sig, async () => {
    await worker.close()
    process.exit(0)
  })
}
ⓘ Worker 是独立进程

别把 Worker 塞进 Web 服务的同一个进程里。分开的好处： 可以独立扩容（Web 开 2 个实例，Worker 开 10 个）、 重任务不会抢占 Web 的 CPU、Worker 崩了不影响用户访问。
部署上就是两条命令：node dist/server.js 和 node dist/worker.js。

重试、退避与死信队列

区分两种失败

class PermanentTaskError extends Error {}     // 重试也没用

async function sendOrderEmail(task: Task, env: Bindings) {
  const order = await getOrder(env.DB, task.orderId)

  // 订单不存在 —— 重试一万次也不会存在。直接放弃，不算失败
  if (!order) {
    console.warn('订单已不存在，跳过任务', task.orderId)
    return
  }

  // 邮箱格式非法 —— 永久错误，重试无意义
  if (!isValidEmail(task.email)) {
    throw new PermanentTaskError(`邮箱格式非法：${task.email}`)
  }

  // 邮件服务 503 —— 临时故障，值得重试
  await mailer.send({ ... })    // 抛普通 Error
}

// 在消费者里区别对待
try {
  await handleTask(msg.body, env)
  msg.ack()
} catch (err) {
  if (err instanceof PermanentTaskError) {
    console.error('永久失败，不重试', { taskId: msg.body.id, err: err.message })
    reportToSentry(err, { task: msg.body })
    msg.ack()          // ← 确认掉，别让它一直重试浪费资源
    continue
  }
  msg.retry({ delaySeconds: backoff(msg.attempts) })
}
⚠ 「毒丸消息」

如果一个任务因为数据格式问题永远会失败，而你又无限重试， 它会一直占用消费能力，拖慢所有其他任务 —— 这叫毒丸消息。
防御手段就是上面两条：设置重试上限（必须有）+ 识别永久错误直接 ack。

定时任务

[triggers]
crons = [
  "*/15 * * * *",     # 每 15 分钟：刷新天气缓存
  "0 3 * * *",        # 每天凌晨 3 点：清理过期会话
  "0 9 * * 1",        # 每周一上午 9 点：发周报
]

export default {
  fetch: app.fetch,
  queue: handleQueue,

  async scheduled(event: ScheduledController, env: Bindings, ctx: ExecutionContext) {
    switch (event.cron) {
      case '*/15 * * * *':
        ctx.waitUntil(refreshWeatherCache(env))
        break
      case '0 3 * * *':
        ctx.waitUntil(cleanupExpiredSessions(env))
        break
      case '0 9 * * 1':
        // 周报要给几千人发 —— 定时任务里不直接发，而是投递任务
        ctx.waitUntil(enqueueWeeklyReports(env))
        break
    }
  },
}
★ 定时任务负责「决定要做什么」，队列负责「做」

定时任务有执行时间上限，而且失败了要等下一个周期。所以它不该自己去做几千件事。
正确的分工：定时任务扫一遍数据库，把要做的事拆成 N 个任务投进队列， 然后立刻结束。队列负责慢慢消化、单独重试失败的那几个。
这样一个用户的邮件发失败，不会影响其余 4999 个。 

async function enqueueWeeklyReports(env: Bindings) {
  let cursor: string | undefined

  do {
    // 一定要分页，别一次性把几万条读进内存
    const page = await getSubscribers(env.DB, { cursor, limit: 500 })

    await env.TASKS.sendBatch(
      page.items.map((u) => ({
        body: newTask('send-weekly-report', { userId: u.id, week: currentWeek() }),
      }))
    )

    cursor = page.nextCursor
  } while (cursor)
}
⚠ 定时任务可能重复执行

平台通常只保证「至少执行一次」。而且多实例部署时，如果用的是自己实现的定时器 （比如 node-cron），每个实例都会各跑一遍。
对策：任务本身幂等，或者用一把带日期的「执行锁」—— INSERT INTO cron_runs (job, date) VALUES ('weekly-report', '2026-09-07')， 靠唯一约束保证一天只有一个实例能插进去。

用户界面怎么配合

异步带来一个新问题：用户提交后，事情还没做完。界面要诚实地反映这一点。

场景做法
用户不关心结果（埋点、同步 CRM）什么都不说，正常返回
用户知道会晚一点（确认邮件）文案说明：「确认邮件将在几分钟内送达」
用户要等结果（生成报表、AI 处理）返回任务 ID，前端轮询状态；或用 SSE 推送进度
结果可能失败（导入文件）做一个「任务列表」页面，显示状态、失败原因、重试按钮

app.get('/api/v1/jobs/:id', async (c) => {
  const job = await getJob(c.env.DB, c.req.param('id'))
  if (!job) throw new HTTPException(404, { message: '任务不存在' })
  return c.json({ status: job.status, progress: job.progress, resultUrl: job.resultUrl })
})
💡 202 这个状态码就是为此而生的

200 OK 的语义是「做完了，这是结果」。
202 Accepted 的语义是「收到了，会去做，但还没做完」。
异步接口用 202，配上一个能查询状态的 URL，是 REST 里的标准做法。

什么时候不该用队列

⚠ 队列不是免费的

它引入了一个新组件（要部署、要监控、要付费）、一套新的故障模式（积压、毒丸、重复消费）、 以及调试难度（日志分散在两个进程里）。不要默认所有东西都走队列。

不该用的情况为什么 / 改用什么
操作只要 20 ms 投递本身就要 10 ms，还多了一堆复杂度。直接同步做
用户必须立刻看到结果 异步做完还要轮询，总时长反而更长，体验更差
需要严格的顺序执行 大多数队列不保证全局顺序。要顺序就用单分区/单消费者，但那就失去了扩容能力
任务失败必须让用户当场知道 异步失败时用户早就走了。这类操作应该同步做，让用户看到错误
整个项目只有一个异步需求 waitUntil + 一张重试表可能就够了，先别上队列

让队列可观测

队列最容易出的问题是悄悄积压：一切看起来正常，只是邮件晚了六个小时。

★ 至少监控这四个指标
  • 队列深度 —— 待处理任务数。持续增长 = 消费能力不够，该扩容了
  • 任务年龄 —— 最老的任务等了多久。比深度更能反映用户感受
  • 失败率 —— 突然上升通常意味着某个下游服务出问题了
  • 死信队列长度 —— 只要不是 0 就该告警
// 在消费者里打结构化日志（第 12 章）
async function handleTask(task: Task, env: Bindings) {
  const start = Date.now()
  try {
    await dispatch(task, env)
    log('info', 'task_done', {
      taskId: task.id,
      type: task.type,
      durationMs: Date.now() - start,
      // 从投递到完成的总延迟 —— 这才是用户实际等待的时间
      latencyMs: Date.now() - task.createdAt,
    })
  } catch (err) {
    log('error', 'task_failed', { taskId: task.id, type: task.type, error: String(err) })
    throw err
  }
}

小结

  • 问「用户看到响应时这件事必须完成吗」，不必须的就移出请求路径。
  • 队列的最大价值不是快，是把外部依赖的可用性和核心业务解耦。
  • 三种手段：waitUntil（丢了无所谓）、队列（不能丢）、定时任务（周期性）。
  • 至少一次投递 ⇒ 消费者必须幂等。这是硬性要求，不是可选项。
  • 任务里放 ID 不放数据，执行时取最新状态。
  • 区分临时失败（重试）和永久失败（直接 ack + 告警），设置重试上限防毒丸。
  • 定时任务只负责「拆任务投队列」，不自己做几千件事。
  • 异步接口返回 202 + 任务 ID；死信队列非空必须告警。
  • 操作很快、用户要等结果、需要严格顺序 —— 这三种情况别用队列。
  • 下一章的 Webhook 接收，以及第 14 章的搜索索引同步，都是队列最典型的应用场景。
