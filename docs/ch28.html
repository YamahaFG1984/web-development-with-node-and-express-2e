第 28 章

可观测性

下一章讲调试 —— 那是你已经知道哪里坏了之后的事。 这一章讲更前面的一步：怎么让系统自己告诉你哪里不对， 在用户投诉之前，在你还没意识到有问题之前。

本章目标

  • 分清「监控」和「可观测性」，知道后者多解决了什么问题
  • 掌握三大支柱：日志、指标、追踪，各自回答什么问题
  • 用 RED 方法设计服务指标
  • 用 SLO 和错误预算把「好不好」变成一个可以争论的数字
  • 设计不会让人麻木的告警
  • 在 Hono 里把这一套落地

监控 vs 可观测性

监控回答你预先想到的问题：CPU 超过 80% 了吗？错误率超过 1% 了吗？ 你事先列出一堆指标，盯着它们。

可观测性回答你没想到的问题： 「为什么只有华南地区的安卓用户在下午三点下单会失败？」 这个问题你不可能提前配一个仪表盘，但系统里必须留下足够的线索让你能事后问出来。

★ 一句话区分

监控告诉你「有问题」，可观测性让你能查出「什么问题」。
前者是有限个预设的仪表盘，后者是能任意切片、任意下钻的原始数据。 小项目先做好监控就够；一旦系统复杂到「不知道该看哪个仪表盘」，就需要可观测性了。

三大支柱

日志：写给机器看

第 12 章已经引入了结构化日志。这里把它做扎实。

❌ 写给人看
用户 u_9 的订单 o_123 创建失败：
库存不足

无法检索、无法聚合、
无法按用户过滤
✅ 写给机器看
{
  "level": "warn",
  "msg": "order_failed",
  "reason": "out_of_stock",
  "userId": "u_9",
  "orderId": "o_123",
  "sku": "HR199",
  "requestId": "5f3a...",
  "traceId": "9b2c...",
  "time": "2026-09-07T10:00:01Z"
}
★ 关键差别：msg 是一个固定的标识符

不要写 "用户 u_9 的订单创建失败"，而要写 msg: "order_failed" 加上独立的字段。
这样你才能查询「过去 24 小时所有 order_failed 且 reason=out_of_stock 的记录， 按 sku 分组」。把变量拼进消息文本里，这个查询就永远做不了。

一个够用的日志器

type Level = 'debug' | 'info' | 'warn' | 'error'

const LEVELS: Record<Level, number> = { debug: 10, info: 20, warn: 30, error: 40 }
const MIN = LEVELS[(process.env.LOG_LEVEL as Level) ?? 'info']

/** 绝不能进日志的字段名 */
const REDACT = new Set([
  'password', 'passwordHash', 'token', 'accessToken', 'refreshToken',
  'authorization', 'cookie', 'secret', 'apiKey', 'creditCard', 'cvv', 'idCard',
])

function scrub(obj: Record<string, unknown>): Record<string, unknown> {
  const out: Record<string, unknown> = {}
  for (const [k, v] of Object.entries(obj)) {
    if (REDACT.has(k)) out[k] = '[已脱敏]'
    else if (v && typeof v === 'object' && !Array.isArray(v)) out[k] = scrub(v as never)
    else out[k] = v
  }
  return out
}

export function log(level: Level, msg: string, fields: Record<string, unknown> = {}) {
  if (LEVELS[level] < MIN) return
  console.log(JSON.stringify({ level, msg, time: new Date().toISOString(), ...scrub(fields) }))
}

/** 绑定一组固定字段，后续每条日志自动带上 */
export function child(base: Record<string, unknown>) {
  return (level: Level, msg: string, fields: Record<string, unknown> = {}) =>
    log(level, msg, { ...base, ...fields })
}
⚠ 主动脱敏，不要靠自觉

「我不会把密码打进日志」这个假设总有一天会被打破 —— 通常是某天有人写了 log('debug', 'req_body', body) 来排查问题，然后忘了删。
把脱敏做进日志器本身，让它成为默认行为。日志会被很多人看到、 同步到第三方、保留很久 —— 一旦写进去就等于泄露。

请求级中间件

import { createMiddleware } from 'hono/factory'
import { child } from '../lib/logger'

export const observability = createMiddleware<{
  Variables: { log: ReturnType<typeof child>; requestId: string; traceId: string }
}>(async (c, next) => {
  // 上游传来的 trace id 要延续，没有才新建 —— 这是跨服务串联的关键
  const traceId = c.req.header('x-trace-id') ?? crypto.randomUUID()
  const requestId = c.req.header('x-request-id') ?? crypto.randomUUID()

  const logger = child({ requestId, traceId })
  c.set('log', logger)
  c.set('requestId', requestId)
  c.set('traceId', traceId)

  const start = Date.now()

  try {
    await next()
  } catch (err) {
    logger('error', 'request_error', { error: String(err) })
    throw err
  } finally {
    const durationMs = Date.now() - start
    const status = c.res.status

    logger(status >= 500 ? 'error' : status >= 400 ? 'warn' : 'info', 'request', {
      method: c.req.method,
      // 用路由模式而不是实际路径 —— 否则 /orders/o_1、/orders/o_2 会变成无数个不同的值
      route: c.req.routePath,
      path: c.req.path,
      status,
      durationMs,
      userId: c.get('user')?.id,
    })
  }

  c.res.headers.set('X-Request-Id', requestId)
})
★ 用 routePath 而不是 path 做聚合维度

/vacations/hood-river、/vacations/oregon-coast…… 如果按实际路径统计，你会得到成千上万个只出现过几次的指标 —— 这叫高基数问题，会撑爆监控系统的存储和查询。
c.req.routePath 返回的是 /vacations/:slug， 是有限的一组值。把它当聚合维度，把具体路径放进日志字段。

把请求 ID 交给用户

app.onError((err, c) => {

  c.get('log')('error', 'unhandled_error', { error: String(err), stack: err.stack })

💡 这一招的价值远超它的成本

用户报错时说「刚才下单失败了」——你要在几百万条日志里大海捞针。
用户报错时说「编号 5f3a-9b2c」——一次查询直接定位到那个请求的全部上下文。
十行代码，把排查时间从两小时降到两分钟。

指标：RED 方法

指标该测什么？对于「请求驱动」的服务，有一个久经考验的极简答案：RED。

字母指标回答的问题
Rate每秒请求数流量多大？突然掉到 0 了吗？
Errors失败请求数 / 比例有多少用户在报错？
Duration响应时间分布用户要等多久？

这三个按 route 和 status 拆开，就能覆盖绝大多数「服务是否健康」的问题。

⚠ 永远不要看平均响应时间

100 个请求，99 个花 10 ms，1 个花 5 秒。平均值是 60 ms —— 看起来很健康， 但有 1% 的用户体验糟糕透顶。
要看分位数：p50（一半用户的体验）、p95、p99（最差的那批人）。 第 12 章压测时已经强调过一次，在线上监控里同样成立。 而且请求量越大，p99 影响的绝对人数越多。

记录指标

// 最省事的做法：从结构化日志里派生指标

  value: order.total,
  currency: order.currency,
})

★ 业务指标往往比技术指标更早发现问题

支付回调因为一个配置错误全部失败 —— CPU 正常、内存正常、错误率正常 （因为回调的 5xx 是对方看到的，你这边只是没收到请求）。
唯一的异常信号是：「过去一小时成功支付订单数 = 0」。
这就是第 31 章「隐形故障」的核心 —— 要监控「应该发生的事」。

追踪

当一个请求要经过网关 → 你的服务 → 数据库 → 第三方 API → 队列时， 「慢了 2 秒」这句话毫无信息量。追踪把这 2 秒拆开：

手工实现一个够用的版本

type Span = { name: string; startMs: number; endMs?: number; attrs: Record<string, unknown> }

export function createTracer(traceId: string) {
  const spans: Span[] = []

  async function span<T>(
    name: string,
    fn: () => Promise<T>,
    attrs: Record<string, unknown> = {}
  ): Promise<T> {
    const s: Span = { name, startMs: Date.now(), attrs }
    spans.push(s)
    try {
      return await fn()
    } catch (err) {
      s.attrs.error = String(err)
      throw err
    } finally {
      s.endMs = Date.now()
    }
  }

  function flush() {
    log('info', 'trace', {
      traceId,
      spans: spans.map((s) => ({
        name: s.name,
        durationMs: (s.endMs ?? Date.now()) - s.startMs,
        ...s.attrs,
      })),
    })
  }

  return { span, flush }
}

app.post('/api/v1/orders', async (c) => {
  const t = createTracer(c.get('traceId'))

  try {
    const user = await t.span('db.get_user', () => getUser(userId))
    const order = await t.span('db.create_order', () => createOrder(user, body))
    await t.span('payment.charge', () => chargeCard(order), { provider: 'stripe' })
    await t.span('queue.send', () => c.env.TASKS.send({ type: 'send-order-email' }))
    return c.json({ orderId: order.id }, 201)
  } finally {
    t.flush()
  }
})
ⓘ 什么时候该上 OpenTelemetry

上面这个手写版本对单体服务完全够用，而且零依赖。
当你有多个服务互相调用时，才需要 OpenTelemetry —— 它的价值在于标准化的上下文传播（把 trace id 通过 traceparent 请求头自动带到下游服务），这样一条 trace 能跨越整个系统。 Hono 有 @hono/otel 中间件可以直接接。

SLO 与错误预算

「我们的服务稳定吗？」这个问题没法争论，因为没有共同标准。 SLO 把它变成一个数字。

概念含义例子
SLI 指标你实际测量的那个数成功请求数 ÷ 总请求数
SLO 目标你承诺达到的水平30 天内成功率 ≥ 99.9%
错误预算SLO 允许你失败的额度30 天内可以失败 0.1%
★ 别把 SLO 定成 100%

100% 可用意味着任何变更都不能做，因为变更就有风险。 这不是目标，是瘫痪。
而且成本是指数级的：99% → 99.9% 可能只要加个健康检查， 99.9% → 99.99% 可能要多区域部署、自动故障转移、24 小时值班 —— 贵几十倍。
先问「用户真的能感知到这个差别吗」，再决定要不要花这个钱。

可用性每月允许不可用大致意味着
99%7 小时 18 分个人项目、内部工具
99.9%43 分钟大多数商业应用的合理起点
99.99%4 分 22 秒需要多区域和自动故障转移
99.999%26 秒电信级，成本极高

告警

告警设计得不好，后果不是「收不到通知」，而是更糟的 —— 大家开始无视所有通知。

★ 三条规则
  1. 基于症状，不是基于原因。「用户在报错」是症状，「CPU 高」是可能的原因之一。 原因有无数种，症状就那么几个 —— 盯症状，覆盖面反而更全。
  2. 每条告警都要可操作。收到它之后，接收人应该知道下一步做什么。 做不到就别设成告警，放进仪表盘。
  3. 分级。页面级（立刻叫醒）、工单级（上班处理）、看板级（有空看看）。 只有第一类才配得上半夜的电话。
// 告警要带上足够的上下文，让人一眼知道该干什么
await notifySlack({
  level: 'page',
  title: '订单接口错误率 8.2%（阈值 5%）',
  fields: {
    影响范围: '过去 5 分钟约 340 个请求失败',
    主要错误: 'payment.timeout（占 91%）',
    最近变更: 'v1.24.0 于 12 分钟前部署',
    仪表盘: 'https://…/orders',
    运维手册: 'https://…/runbook#payment-timeout',
  },
})
💡 「最近变更」这一行特别值钱

绝大多数线上故障是由变更引起的。告警里自动带上「最近一次部署是什么时候、哪个版本」， 能让很多故障在 30 秒内定位 —— 而且直接指向第 30 章的答案：先回滚。

采样与成本

⚠ 可观测性的账单可能超过服务器

每天一亿个请求，每个请求一条 1 KB 的日志 = 100 GB/天 = 3 TB/月。 按主流平台的价格，这个量级的费用能轻松超过你的计算成本。

策略做法
分级采样成功请求采样 1%，错误请求 100% 保留。出问题的那些才是你要看的
慢请求全留耗时超过 p99 的请求 100% 保留 trace
尾部采样先缓存整条 trace，等请求结束后再决定留不留（有错或很慢就留）
分层保留原始日志留 7 天，聚合后的指标留 13 个月（用于同比）
控制基数别把 userId、订单号放进指标标签；它们属于日志字段
function shouldSample(status: number, durationMs: number): boolean {
  if (status >= 500) return true            // 错误全留
  if (durationMs > 1000) return true         // 慢请求全留
  return Math.random() < 0.01                // 其余 1%
}

在 Hono 里串起来

import { requestId } from 'hono/request-id'
import { timing, startTime, endTime } from 'hono/timing'
import { observability } from './middleware/observability'

const app = new Hono<Env>()

app.use(requestId())
app.use(observability)          // 结构化日志 + trace id + 耗时
app.use(timing())               // 输出 Server-Timing 头，浏览器 DevTools 里能直接看到

app.get('/vacations', async (c) => {
  startTime(c, 'db')
  const vacations = await c.get('repo').list({ available: true })
  endTime(c, 'db')

  startTime(c, 'render')
  const html = <VacationsPage vacations={vacations} />
  endTime(c, 'render')

  return c.html(html)
})

// 健康检查（第 12 章）也算可观测性的一部分
app.get('/health', (c) => c.json({ status: 'ok' }))
💡 Server-Timing 是个被忽视的好东西

它把服务端各阶段耗时放进响应头，浏览器 DevTools 的 Network 面板会 直接画出来。前端同事抱怨「接口慢」时， 他自己打开面板就能看到是数据库慢还是渲染慢，不用来找你要日志。

从零开始的优先级

不要一上来就搭全套。按这个顺序做，每一步都有立竿见影的回报：

顺序做什么成本
1结构化日志 + 请求 ID，错误页展示请求 ID半天
2错误追踪（Sentry 之类），接上 app.onError一小时
3外部可用性监控打 /health十分钟
4RED 指标看板（多数日志平台能直接从日志算出来）半天
5定两三条真正可操作的告警一小时
6关键业务指标（订单数、注册数）半天
7定 SLO，开始跟踪错误预算一天
8分布式追踪（确实有多个服务时才做）数天

小结

  • 监控回答「有没有问题」，可观测性回答「是什么问题」。
  • 日志看单个请求、指标看整体趋势、追踪看耗时分布；请求 ID 把三者串起来。
  • 日志的 msg 要是固定标识符，变量放独立字段；脱敏做进日志器本身。
  • 用 routePath 做聚合维度，避免高基数问题。
  • RED 三个指标够用；永远看分位数，不看平均值。
  • 业务指标常常比技术指标更早发现故障。
  • SLO 别定 100%；错误预算把「稳定 vs 速度」变成预先商定的规则。
  • 告警基于症状、必须可操作、要分级 —— 否则只会制造麻木。
  • 错误和慢请求 100% 保留，其余采样。
