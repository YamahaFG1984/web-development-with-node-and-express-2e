第 27 章

接收 Webhook

第 23 章讲的是「你调别人」。这一章反过来：别人调你。 这个方向的思维完全不同 —— 你无法控制对方什么时候调、调几次、按什么顺序调。 做支付集成时，几乎每个人第一次都在这里翻车。

本章目标

  • 理解 webhook 相比轮询的优势，以及它带来的新问题
  • 正确验证签名，包括那个「用原始字节」的关键细节
  • 把「接收」和「处理」拆开，做到快速返回 200
  • 处理重复投递、乱序到达和消息丢失
  • 在本地把 webhook 调通，以及怎么重放事件
  • 反过来，写出让别人好接的 webhook

为什么需要 webhook

★ 你失去了三样东西

调用别人的 API 时，是你决定何时调、调几次、以及并发多少。 接收 webhook 时这三样全归对方：

  • 他可能在你部署重启的那一秒调过来
  • 他可能因为没收到你的 200 而把同一个事件重发十次
  • 他可能并发推送同一笔订单的多个状态变更，而且不保证顺序

本章剩下的内容，基本都是在应对这三件事。

第一件事：验签

你的 webhook 接口在公网上，谁都能 POST。如果不验签，任何人都可以伪造一条 「订单已支付」发给你。

主流做法是 HMAC 签名：你和对方共享一个密钥，对方用它对请求体算一个哈希， 放在请求头里。你用同一个密钥重算一遍，比对是否一致。

那个最容易踩的坑

⚠ 必须用原始字节验签，不能用解析后的对象

对方是对 HTTP 请求体的原始字节算的签名。如果你先 await c.req.json() 解析成对象，再 JSON.stringify() 回去 —— 键的顺序、空格、Unicode 转义、数字精度都可能变，签名必然对不上。

这个 bug 的典型症状是：「我照文档写的，但签名就是验不过」。 九成情况就是这个原因。

❌ 签名永远对不上
const data = await c.req.json()
const body = JSON.stringify(data)   // ← 已经变了
const sig = await hmac(secret, body)
✅ 用原始文本
const raw = await c.req.text()      // ← 一个字节都没动
const sig = await hmac(secret, raw)
// 验签通过之后再解析
const data = JSON.parse(raw)

实现

/** 用 Web Crypto 计算 HMAC-SHA256，所有运行时通用 */
async function hmacSha256(secret: string, message: string): Promise<string> {
  const key = await crypto.subtle.importKey(
    'raw',
    new TextEncoder().encode(secret),
    { name: 'HMAC', hash: 'SHA-256' },
    false,
    ['sign']
  )
  const sig = await crypto.subtle.sign('HMAC', key, new TextEncoder().encode(message))
  return [...new Uint8Array(sig)].map((b) => b.toString(16).padStart(2, '0')).join('')
}

/** 恒定时间比较：不能用 === */
function timingSafeEqual(a: string, b: string): boolean {
  if (a.length !== b.length) return false
  let diff = 0
  for (let i = 0; i < a.length; i++) {
    diff |= a.charCodeAt(i) ^ b.charCodeAt(i)
  }
  return diff === 0
}

export async function verifyWebhook(opts: {
  raw: string
  signature: string | undefined
  timestamp: string | undefined
  secret: string
  toleranceSec?: number
}): Promise<{ ok: true } | { ok: false; reason: string }> {
  const { raw, signature, timestamp, secret, toleranceSec = 300 } = opts

  if (!signature || !timestamp) return { ok: false, reason: '缺少签名或时间戳' }

  // ① 时间戳必须新鲜，防重放
  const age = Math.abs(Date.now() / 1000 - Number(timestamp))
  if (!Number.isFinite(age) || age > toleranceSec) {
    return { ok: false, reason: '时间戳超出容忍窗口' }
  }

  // ② 签名的输入要和对方文档完全一致（这里是 时间戳 + "." + 原始体）
  const expected = await hmacSha256(secret, `${timestamp}.${raw}`)

  if (!timingSafeEqual(expected, signature)) {
    return { ok: false, reason: '签名不匹配' }
  }

  return { ok: true }
}
★ 为什么不能用 === 比较签名

字符串的 === 是短路的：第一个字符就不同时立刻返回，全都相同时才走完。 这个时间差虽然极小，但可以被测量 —— 攻击者逐字符猜测，观察响应时间， 就能一位一位地把正确签名试出来。这叫时序攻击。
timingSafeEqual 无论如何都走完全程，耗时与内容无关。 Node 上也可以直接用 crypto.timingSafeEqual。

第二件事：快速返回 200

几乎所有 webhook 提供方都有超时（通常 3–10 秒）。超时或非 2xx 响应，他们就认为失败并重发。

⚠ 一个真实的连锁反应

你在 webhook 处理函数里同步做了：更新订单 → 发确认邮件 → 同步 CRM → 生成发票。 耗时 4 秒，超过了对方 3 秒的超时。
→ 对方认为失败，重发。
→ 你又跑了一遍这四步（用户收到第二封邮件）。
→ 还是 4 秒，还是超时。
→ 对方按指数退避重发 5 次……用户收到 6 封确认邮件，CRM 里 6 条重复记录。

正确的架构是把「接收」和「处理」彻底拆开 —— 这正好用上第 26 章的队列：

ⓘ 什么时候该返回非 2xx
情况返回为什么
签名验证失败401不是对方的问题就是攻击，别让他重试
请求体不是合法 JSON400重试也没用
事件类型你不关心200已收到，不需要处理，别让他重试
你的数据库暂时挂了500要让他重试，这是唯一该返回 5xx 的情况
业务处理失败（如订单不存在）200已经收下了，业务问题由你的队列自己重试，不该拖累对方

完整实现

export const webhookEvents = sqliteTable('webhook_events', {
  // 对方给的事件 ID，作为主键 —— 这就是去重的全部机制
  id: text('id').primaryKey(),
  provider: text('provider').notNull(),
  type: text('type').notNull(),
  // 原样存下来，出问题时能重放
  payload: text('payload').notNull(),
  // 事件在对方那边发生的时间（不是你收到的时间）
  occurredAt: integer('occurred_at', { mode: 'timestamp' }).notNull(),
  receivedAt: integer('received_at', { mode: 'timestamp' }).notNull(),
  processedAt: integer('processed_at', { mode: 'timestamp' }),
  status: text('status', { enum: ['received', 'done', 'failed'] }).notNull(),
  error: text('error'),
})

import { Hono } from 'hono'
import { verifyWebhook } from '../lib/webhook-verify'

export const webhooks = new Hono<Env>()

webhooks.post('/payments', async (c) => {
  // ① 拿原始文本，不要先 json()
  const raw = await c.req.text()

  const result = await verifyWebhook({
    raw,
    signature: c.req.header('x-signature'),
    timestamp: c.req.header('x-timestamp'),
    secret: c.env.PAYMENT_WEBHOOK_SECRET,
  })

  if (!result.ok) {
    console.warn('webhook 验签失败', { reason: result.reason, ip: c.req.header('cf-connecting-ip') })
    return c.json({ error: result.reason }, 401)
  }

  // ② 验签通过后才解析
  let event: PaymentEvent
  try {
    event = JSON.parse(raw)
  } catch {
    return c.json({ error: '请求体不是合法 JSON' }, 400)
  }

  // ③ 去重 + 存档：靠主键冲突判断是不是重复投递
  try {
    await c.env.DB_CLIENT.insert(webhookEvents).values({
      id: event.id,
      provider: 'payments',
      type: event.type,
      payload: raw,
      occurredAt: new Date(event.created_at * 1000),
      receivedAt: new Date(),
      status: 'received',
    })
  } catch (err) {
    if (isUniqueViolation(err)) {
      // 重复投递 —— 这是正常现象，不是错误
      console.info('重复的 webhook 事件，已忽略', { id: event.id })
      return c.json({ ok: true, duplicate: true })
    }
    throw err     // 数据库真挂了 → 500 → 对方会重试，正确
  }

  // ④ 丢给队列，立刻返回
  await c.env.TASKS.send({ type: 'process-payment-event', id: event.id })

  return c.json({ ok: true })
})
★ 事件表同时解决了三个问题
  • 去重 —— 主键冲突 = 已经收过了（第 24 章的思路）
  • 可重放 —— 代码有 bug 导致处理错了？改完代码，把这些事件重新投一遍队列即可
  • 可审计 —— 「我们到底有没有收到这条通知」，有据可查。和对方扯皮时这是唯一的证据

第三件事：乱序

这是最隐蔽的一个。对方并发推送，网络延迟不同，后发生的事件可能先到达： 

// ❌ 无条件覆盖 —— 旧事件会把新状态盖掉
await db.update(orders)
  .set({ status: event.status })
  .where(eq(orders.id, event.orderId))

// ✅ 只有当事件比数据库里的记录更新时才写
const updated = await db.update(orders)
  .set({ status: event.status, statusUpdatedAt: event.occurredAt })
  .where(and(
    eq(orders.id, event.orderId),
    lt(orders.statusUpdatedAt, event.occurredAt)   // ← 关键
  ))
  .returning()

if (updated.length === 0) {
  // 不是错误：说明我们已经处理过更新的事件了
  console.info('收到过期事件，忽略', { orderId: event.orderId, at: event.occurredAt })
}
💡 更稳的做法：只把 webhook 当「通知」

有些平台（Stripe 是典型）的建议是：不要相信 webhook 里带的数据， 把它当成一个「有东西变了，你去查一下」的信号。收到通知后主动调对方 API 拉一次当前状态。
这样乱序问题自动消失 —— 因为你拿到的永远是最新状态，而不是某个时刻的快照。 代价是多一次 API 调用。涉及钱的场景，这个代价值得付。

第四件事：消息会丢

对方重试 5 次全失败（比如你的服务挂了半小时），事件就永久丢了。 只靠 webhook 的系统一定会漏单。

★ webhook 要有对账兜底

这是行业标准做法：webhook 负责实时性，定时对账负责正确性。 两者缺一不可。 

/** 每小时跑一次：找出本地状态可能过期的订单，主动去对方那边核对 */
export async function reconcilePayments(env: Bindings) {
  // 创建超过 10 分钟仍处于「待支付」的订单 —— 这些很可能漏了通知
  const suspects = await db.select().from(orders)
    .where(and(
      eq(orders.status, 'pending'),
      lt(orders.createdAt, new Date(Date.now() - 10 * 60_000))
    ))
    .limit(500)

  for (const order of suspects) {
    const remote = await paymentApi.getCharge(order.chargeId)   // 主动拉取

    if (remote.status !== order.status) {
      console.warn('对账发现差异', {
        orderId: order.id, local: order.status, remote: remote.status,
      })
      // 走和 webhook 完全相同的处理逻辑，保证幂等
      await env.TASKS.send({ type: 'apply-payment-status', orderId: order.id, status: remote.status })
    }
  }
}
💡 让对账逻辑和 webhook 处理逻辑共用同一个函数

两条路径最终都调 applyPaymentStatus(orderId, status, occurredAt)。 这个函数本身是幂等的、带时间戳判断的。
如果两条路径各写一套逻辑，它们迟早会不一致 —— 而且这种不一致极难发现。

做一个重放端点

// 只在开发环境挂载：把存档的事件重新走一遍处理流程
if (!isProduction) {
  app.post('/dev/webhooks/replay/:id', async (c) => {
    const [event] = await db.select().from(webhookEvents)
      .where(eq(webhookEvents.id, c.req.param('id')))

    if (!event) throw new HTTPException(404, { message: '事件不存在' })

    await processPaymentEvent(JSON.parse(event.payload), c.env)
    return c.json({ ok: true, replayed: event.id })
  })
}
★ 这个端点在生产事故时非常值钱

「上周三有 200 个订单因为一个 bug 没有正确入账」—— 如果你原样存了 payload，修完 bug 之后把这 200 个事件重放一遍就行， 几分钟解决。
如果没存，你要去求对方重发（很多平台不支持），或者手工从对账单里补数据。

反过来：你给别人发 webhook

如果你的产品要给客户推送事件，把上面的痛点反过来想，就知道该怎么做了：

做法为什么
每个事件带唯一 ID让接收方能去重
带事件发生时间，而不只是发送时间让接收方能处理乱序
用 HMAC 签名 + 时间戳让接收方能验证真伪
失败时指数退避重试，并设上限对方短暂故障不该丢消息，也不该被你打垮
提供事件日志和手动重发界面对方出问题时能自助恢复，你少一堆工单
提供轮询 API 兜底让对方能对账
超时设短（3–5 秒）并明确写进文档逼对方异步处理，而不是在你的调用里干重活
连续失败多次后自动停用并通知不要对一个已经废弃的地址永远重试
// 发送方的签名要和你的文档完全一致，并且给出验证示例代码
async function deliverWebhook(endpoint: Endpoint, event: OutgoingEvent) {
  const body = JSON.stringify(event)
  const ts = Math.floor(Date.now() / 1000).toString()
  const sig = await hmacSha256(endpoint.secret, `${ts}.${body}`)

  const res = await fetch(endpoint.url, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'X-Timestamp': ts,
      'X-Signature': sig,
      'X-Event-Id': event.id,
      'User-Agent': 'Meadowlark-Webhooks/1.0',
    },
    body,
    signal: AbortSignal.timeout(5000),      // 第 23 章：超时预算
  })

  if (!res.ok) throw new Error(`接收方返回 ${res.status}`)
}
⚠ 发 webhook 时的 SSRF 风险

客户可以填任意 URL 作为接收地址。如果不校验，他可以填 http://169.254.169.254/（云厂商的元数据服务，能拿到你的凭证） 或者 http://localhost:6379（你的内网 Redis）。
必须校验：只允许 https、解析出的 IP 不能是私有网段或回环地址、 禁止重定向到内网。这类攻击叫 SSRF，是云环境下最危险的漏洞之一。

小结

  • Webhook 把控制权交给了对方：时机、次数、顺序都不由你。
  • 验签必须用原始字节，必须检查时间戳防重放，必须用恒定时间比较。
  • 接收端只做三件事：验签、存档去重、投队列，目标 50 ms 返回 200。
  • 只有「你自己临时故障」才该返回 5xx；业务失败返回 200，由你的队列重试。
  • 不要假设到达顺序，用事件时间戳做条件更新；涉及钱时改为主动拉取最新状态。
  • 消息一定会丢，必须有定时对账兜底，且和 webhook 共用同一套处理函数。
  • 原样存档 payload —— 出事故时重放能救命。
  • 自己发 webhook 时，把接收方的痛点反过来做；并防住 SSRF。
  • 支付是 webhook 最典型也最不容出错的场景 —— 见第 30 章。
