第 15 章

REST API 与 JSON

网站是给人看的，API 是给程序用的。这一章设计并实现云雀旅行的 API， 并展示 Hono 的杀手锏：让前端直接拿到后端的类型。

本章目标

  • 设计一套讲道理的 REST 接口，并规划错误响应格式
  • 用 HTTPException 做统一的错误处理
  • 理解 CORS 到底在防什么，正确配置它
  • 用 RPC 客户端让前端共享后端类型
  • 用 Zod OpenAPI 自动生成接口文档

设计 API

REST 的核心思想很简单：用名词表示资源，用 HTTP 方法表示动作。

❌ 动词进路径
GET  /api/getVacations
POST /api/createVacation
POST /api/deleteVacation
POST /api/updateVacationPrice
✅ 名词 + 方法
GET    /api/v1/vacations
POST   /api/v1/vacations
DELETE /api/v1/vacations/:sku
PATCH  /api/v1/vacations/:sku

云雀旅行的 API：

方法与路径作用参数位置
GET /api/v1/vacations列出度假套餐查询串：available、limit、cursor
GET /api/v1/vacations/:sku取单个路径参数
POST /api/v1/vacations/:sku/notify订阅到季通知JSON 请求体：email
DELETE /api/v1/vacations/:sku申请下架（标记待审核）JSON 请求体：email、notes
💡 第一天就加版本号

路径里的 /v1/ 现在看起来多余，但它是你未来唯一的退路。 当某天必须做破坏性改动时，你可以上线 /v2/ 而让 /v1/ 继续服务老客户端。 没有版本号的话，你要么永远不能改，要么一改就有人的 App 崩掉。

返回格式

// 列表：包一层，方便加分页信息
{
  "data": [
    { "sku": "HR199", "name": "胡德河一日游", "price": 99.95 }
  ],
  "nextCursor": "eyJza3UiOiJIUjE5OSJ9"
}

// 单个资源：直接返回
{ "sku": "HR199", "name": "胡德河一日游", "price": 99.95 }

// 错误：结构固定，客户端好统一处理
{
  "error": {
    "code": "VACATION_NOT_FOUND",
    "message": "没有找到 SKU 为 XX000 的度假套餐"
  }
}
⚠ 列表接口不要直接返回数组

返回 [{...}, {...}] 看起来很干净，但等你需要加分页游标、总数、 或者「本次结果被截断了」这种元信息时，就必须改变返回结构 —— 这是破坏性变更。 一开始就包一层 { data: [...] }，未来加字段是兼容的。

错误处理

错误分三类，处理方式完全不同：

ⓘ 空结果不是错误

「查询列表，一条都没有」应该返回 200 加一个空数组，不是 404。 404 的含义是「你请求的这个资源不存在」，而 /api/v1/vacations 这个资源是存在的，只是当前内容为空。

HTTPException

Hono 提供了一个专门的异常类，让你在任何深度都能中断请求并返回指定状态码：

import { HTTPException } from 'hono/http-exception'

app.get('/api/v1/vacations/:sku', async (c) => {
  const v = await repo.findBySku(c.req.param('sku'))

  if (!v) {
    throw new HTTPException(404, { message: '没有找到这个度假套餐' })
  }

  return c.json(v)
})

import { HTTPException } from 'hono/http-exception'

app.onError((err, c) => {
  // ① 我们主动抛出的：按原样返回
  if (err instanceof HTTPException) {
    return c.json(
      { error: { code: 'HTTP_ERROR', message: err.message } },
      err.status
    )
  }

  // ② 意料之外的：记录 + 上报，只给客户端一句笼统的话
  console.error('未预期的错误', err)
  reportToSentry(err, { path: c.req.path, requestId: c.get('requestId') })

  return c.json(
    { error: { code: 'INTERNAL_ERROR', message: '服务器内部错误' } },
    500
  )
})
⚠ 永远不要把异常信息直接返回给客户端

return c.json({ error: err.message }, 500) 看起来很方便， 但数据库错误信息里可能包含表名、列名、甚至部分数据；文件错误里包含服务器路径。 这些都是攻击者做侦察的素材。细节写日志，客户端只给一句话和一个请求 ID。

CORS

浏览器有一条铁律叫同源策略：https://a.com 上的 JavaScript 默认不能读取 https://b.com 的响应内容。 

import { cors } from 'hono/cors'

app.use(
  '/api/*',
  cors({
    origin: ['https://meadowlarktravel.com', 'https://app.meadowlarktravel.com'],
    allowMethods: ['GET', 'POST', 'PATCH', 'DELETE', 'OPTIONS'],
    allowHeaders: ['Content-Type', 'Authorization'],
    exposeHeaders: ['X-Request-Id'],
    credentials: true,      // 允许带 Cookie
    maxAge: 86400,          // 预检结果缓存一天，减少 OPTIONS 请求
  })
)
⚠ 两个常见的错误配置
  • origin: '*' 配上 credentials: true —— 规范禁止这个组合，浏览器会直接拒绝。而且真这么做等于允许任何网站带着用户 Cookie 调你的接口。
  • 把 CORS 当成认证。它完全不是。CORS 只约束浏览器里的脚本， 任何人用 curl 都能绕过。鉴权必须在服务端做（第 18 章）。

实现

import { Hono } from 'hono'
import { cors } from 'hono/cors'
import { HTTPException } from 'hono/http-exception'
import { zValidator } from '@hono/zod-validator'
import { z } from 'zod'

const listQuery = z.object({
  available: z.enum(['true', 'false']).optional(),
  limit: z.coerce.number().int().min(1).max(100).default(20),
})

const notifyBody = z.object({
  email: z.string().email(),
})

const deleteBody = z.object({
  email: z.string().email(),
  notes: z.string().max(500).optional(),
})

export const api = new Hono<Env>()
  .use('*', cors({ origin: allowedOrigins }))

  .get('/vacations', zValidator('query', listQuery), async (c) => {
    const { available, limit } = c.req.valid('query')
    const data = await c.get('repo').list({
      available: available === undefined ? undefined : available === 'true',
      limit,
    })
    return c.json({ data })
  })

  .get('/vacations/:sku', async (c) => {
    const v = await c.get('repo').findBySku(c.req.param('sku'))
    if (!v) throw new HTTPException(404, { message: '没有找到这个度假套餐' })
    return c.json(v)
  })

  .post('/vacations/:sku/notify', zValidator('json', notifyBody), async (c) => {
    const sku = c.req.param('sku')
    const { email } = c.req.valid('json')

    const v = await c.get('repo').findBySku(sku)
    if (!v) throw new HTTPException(404, { message: '没有找到这个度假套餐' })

    await c.get('repo').addInSeasonListener(email, sku)
    return c.json({ ok: true }, 201)
  })

  .delete('/vacations/:sku', zValidator('json', deleteBody), async (c) => {
    const sku = c.req.param('sku')
    const { email, notes } = c.req.valid('json')

    // 公开接口不真删，只标记待审核
    const ok = await c.get('repo').requestDeletion(sku, email, notes)
    if (!ok) throw new HTTPException(404, { message: '没有找到这个度假套餐' })

    return c.body(null, 204)
  })

RPC：前端直接用后端的类型

这是 Hono 最值得炫耀的功能。你不用写 OpenAPI，不用跑代码生成器 —— 把后端的类型 import 到前端就行。 

// 后端：导出类型（注意必须是链式定义的）
export type ApiType = typeof api

// 前端：导入类型（只是类型，不会打包任何后端代码）
import { hc } from 'hono/client'
import type { ApiType } from '../../src/routes/api'

export const client = hc<ApiType>('https://api.meadowlarktravel.com/v1')

// 使用：全程有补全和检查
const res = await client.vacations.$get({
  query: { available: 'true', limit: '20' },
})

if (res.ok) {
  const body = await res.json()
  // body.data 的类型是 Vacation[]，编辑器里点得出每个字段
  body.data.forEach((v) => console.log(v.name, v.price))
}

// 写错了当场报错：
await client.vacations.$get({ query: { availabel: 'true' } })
//                                     ^^^^^^^^^ 拼写错误，编译不过

await client.vacationz.$get()
//           ^^^^^^^^^ 没有这个路径，编译不过
ⓘ RPC 的适用范围

它要求前后端在同一个 TypeScript 项目（或 monorepo）里。
如果你的 API 要给外部团队、给移动端、给第三方用，还是需要 OpenAPI 文档 —— 见下一节。 两者可以同时存在。

生成 OpenAPI 文档

npm install @hono/zod-openapi @hono/swagger-ui

import { OpenAPIHono, createRoute, z } from '@hono/zod-openapi'
import { swaggerUI } from '@hono/swagger-ui'

const VacationSchema = z
  .object({
    sku: z.string().openapi({ example: 'HR199' }),
    name: z.string().openapi({ example: '胡德河一日游' }),
    price: z.number().openapi({ example: 99.95 }),
    inSeason: z.boolean(),
  })
  .openapi('Vacation')

const listRoute = createRoute({
  method: 'get',
  path: '/vacations',
  summary: '列出度假套餐',
  request: {
    query: z.object({
      available: z.enum(['true', 'false']).optional(),
    }),
  },
  responses: {
    200: {
      description: '度假套餐列表',
      content: {
        'application/json': {
          schema: z.object({ data: z.array(VacationSchema) }),
        },
      },
    },
  },
})

const app = new OpenAPIHono()

app.openapi(listRoute, async (c) => {
  const { available } = c.req.valid('query')
  const data = await repo.list({ available: available === 'true' })
  return c.json({ data })
})

// 生成 OpenAPI JSON
app.doc('/openapi.json', {
  openapi: '3.0.0',
  info: { version: '1.0.0', title: '云雀旅行 API' },
})

// 可交互的文档页面
app.get('/docs', swaggerUI({ url: '/openapi.json' }))
★ 文档不会过期

这里的 schema 同时承担三个职责：运行时校验、TypeScript 类型、 OpenAPI 文档。三者由同一份代码生成，所以不可能不一致。
传统做法里「文档和实现对不上」是常态，因为它们是两份需要人工同步的东西。

小结

  • REST：名词做路径，HTTP 方法做动作。第一天就加版本号。
  • 列表接口返回 { data: [...] } 而不是裸数组，为未来加元信息留余地。
  • 区分三类错误：4xx 是客户端的问题，不要当故障告警；5xx 才是你的问题。
  • 用 HTTPException 抛错，用 app.onError 统一格式化；细节写日志，不返回给客户端。
  • CORS 保护浏览器用户，不是鉴权手段。
  • 同仓库前后端用 RPC 共享类型；对外 API 用 @hono/zod-openapi 生成文档。

动手练习

  1. 实现本章的四个 API 端点，用 testClient 给每个端点写至少两个测试（成功和失败各一个）。
  2. 用 curl 请求一个不存在的 SKU，确认返回 404 且响应体是你设计的错误格式。
  3. 写一个最简单的 HTML 页面放在另一个端口上，用 fetch 调你的 API。先不配 CORS，看看浏览器控制台的报错；然后加上 CORS 再试。
  4. 导出 ApiType，在一个测试文件里用 hc 创建客户端。故意写错一个字段名，确认 tsc 报错。
  5. 用 @hono/zod-openapi 给一个端点加上文档，打开 /docs 页面，在里面直接发一次请求。
