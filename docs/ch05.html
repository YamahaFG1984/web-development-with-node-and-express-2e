第 5 章

质量保证

Hono 有个别的框架羡慕的特性：测试一个路由不需要启动服务器。 因为应用本身就是个函数，你直接调用它就行。这让写测试的成本低到没有借口不写。

本章目标

  • 分清单元测试和集成测试，知道各自该测什么
  • 用 app.request() 和 testClient 在内存里测路由
  • 用 Vitest 写断言、做 mock、看覆盖率
  • 用 Playwright 写一个真浏览器的端到端测试
  • 配好代码检查工具和 GitHub Actions 持续集成

测试到底在保护什么

很多人把测试理解成「证明代码是对的」。更准确的说法是：测试保护的是「改代码的勇气」。 没有测试的项目，每次改动都是赌博；有测试的项目，你敢重构。

质量本身有四个维度，但只有一部分能自动化：

维度关心什么能自动测吗
触达有多少人能找到并访问你的站（SEO、可达性）部分（链接检查、结构化数据校验）
功能它是否按承诺工作可以，本章重点
易用性用户能不能顺利完成任务不能，需要真人
美观看起来是否得体不能（视觉回归测试只能测「有没有变」）

逻辑与展现要分开

一条规则：「租摩托车必须有驾照」—— 这是逻辑。 「驾照那一栏是复选框还是输入框」—— 这是展现。

逻辑应该待在 src/lib/ 这样不认识 HTTP 的模块里，因为它最值得也最容易测。 展现变化频繁，测得太死反而拖后腿。这就是我们在第 4 章分层的实际收益。

两种测试

安装 Vitest

Vitest 是目前 TypeScript 项目最顺手的测试框架：原生支持 TS 和 ESM，不用额外配置。 

npm install -D vitest

在 package.json 的 scripts 里加：

"scripts": {
  "test": "vitest run",
  "test:watch": "vitest",
  "coverage": "vitest run --coverage"
}

单元测试

先测最简单的：src/lib/fortune.ts。新建 src/lib/fortune.test.ts： 

import { describe, it, expect } from 'vitest'
import { getFortune } from './fortune'

describe('getFortune', () => {
  it('返回一个非空字符串', () => {
    const fortune = getFortune()
    expect(typeof fortune).toBe('string')
    expect(fortune.length).toBeGreaterThan(0)
  })

  it('多次调用能返回不同结果', () => {
    const results = new Set<string>()
    for (let i = 0; i < 50; i++) results.add(getFortune())
    expect(results.size).toBeGreaterThan(1)
  })
})
ⓘ 测试随机性的坑

第二个测试有个隐患：理论上 50 次全抽到同一条签语是可能的，测试会偶发失败。 这类「有时红有时绿」的测试叫 flaky test，比没有测试还烦人。 处理办法：要么把阈值放宽（像这里只要求「不止一种」），要么把随机源作为参数注入，测试时传一个假的。

测路由：不用启动服务器

这是 Hono 最舒服的地方。因为 app 就是个函数，你可以直接给它一个请求：

import { describe, it, expect } from 'vitest'
import { app } from './app'

describe('页面路由', () => {
  it('首页返回 200 和 HTML', async () => {
    const res = await app.request('/')

    expect(res.status).toBe(200)
    expect(res.headers.get('content-type')).toContain('text/html')

    const html = await res.text()
    expect(html).toContain('欢迎来到云雀旅行')
  })

  it('关于页包含签语', async () => {
    const res = await app.request('/about')
    const html = await res.text()
    expect(html).toContain('今日签语')
  })

  it('不存在的路径返回 404', async () => {
    const res = await app.request('/这个页面不存在')
    expect(res.status).toBe(404)
  })
})

app.request() 接受一个路径字符串或一个完整的 Request 对象，返回标准的 Response。 没有端口，没有网络，没有 beforeEach 里启动服务器再关掉。毫秒级。

testClient：带类型的测试客户端

app.request('/about') 里的路径是字符串，写错了 TypeScript 不会提醒你。 testClient 解决这个问题 —— 它根据你的路由定义生成一个有类型的客户端： 

import { testClient } from 'hono/testing'
import { Hono } from 'hono'

// 注意：要用链式写法定义路由，类型才能被推导出来
const routes = new Hono()
  .get('/api/vacations', (c) => c.json([{ sku: 'HR199', name: '胡德河一日游' }]))
  .get('/api/vacations/:sku', (c) => c.json({ sku: c.req.param('sku') }))

const client = testClient(routes)

it('列出度假套餐', async () => {
  const res = await client.api.vacations.$get()
  expect(res.status).toBe(200)

  const data = await res.json()   // ← 类型是 { sku: string; name: string }[]
  expect(data[0].sku).toBe('HR199')
})
💡 为什么必须链式写

app.get(...) 会返回一个带上了这条路由类型信息的新类型。 如果你写成分开的 app.get(a); app.get(b);，类型信息就丢了。 链式 .get().get().post() 让类型一路累加。这同样是第 15 章 RPC 客户端能工作的前提。

Mock：把依赖换成假的

测试要隔离。如果 /about 的测试因为签语模块改了内容而失败，那这个测试就太脆了。 用 Vitest 的 mock 把依赖替换掉： 

import { describe, it, expect, vi } from 'vitest'

// 把整个模块替换成假的
vi.mock('./lib/fortune', () => ({
  getFortune: () => '这是一条测试签语',
}))

// 注意：import 要放在 vi.mock 之后（Vitest 会自动提升，但这样读起来更清楚）
const { app } = await import('./app')

it('关于页渲染签语', async () => {
  const res = await app.request('/about')
  const html = await res.text()
  expect(html).toContain('这是一条测试签语')   // 现在结果是确定的
})

还有一种常用 mock：监视函数被怎么调用了。

const sendEmail = vi.fn()          // 一个记录调用情况的假函数

await someHandlerThatSendsEmail(sendEmail)

expect(sendEmail).toHaveBeenCalledTimes(1)
expect(sendEmail).toHaveBeenCalledWith('a@example.com', expect.stringContaining('欢迎'))

覆盖率

npm install -D @vitest/coverage-v8
npm run coverage

你会得到一张表，四个数字：

指标含义
Stmts 语句有多少条语句被执行过
Branch 分支if/else 的两条路都走过吗
Funcs 函数有多少函数被调用过
Lines 行有多少行被执行过
⚠ 覆盖率是个骗子

100% 覆盖率不代表没 bug —— 它只说明每行代码都被执行过，不代表每行的结果被检查过。 反过来，server.tsx 覆盖率是 0% 也完全正常，那里面只有启动逻辑，测它没有意义。 把覆盖率当成找出「完全没人碰过的角落」的工具，而不是 KPI。

端到端测试

前面的测试都在内存里，验证不了「用户点了链接会不会跳转」。这需要真浏览器。 Playwright 能控制一个无头浏览器（不显示界面但功能完整的 Chrome）。 

npm install -D @playwright/test
npx playwright install chromium

先给要测的链接加一个专门的标记属性：

<a href="/about" data-testid="about-link">关于我们</a>
💡 为什么用 data-testid 而不是 class

class 是给设计师改样式用的，随时可能变；靠文字「关于我们」定位，改一次文案测试就挂。 data-testid 是专门给测试用的锚点，看到它的人就知道「这个别乱删」。

e2e/navigation.spec.ts：

import { test, expect } from '@playwright/test'

test('首页能跳到关于页', async ({ page }) => {
  await page.goto('http://localhost:3000/')
  await page.getByTestId('about-link').click()
  await expect(page).toHaveURL(/\/about$/)
  await expect(page.getByRole('heading', { name: '关于云雀旅行' })).toBeVisible()
})

playwright.config.ts 让它自动帮你启动服务器：

import { defineConfig } from '@playwright/test'

export default defineConfig({
  testDir: './e2e',
  webServer: {
    command: 'npm run start',
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
  },
})
ⓘ 端到端测试要少而精

它慢（秒级）、脆（改个按钮位置就挂）、难调试。只用它覆盖最关键的几条用户路径： 注册、下单、支付。其余交给单元测试和 app.request()。

代码检查

Linter 找的不是「错误」，而是「未来可能出错的写法」：没用到的变量、忘了 await 的 Promise、 可能是 undefined 的访问。

推荐 Biome：一个工具同时做检查和格式化，速度极快，配置极少。 

npm install -D --save-exact @biomejs/biome
npx biome init

{
  "$schema": "https://biomejs.dev/schemas/1.9.4/schema.json",
  "linter": { "enabled": true, "rules": { "recommended": true } },
  "formatter": { "enabled": true, "indentStyle": "space", "indentWidth": 2 },
  "javascript": { "formatter": { "semicolons": "asNeeded", "quoteStyle": "single" } }
}

"scripts": {
  "lint": "biome check src",
  "lint:fix": "biome check --write src",
  "format": "biome format --write src"
}

第一次跑会看到一堆问题，这很正常。每条报告有三种处理方式：

  1. 它是对的 —— 改代码。
  2. 你不同意这条规则 —— 在配置里关掉它。规则是为你服务的。
  3. 规则对，但这一处确实要例外 —— 用 // biome-ignore lint/...: 原因 单行豁免，并写清楚原因。

持续集成

写了测试却不跑，等于没写。持续集成（CI）就是「每次推代码，服务器自动帮你跑一遍」。 GitHub 上建一个文件就行： 

name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm test

小结

  • Hono 应用是函数，所以 app.request('/path') 就能测路由，不用起服务器。
  • testClient 给测试加上类型，前提是路由用链式语法定义。
  • 用 mock 隔离依赖，让测试结果确定、失败原因明确。
  • 覆盖率是发现「没人碰过的角落」的工具，不是目标。
  • 端到端测试只用在最关键的用户路径上。
  • CI 让「跑测试」这件事不依赖任何人的自觉。

动手练习

  1. 给你的 /、/about、404 三个路由都补上测试，跑 npm test 全绿。
  2. 故意把 Home 组件里的标题改掉，确认测试变红了 —— 这才说明测试真的在保护你。
  3. 跑一次 npm run coverage，找出覆盖率最低的文件。它是「该补测试」还是「不值得测」？
  4. 接上 Biome，把 npm run lint 跑到零报错。有哪条规则你不认同？把它关掉，并在配置里写注释说明理由。
