第 26 章

调试

调试的核心不是工具，是方法。这一章先讲一条能用一辈子的原则， 再给出 Hono 项目里最常见故障的速查表。

本章目标

  • 掌握「二分缩小范围」这个通用调试方法
  • 用好 console 里那些你可能没用过的方法
  • 用调试器打断点，而不是到处加打印
  • 调试异步代码和中间件顺序问题
  • 会用 Hono 的诊断工具定位路由问题

第一原则：缩小范围

面对一个 bug，最没效率的做法是盯着代码想「哪里错了」。 最有效的做法是系统地把「可能出错的范围」一次次砍半，直到只剩几行。

★ 调试前先回答四个问题
  1. 能稳定复现吗？不能稳定复现的 bug，无法验证是否修好了。先花时间找到复现步骤。
  2. 最小复现是什么？把无关的部分一点点删掉，直到删任何一行 bug 就消失。 这个过程本身经常就把原因暴露出来了。
  3. 最后一次正常是什么时候？git bisect 能在几十次提交里用几步定位到引入问题的那次提交。
  4. 我假设了什么？Bug 几乎总是藏在你「觉得肯定没问题」的地方。把假设一条条验证。
# git bisect：在 100 次提交里，7 次就能定位
git bisect start
git bisect bad                  # 当前版本有问题
git bisect good v1.2.0          # 这个版本是好的
# Git 会自动切到中间某次提交，你测试后告诉它 good 还是 bad
git bisect good
git bisect bad
# ...重复几次
git bisect reset

💡 一个省时间的小技巧

打印变量时用对象简写，这样输出里自带变量名： 

console.log(userId, cartTotal, itemCount)
// → u_123 299.85 3        ← 哪个是哪个？

console.log({ userId, cartTotal, itemCount })
// → { userId: 'u_123', cartTotal: 299.85, itemCount: 3 }   ✓

用调试器

打印语句的问题是：你只能看到你想到要打印的东西。 调试器让你暂停程序，然后随便看任何变量。 

# 启动时开启调试端口
node --inspect dist/server.js

# 用 tsx 开发时
npx tsx --inspect src/server.tsx

# 在第一行就暂停（用于调试启动过程）
node --inspect-brk dist/server.js

然后打开 Chrome，访问 chrome://inspect，点击 「inspect」。

更方便的是在 VS Code 里直接调试：

★ 三种断点，各有用处
  • 普通断点 —— 点行号左边。程序跑到这里就停。
  • 条件断点 —— 右键行号，输入条件。「只在 sku === 'HR199' 时停下」， 循环里调试必备。
  • 日志断点 —— 右键选 Logpoint。不暂停，只打印一条消息。 相当于「临时加一行 console.log，但不用改代码，也不会忘了删」。

调试异步代码

// ❌ 忘了 await：错误堆栈里根本看不到这个函数
async function handler(c) {
  saveToDatabase(data)         // 返回的 Promise 没人管
  return c.text('ok')
}

// ✅
async function handler(c) {
  await saveToDatabase(data)
  return c.text('ok')
}
⚠ 忘记 await 是最常见的异步 bug

症状五花八门：数据没保存但接口返回成功、日志顺序错乱、 偶发的「connection closed」、错误堆栈指向完全无关的地方。
防御手段：开启 ESLint 的 no-floating-promises 规则 （需要 TypeScript 类型信息），它会在编译期就抓出所有没处理的 Promise。 

// 让异步堆栈更完整
process.on('unhandledRejection', (reason) => {
  console.error('未处理的 Promise 拒绝：')
  console.error(reason)
})

// 用 Error.cause 保留原始错误（不要把它吞掉）
try {
  await callExternalApi()
} catch (err) {
  throw new Error('获取天气数据失败', { cause: err })
}

Hono 专属排查

看路由表

import { showRoutes } from 'hono/dev'

if (process.env.NODE_ENV !== 'production') {
  showRoutes(app, { verbose: true })
}

看请求经过了哪些中间件

// 临时插在最外层
app.use('*', async (c, next) => {
  console.group(`>>> ${c.req.method} ${c.req.path}`)
  console.time('总耗时')
  await next()
  console.timeEnd('总耗时')
  console.log('匹配的路由：', c.req.routePath)   // ← 关键：实际匹配到哪条
  console.log('响应状态：', c.res.status)
  console.groupEnd()
})

c.req.routePath 特别有用：它告诉你实际匹配上的是哪条路由规则。 「我明明访问的是 /vacations/new，为什么走到了详情页」—— 打印一下就会看到 routePath 是 /vacations/:slug， 于是知道是路由顺序问题（第 15 章）。

看真实的请求和响应

# -v 显示完整的请求头和响应头
curl -v http://localhost:3000/api/v1/vacations

# 只看响应头
curl -I http://localhost:3000/

# 发 JSON
curl -X POST http://localhost:3000/api/v1/vacations/HR199/notify \
  -H 'Content-Type: application/json' \
  -d '{"email":"a@example.com"}' -i

# 带 Cookie
curl -b 'sid=abc123' http://localhost:3000/account -i
💡 分不清是前端还是后端的问题时，用 curl

curl 绕过了浏览器的一切（缓存、Cookie、CORS、Service Worker、前端代码）。 如果 curl 结果正确而浏览器不对，问题一定在浏览器侧；反之在服务端。 一条命令就砍掉了一半的搜索范围。

常见故障速查表

症状最可能的原因
中间件完全不生效 ① 写在路由注册之后了；② 忘了调用工厂函数（logger 少了括号）；③ 路径模式不匹配
响应内容为空 / 请求挂住 处理函数忘了 return，或者中间件忘了 await next()
「Body has already been read」 请求体读了两次。改成读一次存到变量里（第 6 章）
路由匹配错了 顺序问题。具体路径要写在通配和参数路由前面。用 c.req.routePath 确认（第 15 章）
写了路由但访问到静态文件 serveStatic 在前面抢走了。检查 public/ 里有没有同名文件（第 3 章）
浏览器报 CORS 错误 CORS 中间件没配、配在路由后面、或者 origin 写错了（第 16 章）
Cookie 设了但读不到 path / domain 不匹配；本地开发时设了 secure: true；跨站被 sameSite 挡住（第 9 章）
Workers 上 c.env 是 undefined 在模块顶层访问了。必须在请求上下文里读（第 12 章）
本地好好的，线上 500 环境变量没配；用了 Node 独有 API；构建产物和源码不一致
JSX 报「找不到命名空间」 tsconfig.json 里缺 jsxImportSource: "hono/jsx"；或文件后缀不是 .tsx（第 3 章）
RPC 客户端没有类型提示 路由不是链式定义的，类型信息丢了（第 15 章）
SPA 刷新子页面 404 服务端没配 SPA 回退（第 17 章）

线上问题

生产环境不能打断点，你只有三样东西：

📜

结构化日志

带上请求 ID，就能把一个请求经过的所有日志串起来（第 12 章）。

🚨

错误追踪

Sentry 之类。带上堆栈、用户、请求上下文，比翻日志高效得多。

📈

指标

响应时间、错误率、依赖耗时。它们告诉你「什么时候开始变坏的」。

# Cloudflare Workers：实时看线上日志
npx wrangler tail

# 只看错误
npx wrangler tail --status error
★ 每修一个 bug，问一句「怎么才能更早发现它」

如果答案是「加个类型」「加个校验」「加个测试」「加条日志」，那就顺手加上。
修 bug 只解决了这一个；改进发现机制能解决一整类。 这也是第 5 章说的「QA 计划是活文档」的意思。

小结

  • 调试的核心是二分缩小范围，不是盯着代码猜。
  • 先确保能稳定复现，再找最小复现；git bisect 能快速定位引入问题的提交。
  • console.table、console.time、条件断点、日志断点都能省大量时间。
  • 忘记 await 是最常见的异步 bug，用 lint 规则防住。
  • showRoutes() 和 c.req.routePath 是 Hono 路由问题的照妖镜。
  • 用 curl 排除浏览器因素，一步砍掉一半搜索范围。

动手练习

  1. 配好 VS Code 的调试配置，在一个路由处理函数里打断点，观察 c.req 对象里到底有什么。
  2. 在一个循环里设置条件断点，只在特定的 sku 上停下来。
  3. 加上本章的调试中间件，访问几个不同路径，看 routePath 输出。故意制造一次路由遮蔽，观察它怎么暴露出来。
  4. 故意写一个忘了 await 的 bug，观察它的表现有多难懂。然后开启 no-floating-promises 规则，看它是否被抓住。
  5. 在你的项目里制造一个 bug，提交几次之后用 git bisect 把它找出来。
