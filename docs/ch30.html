第 30 章

支付与订阅

这一章几乎不引入新概念 —— 它是前面几章的期末考试。 幂等、Webhook、队列、对账、审计日志、时区，这些你都学过了。 区别在于：在别的地方出错叫 bug，在这里出错叫少收了钱或者多扣了钱。

本章目标

  • 理解「不要碰卡号」这条底线，以及它如何简化你的合规负担
  • 用状态机而不是布尔值表达支付和订阅
  • 知道为什么永远不能相信客户端说「我付款成功了」
  • 处理订阅特有的难题：计费周期、升降级、宽限期、取消
  • 把订阅状态映射成权限，并在状态不确定时做出正确选择
  • 建立对账机制，处理退款与拒付

第一条：不要碰卡号

处理信用卡数据受 PCI DSS 标准约束。如果卡号进过你的服务器 —— 哪怕只是内存里过一遍、哪怕立刻转发出去 —— 你的合规范围就会急剧扩大： 网络隔离、日志审计、渗透测试、年度认证。

★ 这是本章最重要的一条

用支付平台提供的托管收银页或嵌入式组件（Stripe Elements、Checkout 之类）。 卡号在一个跨域 iframe 里，连你自己的 JavaScript 都读不到。
你拿到的是一个令牌，它只在你的账户下、只能用来发起收款 —— 泄露了也拿不去别处刷。
「我们自己做个表单，看起来更统一」是个非常昂贵的审美偏好。

用状态机，不要用布尔值

❌ 布尔值
{ isPaid: boolean }
「正在支付中」是什么？「支付失败了」呢？
「付了又退了」是 true 还是 false？
每多一种情况就要加一个布尔值，然后组合爆炸。
✅ 状态机
type PaymentStatus =
  | 'requires_payment'   // 待支付
  | 'processing'          // 处理中
  | 'succeeded'           // 已成功
  | 'failed'              // 已失败
  | 'refunded'            // 已退款
  | 'disputed'            // 争议中

const ALLOWED: Record<PaymentStatus, PaymentStatus[]> = {
  requires_payment: ['processing', 'failed'],
  processing:       ['succeeded', 'failed'],
  succeeded:        ['refunded', 'disputed'],
  failed:           [],                        // 终态：重试要新建一笔
  refunded:         ['disputed'],
  disputed:         ['refunded', 'succeeded'], // 争议可能赢也可能输
}

export function canTransition(from: PaymentStatus, to: PaymentStatus): boolean {
  return ALLOWED[from].includes(to)
}

export async function applyPaymentStatus(
  db: Db, paymentId: string, to: PaymentStatus, occurredAt: Date
) {
  const payment = await db.getPayment(paymentId)
  if (!payment) return

  // 幂等：已经是这个状态了，直接返回（第 24 章）
  if (payment.status === to) return

  if (!canTransition(payment.status, to)) {
    // 不是错误，通常是乱序到达的旧事件（第 27 章）
    log('warn', 'invalid_payment_transition', {
      paymentId, from: payment.status, to, occurredAt,
    })
    return
  }

  // 条件更新：只接受比当前更新的事件（第 27 章的乱序处理）
  await db.update(payments)
    .set({ status: to, statusUpdatedAt: occurredAt })
    .where(and(
      eq(payments.id, paymentId),
      lt(payments.statusUpdatedAt, occurredAt)
    ))
}
★ 状态机同时解决了三个问题
  • 乱序事件：「已成功」之后收到「处理中」，转移非法，自动忽略
  • 重复事件：状态已经对了就直接返回，天然幂等
  • 非法状态：不可能出现「已退款但从未成功」这种数据

支付流程：不要相信客户端

⚠ 两个绝不能犯的错
  1. 金额由前端传上来。 POST /checkout { sku: 'HR199', amount: 1 } —— 攻击者把 9995 改成 1，你就一分钱卖了套餐。 金额永远在服务端根据 SKU 查出来。
  2. 前端说成功就发货。 浏览器里的「支付成功」回调可以被伪造、可以被重放，也可能因为用户网络中断而根本没执行。 只有 Webhook（或你主动查询的结果）才能改变订单状态。 
app.post('/api/v1/checkout', requireLogin, zValidator('json',
  z.object({ sku: z.string() })     // ← 注意：没有 amount 字段
), async (c) => {
  const { sku } = c.req.valid('json')
  const user = c.get('user')

  // 价格从数据库取，不接受客户端传入
  const vacation = await c.get('repo').findBySku(sku)
  if (!vacation || !vacation.available) {
    throw new HTTPException(404, { message: '这个套餐当前不可购买' })
  }

  const order = await c.get('db').createOrder({
    userId: user.id,
    sku,
    amountMinor: Math.round(vacation.price * 100),   // 最小货币单位（第 16 章）
    currency: 'CNY',
    status: 'requires_payment',
  })

  const intent = await payments.createIntent({
    amount: order.amountMinor,
    currency: order.currency,
    // 幂等键：网络重试不会创建两笔支付（第 24 章）
    idempotencyKey: `order:${order.id}`,
    metadata: { orderId: order.id, userId: user.id },
  })

  await c.get('db').attachIntent(order.id, intent.id)

  return c.json({ orderId: order.id, clientSecret: intent.clientSecret })
})
💡 metadata 里放你自己的 ID

支付平台允许你附加任意元数据。一定要把 orderId 放进去 —— 这样 Webhook 到达时你能立刻定位到本地订单，不用反查。
但不要放敏感信息：metadata 会出现在支付平台的后台界面和导出文件里。

订阅：难度是一次性支付的十倍

一次性支付是一个瞬间事件。订阅是一段持续的关系， 它会自己往前走、会失败、会被暂停、会变更 —— 而你的系统必须一直跟得上。

宽限期与挽回流程

★ 扣款失败大多不是「不想付」

行业数据里，订阅流失有相当一部分是非自愿的：卡过期了、 额度不足、银行风控拦截、换了张卡忘了更新。
直接停服等于把这些客户送走。正确做法是一套挽回流程（dunning）： 

const DUNNING_SCHEDULE = [
  { day: 0,  action: 'email', template: 'payment-failed-1' },
  { day: 3,  action: 'retry' },
  { day: 5,  action: 'email', template: 'payment-failed-2' },
  { day: 7,  action: 'retry' },
  { day: 10, action: 'email', template: 'payment-failed-final' },
  { day: 14, action: 'downgrade' },      // 降级到免费版，而不是直接删数据
]

/** 每天跑一次（第 26 章的定时任务 + 队列） */
export async function processDunning(env: Bindings) {
  const overdue = await getSubscriptions(env.DB, { status: 'past_due' })

  for (const sub of overdue) {
    const days = daysSince(sub.pastDueSince)
    const step = DUNNING_SCHEDULE.find((s) => s.day === days)
    if (!step) continue

    // 幂等：用 (subscriptionId, day) 做唯一键，重跑不会重复发信
    await env.TASKS.send({
      type: 'dunning-step',
      subscriptionId: sub.id,
      day: days,
      step,
    })
  }
}
💡 「降级」优于「删除」

宽限期结束后，把用户降到免费版并保留数据，而不是关停账号。
① 他随时可能回来付费（数据还在，回归成本为零）； ② 直接删数据在很多地区有法律风险； ③ 客服工单会少很多。
真要清理数据，也应该是「降级 N 个月后」的独立流程，并提前邮件通知。

升级、降级与按比例计费

场景常见处理要注意
升级（月付 → 年付、基础 → 专业） 立即生效，按剩余天数抵扣差价 用户期望「马上能用」。抵扣金额要在界面上说清楚，否则会有工单
降级 期末生效，不退差价 立即降级会导致「已经用掉的额度怎么算」的死结
数量变更（席位数） 增加立即计费，减少期末生效 同上：减少席位时要处理「多出来的人怎么办」
取消 期末生效，期间仍可用 提供「撤销取消」。相当一部分人会反悔
⚠ 按比例计费的账要让支付平台去算

「用了 17 天的月付套餐，升级到年付，应该抵扣多少」—— 这个计算涉及时区、月份天数、税率、货币精度，自己算几乎一定会有分歧。
主流支付平台都提供 proration 计算接口，调它，并把结果原样展示给用户确认。 你负责展示和记录，不负责计算。

计费周期与时区

⚠ 1 月 31 日订阅，2 月几号扣款？

这个问题没有「正确」答案，只有「一致」的答案。主流做法是取当月最后一天 （2 月 28 日），然后回到 31 日（3 月 31 日）—— 而不是从此永远变成 28 日。
不要自己实现这个逻辑。让支付平台管理周期，你只负责响应它发来的事件。
另外：计费周期的「一天」按哪个时区算？这是第 16 章的问题 —— 统一按 UTC，并在界面上明确标注时区，否则用户会觉得你早扣了一天钱。

把订阅状态变成权限

应用里到处都要判断「这个用户能用这个功能吗」。 这个判断绝不能实时去问支付平台 —— 太慢、有配额、而且对方挂了你就全挂。 

export const entitlements = sqliteTable('entitlements', {
  tenantId: text('tenant_id').primaryKey(),
  plan: text('plan', { enum: ['free', 'pro', 'enterprise'] }).notNull(),
  seats: integer('seats').notNull().default(1),
  // 有效期终点：宽限期也算在内
  validUntil: integer('valid_until', { mode: 'timestamp' }).notNull(),
  // 来源信息只用于排查，业务逻辑不读它
  source: text('source'),
  updatedAt: integer('updated_at', { mode: 'timestamp' }).notNull(),
})

/** 业务代码只用这一个函数（第 22 章的权限判断） */
export async function hasFeature(db: Db, tenantId: string, feature: Feature) {
  const ent = await db.getEntitlement(tenantId)
  if (!ent) return FEATURES.free.includes(feature)

  // 过期了就按免费版算
  if (ent.validUntil < new Date()) return FEATURES.free.includes(feature)

  return FEATURES[ent.plan].includes(feature)
}
★ 状态不确定时，宽容一点

Webhook 迟到了几分钟、对账还没跑、支付平台在维护 —— 这些时候你不确定用户到底付没付。
此时应该让他继续用。理由很简单：
① 错误地放行一个已过期用户，代价是几小时的服务成本；
② 错误地拦截一个付了钱的用户，代价是一张愤怒的工单、一条差评，可能还有退款。
做法：validUntil 在真实到期时间上再加一段缓冲。

退款与拒付

退款 Refund拒付 Chargeback
谁发起你（通常应客户要求）持卡人直接找发卡行
你的控制权完全可控几乎没有，钱先被扣走再让你申辩
成本退回本金（手续费通常不退）本金 + 一笔不低的争议处理费
时限有窗口期（通常几个月）你申辩的时限很短，通常只有几天
后果无拒付率过高会被支付平台限制甚至关停账户
★ 主动退款几乎总是比被拒付划算

用户投诉要求退款时，直接退掉通常是最优解：省下争议处理费、避免拒付率上升、 还可能挽回一个客户。
而且拒付率是支付平台评估你的核心指标 —— 它超标的后果远比几笔退款严重。 

app.post('/api/v1/orders/:id/refund', requirePermission('order:refund'), async (c) => {
  const order = await c.get('db').findOrderById(c.req.param('id'))   // 已含租户条件（第 22 章）
  if (!order) return c.notFound()

  if (order.status !== 'succeeded') {
    throw new HTTPException(409, { message: '只有已成功的订单可以退款' })
  }

  const refund = await payments.createRefund({
    paymentIntentId: order.intentId,
    amount: order.amountMinor,
    // 幂等键防止重复退款 —— 这里出错是真金白银
    idempotencyKey: `refund:${order.id}`,
  })

  // 注意：不在这里改状态。等 Webhook 确认后再改（唯一可信来源）
  await c.get('db').recordRefundRequested(order.id, refund.id)

  // 审计日志：谁在什么时候退了谁的款（第 22 章）
  await writeAudit(c, { action: 'order.refund', resourceId: order.id,
                        changes: { amountMinor: order.amountMinor } })

  return c.json({ ok: true, refundId: refund.id })
})
⚠ 争议来了，你需要证据

发卡行会要求你在几天内提交材料证明这笔交易是真实的： 用户是谁、什么时候下的单、从哪个 IP、服务有没有真的交付、有没有服务条款同意记录。
这些必须事先就在记录，事后补不出来。第 22 章的审计日志和第 29 章的结构化日志 在这个场景下的价值是直接可以用钱衡量的。

对账

第 27 章说过：只靠 Webhook 的系统一定会漏。在支付场景下，漏掉一个事件的意思是 用户付了钱但没拿到服务，或者反过来。 

/** 每天凌晨对账昨天的数据 */
export async function reconcilePayments(env: Bindings, day: string) {
  const remote = await payments.listCharges({ day })       // 支付平台的
  const local = await getSuccessfulOrders(env.DB, day)     // 我们的

  const remoteById = new Map(remote.map((r) => [r.metadata.orderId, r]))
  const localById = new Map(local.map((o) => [o.id, o]))

  const mismatches: Mismatch[] = []

  // 方向一：对方有，我没有 —— 用户付了钱没拿到服务，最严重
  for (const [orderId, charge] of remoteById) {
    if (!localById.has(orderId)) {
      mismatches.push({ type: 'missing_locally', orderId, amount: charge.amount })
      // 走和 Webhook 完全相同的处理逻辑，保证幂等（第 27 章）
      await env.TASKS.send({ type: 'apply-payment-status', orderId, status: 'succeeded' })
    }
  }

  // 方向二：我有，对方没有 —— 收入漏损或数据错误
  for (const [orderId, order] of localById) {
    if (!remoteById.has(orderId)) {
      mismatches.push({ type: 'missing_remotely', orderId, amount: order.amountMinor })
    }
  }

  // 金额也要逐笔核对
  for (const [orderId, charge] of remoteById) {
    const order = localById.get(orderId)
    if (order && order.amountMinor !== charge.amount) {
      mismatches.push({ type: 'amount_mismatch', orderId,
                        local: order.amountMinor, remote: charge.amount })
    }
  }

  log('info', 'reconciliation', { day, checked: remote.length, mismatches: mismatches.length })

  // 差异不为零就告警 —— 这是必须有人看的那类告警（第 29 章）
  if (mismatches.length > 0) await alertFinance(day, mismatches)
}

测试

要测什么怎么测
状态机的每条转移纯单元测试，不需要任何网络。性价比最高
非法转移被拒绝断言「已成功」收到「处理中」事件后状态不变
Webhook 重复投递同一个事件发两次，断言只发货一次（第 27 章）
各种失败卡支付平台提供测试卡号：余额不足、被拒、需要 3DS 验证
金额不能被篡改请求体里塞 amount: 1，断言实际收款仍是真实价格

⚠ 生产密钥和测试密钥要在结构上隔离

「不小心用生产密钥跑了测试」是真实发生过的事故 —— 给真实用户扣了钱。
对策：
① 密钥名区分明显（sk_test_ / sk_live_），启动时校验环境与密钥前缀是否匹配；
② 测试环境的密钥根本不配置生产的那份（第 12 章的环境隔离）。

指标为什么
支付成功率突然下降通常意味着风控规则变了或某个渠道故障

常见坑清单

★ 上线前逐条确认
  • ☐ 卡号从不经过你的服务器
  • ☐ 金额永远从服务端取，不接受客户端传入
  • ☐ 只有 Webhook / 主动查询能改变订单状态，前端回调只用于更新界面
  • ☐ 创建支付和退款都带幂等键
  • ☐ 状态机拒绝非法转移，条件更新处理乱序事件
  • ☐ 金额用最小货币单位的整数存，且币种寸步不离（第 16 章）
  • ☐ 有 entitlement 表，业务代码不直接查支付平台
  • ☐ 状态不确定时倾向于放行
  • ☐ 扣款失败有挽回流程，宽限期结束是降级不是删除
  • ☐ 每日对账，双向核对，差异有人跟进
  • ☐ 退款、状态变更都有审计日志（第 22 章）
  • ☐ 测试密钥与生产密钥在启动时校验
  • ☐ 支付相关日志不含卡号、CVV 等任何敏感信息（第 29 章）

小结

  • 不要碰卡号：用托管收银组件，把合规范围缩到最小。
  • 用状态机而不是布尔值；状态只能前进，非法转移直接拒绝。
  • 金额在服务端算，状态由 Webhook 定 —— 前端说什么都不算数。
  • 订阅的难点在「逾期未付」这段挽回窗口，以及升降级的按比例计费（让平台算）。
  • 用 entitlement 表隔离支付系统和业务系统；状态不确定时倾向于放行。
  • 主动退款通常比被拒付划算；争议需要的证据必须事先就在记录。
  • Webhook 会丢，每日双向对账是必需品，不是加分项。
  • 状态机的单元测试性价比最高；生产与测试密钥要在启动时校验。

动手练习

  1. 用支付平台的测试模式做一笔完整支付：创建订单 → 唤起收银 → 接收 Webhook → 改状态。全程用测试卡号。
  2. 在请求体里塞 amount: 1，确认实际收款金额仍是数据库里的价格。
  3. 把同一个 payment.succeeded 事件手动重投三次，确认只发货一次。
  4. 实现 canTransition，为每一条合法和非法转移各写一个测试。这是本章投入产出比最高的部分。
  5. 用测试卡号触发一次扣款失败，走一遍挽回流程的第一步（发邮件）。
  6. 手工在数据库里删掉一条已成功的订单，跑对账脚本，确认它被识别为「对方有、我没有」并触发了补偿。
  7. 做一张 entitlement 表，把至少一个功能开关改成读它，然后把订阅状态改成过期，确认功能被关闭。
